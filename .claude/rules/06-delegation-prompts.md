# Rule 06: サブエージェント委譲プロンプト (指示の書き方)

Agent ツールで `poc-analyst` / `architecture-designer` / `Explore` / `design-reviewer` 等へ
タスクを委譲するときの**プロンプトの書き方**を定める。「誰を呼ぶか・どのモデルにするか」は
`02-agents.md`、本ファイルは「どう指示すれば良い出力が返るか」のみを扱う。

前提: サブエージェントは**明示された指示への忠実さが高い分、書かれていない意図は推測しない**。
オーケストレーター (メインセッション) が持つ文脈をどれだけ指示文に落とせるかが出力品質をほぼ決める。

## 3 つの原則

1. **サブエージェントは会話コンテキストゼロで起動する**
   メイン会話で確定した事実 (絶対パス・決定事項・制約・却下済みの案) は全て指示文に書き写す。
   「さっきの」「例の機能」「前に話した通り」は一切通じない。
2. **出力仕様が品質を決める**
   何を・どの粒度で・どの形式で返すかを構造で指定する
   (「リポジトリ相対パス:行 付き」「表で」「見出し文言はそのまま引用」)。
3. **途中で質問できない前提で書く**
   迷いそうな分岐に判断ルールを先に与える (「A と B で迷ったら v2 の既存規約に寄せる」
   「確信が持てない項目は『要確認』と明記して先に進む」)。

## 指示テンプレート (7 要素)

| # | 要素 | 書くこと | 省くと起きること |
|---|---|---|---|
| 1 | **目的/背景** | 何のためのタスクか。**出力が何にどう使われるか** | 的外れな粒度・網羅で返ってくる |
| 2 | **対象** | リポジトリ**絶対パス** + 対象ディレクトリ。確信がなければ「〜あたり」とヒント | 探索の浪費・別リポを触る |
| 3 | **やること** | 番号付きで分割。1 項目 = 1 つの検証可能な作業 | 一部だけやって「完了」と報告される |
| 4 | **従うべき既存例** | 平仄を合わせたい文書・実装の パス:行 | 既存の書式・規約から浮いた成果物 |
| 5 | **制約・やらないこと** | スコープ外の明示、**参照リポジトリを編集しないこと**、該当する頻出パターン番号 | 善意の巻き込み変更・既知の落とし穴の再発 |
| 6 | **完了条件** | 実行すべき検証 (`make doc-lint` / 出典の実在確認) と期待結果 | 「たぶん合ってる」状態で返ってくる |
| 7 | **報告フォーマット** | 言語 (日本語)、構造 (①成果物 ②検証結果 ③残課題/要確認)、出典必須 | 検証不能な「完了しました」報告 |

すべてのタスクで 7 要素全部が要るわけではない。ただし **1・2・7 は必須**。

## 役割別の追記事項

### 事実収集 (poc-analyst / Explore / general-purpose)

- **指示の冒頭に「まず `.claude/skills/investigating-thoroughly/SKILL.md` を読み、その手順に従う」を含める**
  (`07-quality-protocols.md`)。組み込みエージェント (Explore 等) は定義に埋め込めないため、
  委譲プロンプトが唯一の適用経路
- **具体性のレベルを指定する**。「調べて」ではなく「◯◯を設計判断できるレベルの具体性で」
- 報告してほしい情報を**名詞で列挙**する (「エンドポイントとメソッドの表」「テーブル名とカラム」
  「ミドルウェアの適用順」)
- **「事実と推測を分けて書く。調べていない範囲は『未調査』と明記する」を必ず入れる**
- **「参照リポジトリは読み取り専用。ファイルを一切変更しない」を制約に入れる**

実例 (v2 の認証機構を設計入力として集める):

```
対象リポジトリ: /Users/yuyamorishita/aillio/hassan/hassan-v2-backend (読み取り専用・変更禁止)

まず /Users/yuyamorishita/aillio/hassan/hassan_v3/.claude/skills/investigating-thoroughly/SKILL.md
を読み、その手順に従ってください。

目的: hassan_v3 の本番設計で「認証・テナント境界」を v2 準拠で設計するための事実収集。
出力は docs/analysis/gap-analysis.md の「認証・テナント」節にそのまま転記します。

1. 認証方式 — auth/ 配下:
   - トークンの受け渡し (ヘッダ名・形式・有効期限)、検証の実装箇所
   - ロールの種類と、それぞれが通るミドルウェア
2. テナント境界 — db/schema.sql と controller/:
   - 所有権を表すカラムと、それを持つテーブルの一覧
   - 一覧系エンドポイントでの絞り込みがどの層で行われているか (代表 3 例)
3. 401/403/404 の使い分け — 実際の分岐箇所を 3 例

報告は日本語で、リポジトリ相対パス:行 付き。事実と推測を分け、未調査の範囲は明記してください。
```

### 設計起草 (architecture-designer)

- **確定済みの前提を全て書き写す** (採用アーキ方針・却下済みの案・すでに合意した AC)
- **判断が割れたときのルールを与える**: 「v2 の既存規約に寄せる。逸脱するなら却下案と理由を書く」
- 出力先ファイルと章構成を指定する (`docs/design/<topic>.md` の第 N 章)
- `08-production-gates.md` の該当領域を名指しする (「可観測性の節では 08 の O-1〜O-4 に回答すること」)

### レビュー (design-reviewer)

- 対象差分の範囲を明示 (「未コミット差分」「main...HEAD の全差分」「docs/design/architecture.md 全文」)
- 結果の保存先を指示 (`aidlc-docs/reviews/<feature>/review.md` — push ゲートが要求)
- **本番基準で見ること**を再掲する (PoC 基準に引きずられない)

## モデル・effort の添え方 (詳細は `02-agents.md`)

- 機械的・定型的 (一覧化・転記・突き合わせ) → `effort: low〜medium` を明示
- 非自明 (経路の挙動差判定・前例のない設計) → `model: opus` へエスカレーション。
  **指示を曖昧なまま opus に丸投げするより、指示を具体化して sonnet に渡す方が良い結果になることが多い**
- 7 要素を書き切れない (= 自分でも要件が曖昧な) タスクは委譲せず、先に `aidlc-planner` で要件を固める

## アンチパターン

| ダメな指示 | 何が起きるか | 直し方 |
|---|---|---|
| 「PoC について調べて」 | 用途不明のまま網羅的で薄い報告 | 目的 + 具体性レベル + 報告項目の名詞列挙 |
| 「本番向けにいい感じに設計して」 | ワーカーの自己基準で別物になる | 採用方針・AC・却下案を列挙 |
| 「さっき決めた方針で」 | コンテキストゼロなので方針を知らない | 決定事項を指示文に書き写す |
| 巨大トピックを 1 回で委譲 | 途中経過が見えず検証不能 | 検証可能な単位に分割し、並列可否を設計 |
| 完了条件なし | 「完了しました」だけ返る | 検証手段 + 報告 3 点を義務化 |
| 迷ったら聞いて、と書く | 質問できずブロック or 勝手に判断 | 判断ルールを先に与える |

## 委譲は指示で終わらない (オーケストレーターの責務)

**思考ステップの実体は `orchestrating-delegation` skill** — 委譲を含むタスクではこれを適用する:

1. **報告の抜き取り検証** — 報告を成果物や次の指示に取り込む前に、load-bearing な事実
   (パス・行番号・テーブル名・数値・順序) を一次ソースで照合する。「報告が詳細」≠「正確」。
   **設計リポでは特に重い** — 誤った事実は設計に埋め込まれ、実装リポまで運ばれる
2. **葉だけ委譲** — 受入基準とコンテキストを事前に文章化できる作業のみ委譲し、
   相互作用する設計判断・統合はオーケストレーターに残す
3. **タスク固有検証** — `make doc-lint` がその主張を検証しないなら (内容の正しさは検証しない)、
   使い捨てでよいので照合コマンド (grep 等) を作り、**実行コマンドと出力を証拠として報告に含める**

## 機構を直したら、その機構を語る文書を同じ差分で直す (2026-07-30 追加)

**3 巡連続でレビューの最上位指摘が同じ型だった**: 「`templates/` の機構は直したのに、
設計文書が『未対応』『未設定』『未実装』と書いたまま」。読者 (実装リポの開発者) は文書を正として読むため、
**直した機構が使われず、同じものを再実装する**か「担保されていない」と誤解する。

**手順 (機構 = `templates/` 配下・`scripts/` 配下を編集したら必ず行う)**:

1. 編集したファイル名で**設計文書を全文検索する** — `grep -rn "<ファイル名>" docs/ aidlc-docs/`。
   **キーワードは数値だけでなく状態語も grep する** (2026-07-31 追加。**5 巡連続再発の原因は手順側の不足だった**) —
   `未了` / `未実装` / `未設定` / `未登録` / `未着手` / `含まれていない` / `是正要求` / `必要` / `無い`。
   数値語 (`5 種` / `#4 / #5` 等) だけで再検査すると「登録は未了」「是正要求を…出した」に一致せず**構造的に取り残す**
2. ヒットした箇所のうち、**状態を語っている記述** (「未実装」「未設定」「無い」「追加する必要がある」
   「是正要求」「§N の残作業」) を**同じ差分で更新する**
3. **行番号を引用している箇所は実測値へ更新する** (`grep -n` の結果を使う)。
   機構にステップを足すと後続の行番号が全部ずれる
4. 「是正要求」の表がある文書は**状態列を持たせる** (未対応 / 実施済み / 対応不要 + 日付)。
   状態列が無い表は、実施しても未対応に見えたまま残る

**やってはいけないこと**: 機構だけ直して「文書側は次のレビューで指摘されたら直す」。
それは**レビュー 1 巡分のコスト**を毎回払うことになる (実測: 3 巡で重大 3 件・中 6 件がこの型だった)。

## 運用

- 委譲がうまくいかなかった場合、原因はほぼ 7 要素の欠落。再委譲の前に**どの要素が欠けていたか**を
  確認し、パターン化できるものは本ファイルへ追記する
- 報告の誤りが成果物まで到達した場合は責務 1 (抜き取り検証) の省略が原因。
  再発パターンは `orchestrating-delegation` skill の「よくある間違い」表へ追記する
