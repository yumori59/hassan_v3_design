# Rule 07: 品質プロトコル (調査・計画・執筆の思考ステップ)

## 原則

規約 (what: 検証ゲート・レビュー・本番観点) は `CLAUDE.md` と rules 01〜06・08 が定める。
本 rule は **思考ステップ (how: どう調べ・どう設計し・どう完了を判断するか)** を場面ごとの
skill として定め、**デフォルトで適用する**。

| 場面 | 適用 skill | 起動タイミング |
|---|---|---|
| 調査・「どこで/なぜ/どう動くか」への回答 | `investigating-thoroughly` | 調べ始める前 + 報告を確定する直前 |
| 開発計画・設計判断 | `designing-development-plans` | 要件を受けた直後 (aidlc-planner 経由でも直接でも) |
| 構想資料 (concept.md) の作成 | `writing-concept-docs` | 「資料に起こしたい」と言われた直後 |
| サブエージェントへの委譲 | `orchestrating-delegation` | 委譲プロンプトを書く前 + 報告を取り込む直前 |
| 完了・合格の主張 | `verification-before-completion` | 「できました」と書く直前 |

## 適用の仕組み (デフォルト化の配線)

- **メインセッション**: 該当タスクを受けたら対応 skill を Skill ツールで起動する
  (本 rule が常時ロードされるため、上表がトリガーになる)
- **サブエージェント委譲時**: サブエージェントは Skill ツールを持たないため、
  委譲プロンプトに「まず `.claude/skills/<name>/SKILL.md` を読み従う」を含める (`06-delegation-prompts.md`)。
  **絶対パスで参照させる** (`/Users/yuyamorishita/aillio/hassan/hassan_v3/.claude/skills/...`)
- **プロジェクトエージェント**: `aidlc-planner` / `poc-analyst` / `architecture-designer` /
  `design-reviewer` の定義には該当 skill が必読として組み込み済み (定義変更時に外さない)

## skill の実例について (重要)

これらの skill は PoC (`claude_managed_agents`) での失敗・成功の観測から書かれており、
実例・引用が PoC のコード (`cmd/devui/...`・BE-2/BE-5 等) を指している。
**原則はリポジトリ非依存だが、実例は PoC のもの**として読むこと。v3 への読み替え:

| skill の記述 | v3 での意味 |
|---|---|
| 「知識が Go / frontend / prompts の 3 層に散在」 | 知識が **PoC / v2 / 本リポジトリの設計書** の 3 箇所に散在。1 つ見て結論しない |
| 「死んでいるコードを手本にしない」 | PoC の未配線コード・v2 の廃止済みエンドポイントを設計の根拠にしない |
| 「永続データとの契約」 | **v2 の本番 DB に既存データがある**。設計変更は移行手順とセットでなければ未完成 |
| 「検証ゲート (go test / tsc)」 | `make check` (**本数はここに書かない** — ルート `CLAUDE.md` の検証ゲート節が SSOT。DR-9)。ただし内容の正しさは検証しない (`05-harness.md`) |

## 3 つに共通する原則

1. **局所で結論しない** — 単一ファイル・単一経路・単一検索軸・最初のヒットで打ち切らない
2. **「同等」「存在しない」「完了」は検証済み主張としてのみ書く** — 見た目の類似・未探索・
   未実行のまま断定しない。読者 (と実装リポの開発者) は検証せずに転記する
3. **カバレッジの正直さ** — 調べていない範囲・対象外と判断した理由・残課題を報告に含める

## 運用

- 新たに観測された失敗パターンは該当 skill の「よくある間違い」表へ追記する
  (`feedback_review_patterns.md` と同じ還流)
- skill の変更は `writing-skills` の手順 (ベースライン → 執筆 → 再検証) に従う
