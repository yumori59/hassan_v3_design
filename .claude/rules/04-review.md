# Rule 04: レビュー必須

## 原則

起草エージェントの「完了」報告は**完了とみなさない**。`design-reviewer` を通して重大事項ゼロを
確認するまでが完了。**設計の誤りは実装リポで N 倍のコストになって返ってくる** — このリポジトリの
レビューが、システム全体で最も費用対効果の高い関門である。

## レビュータイミング

| タイミング | 対象 |
|---|---|
| 起草エージェントの完了直後 | 当該の差分 |
| Design Freeze 前 | その feature の設計成果物全体 |
| push / PR 前 | ブランチの全差分 (`main...HEAD`) |

## レビュー観点 (`design-reviewer` が実施)

1. **事実の裏取り** — 設計が前提にしている PoC / v2 の事実に出典 (リポジトリ相対パス:行) があり、
   実在するか。**出典なしの断定は最優先の指摘対象** (`make doc-lint` は実在は見るが、内容の正しさは見ない)
2. **本番観点 (`08-production-gates.md`) の網羅** — 認証・テナント分離・権限 / 可観測性・LLM コスト /
   CI/CD・デプロイ・IaC。各領域に設計上の回答があるか、「対象外」に理由と先送り先があるか
3. **v2 規約との整合** — ハイブリッド方針 (ルート `CLAUDE.md`) どおり、v2 の 3 層・sqlc/wire・
   `CodedError`・命名規約に沿った設計か。逸脱に理由と却下案が書かれているか
4. **頻出パターン** (`feedback_review_patterns.md` — SSOT。全パターンを確認する)
5. **移行の実行可能性** — 既存データ (v2 の本番 DB) との共存・移行手順・ロールバック・
   段階リリースが設計に含まれるか
6. **AC トレーサビリティ** — 受入基準に AC-ID があり、plan/設計書から参照されているか
   (`make check-traceability` の結果を貼る)
7. **決定の明示性** — 主要な設計判断に「採用案 / 却下案 / 理由」が揃っているか。
   曖昧な記述 (「適切に」「必要に応じて」) が実装者の判断に丸投げになっていないか

## 出力

- 重大 / 中 / 軽微 / 良かった点 で分類
- 重大ゼロでない場合、修正してから再レビュー
- レビュー結果は **`aidlc-docs/reviews/<feature>/review.md`** に保存する
  (**push/PR ゲートがこれを要求** — `05-harness.md`)
- review.md には**レビューした設計成果物のリポジトリ相対パスを必ず記載する** —
  push ゲートが「レンジ内で変更された review*.md に、変更された設計成果物の相対パスが登場すること」を
  要求する (無関係 feature の review 同梱によるすり抜け防止。basename のみの記載は照合にヒットしない)
- 修正後の再レビュー (または軽微修正の追記) も review.md に反映する — push ゲートは
  **review.md の最終更新より後の設計成果物の変更コミット**を「レビューが古い」としてブロックする

## 自己レビュー禁止

起草したエージェント・セッションとは**別セッションで** `design-reviewer` を呼ぶ。
