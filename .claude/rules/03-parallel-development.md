# Rule 03: 並列作業

## 原則

**依存関係がない作業は同時に走らせる**。設計リポでは特に「事実収集 (analyst)」の並列化が効く —
PoC・v2 backend・v2 frontend は独立した読み取り対象で、衝突しない。

## 並列化の判断基準

### 並列実行可

- **異なる参照リポジトリ・異なるドメインへの事実収集** (例: PoC の会話機能調査 と v2 の認証機構調査)
- 独立した設計トピックの起草 (例: `docs/design/data-model.md` と `docs/design/observability.md`)
- ドキュメント執筆と、別トピックの調査

### 直列必須

- **同一ファイルの編集** (マージ衝突)
- **requirements → plan → 設計書** の連鎖 (上流が変わると下流が無効になる)
- **事実収集 → その事実に依存する設計判断** (analyst の報告を検証してから designer に渡す。
  `06-delegation-prompts.md` の責務 1)
- レビューは集約する (並列で起草しても、レビューは差分全体を 1 セッションで見る)

## 実行方法

### 1. plan.md に並列タスクを必ず明記

`aidlc-planner` の出力には**「並列実行可能なタスク」セクションを必ず設ける**。

```markdown
## 並列実行可能
- [ ] PoC の会話フロー調査      ← poc-analyst
- [ ] v2 の認証・テナント境界調査 ← poc-analyst
- [ ] 用語集の整備               ← 手動
```

### 2. Agent 並列呼び出し

複数の独立した作業は、**同一メッセージ内で複数の `Agent` ツールを発行**する。

### 3. worktree 隔離

設計リポでは通常不要 (テキスト編集のみ・ビルド成果物なし)。
**大きな設計案を 2 案並行で書き切って比較する**ようなケースでのみ worktree を使う。

## やってはいけない

- 並列を理由に**同一ファイルへの同時編集**
- **未検証の analyst 報告を、複数の designer に同時に配る** (誤った事実が全成果物に伝播する)
- レビューの並列スキップ
