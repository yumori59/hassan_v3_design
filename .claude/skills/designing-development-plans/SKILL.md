# 開発計画の設計 (現状把握 → 設計判断 → 検証可能な分解)

## Overview

計画の品質は分解の巧拙より **現状把握の深さ** で決まる。2026-07-05 のベースライン検証では、
高品質だった計画はいずれも「書く前に読む」に時間の大半を投じていた:
作ろうとした機能が実装済みだった・キー設計 (idea_id) が移行途中だった・
要件の言葉 (「再発散」) の実体が想定と違った — どれも、把握を飛ばすと
**計画全体が無効になる** 種類の事実である。

AIDLC のプロセス (`01-aidlc.md`・aidlc-planner) はフェーズと成果物を定める。
本 skill はその中身 — 各フェーズで何を考えるか — を定める。planner を経由しない
軽量な計画・メインセッションでの直接の計画にも適用する。

## ステップ

### ① 現状把握が先 — 計画の 1 文字目を書く前に読む

- **その機能 (または近縁機能) が既に存在しないか** を BE / FE / DB の 3 面から grep する。
  部分的にでも存在するなら、計画は「新規設計」ではなく「ギャップ分析」になる
- **要件の各キーワードの実体**をコードで特定する (「一覧」「維持」「再発散」が
  指す挙動はどの関数か)。解釈が複数あり得るなら、コードの実態から最有力を選び、
  選んだ解釈を要確認に載せる
- 触るデータの**同一性とライフサイクル**を確認する: キーは何か、いつ再生成されるか、
  移行途中の仕組み (新旧キーの併存・バックフィル) はないか
- **死んでいるコードを手本にしない**: 似た既存実装を真似る前に、それが実際に
  配線されている (呼び出し元が非テストコードに存在する) ことを確認する

### ② 設計判断には理由と却下案

主要な設計判断 (データの持ち方・キー設計・エンドポイント形状・置き場所) は、
採用案に加えて**検討して却下した代替案とその理由**を書く。最初に思いついた 1 案を
そのまま採用しない。根拠として最も強いのは「既存コードベースの一貫した設計」への
参照 (file:line)。

### ③ 影響範囲の層チェックリスト

- DB: migration 連番・store・**インメモリ / nil-pool 経路 (BE-5。CI 前提)**
- BE: ハンドラ・ルーティング・DI 配線 (main.go)・**同じレスポンスを組み立てる全箇所**
  (一覧 API と集約 API など。1 箇所だけ直すマージ漏れが頻出)
- FE: types・api 境界・components・エクスポート系 (CSV 等) の追従
- prompts/ (LLM に渡る知識の重複)・ドキュメント・テスト

### ④ エッジケース・ライフサイクルの機械的列挙

空/ゼロ件・**機能追加前に作られた既存データ** (旧形式・localStorage・旧キー) との共存・
再実行/冪等性・並行操作・参照先の消滅 (親の削除・再生成で orphan になる派生物)・後方互換。

### ⑤ 出力: 検証可能な分解

- 受入基準 → テストケース (Red 先行・AC-ID 付き。`01-aidlc.md` の形式)
- 直列必須 (DB 変更フローが起点) と並列可能の区別 (`03-parallel-development.md`)
- **要確認事項には自分の仮定を添える** (「◯◯と仮定して進める。違えば指摘を」)。
  質問だけ並べて計画を宙吊りにしない
- スコープ外 (やらないこと) を明記する

## よくある間違い

| 間違い | 現実 |
|---|---|
| 要件文言から直接タスク分解 | 機能が既に在った / 言葉の実体が違った、で計画全体が無効化する |
| 最初の設計案をそのまま採用 | 却下案の無い計画は、レビューで設計ごと手戻りする |
| 影響範囲を「主要ファイル」だけ列挙 | 同じデータを組み立てる箇所は複数ある。全箇所列挙する |
| 要確認を質問の羅列にする | 仮定を添えないと計画が宙吊りになり、往復だけ増える |
| 似た既存コードを無条件に手本にする | 配線されていない死にコードがある。呼び出し元の存在を先に確認 |
| 新規データの設計で既存データを忘れる | 機能追加前のデータ (旧形式・localStorage) との共存・移行が必要 |

## 実例 (本リポジトリ: 2026-07-05 ベースライン検証)

「テーマのアーカイブ機能」の計画依頼 — 機能は**ほぼ実装済み**だった (status='archived'・
FE タブ・統計カード)。①を実施した計画は「ギャップ 2 点 (起動 UI が無い / all タブに
出続ける) + categorize() の completedAt 優先との競合」という正しい計画に落ち、
①を飛ばせばゼロから作り直す無効な計画になった。
「アイデアのピン留め」では、①の把握 (idea_id の段階移行・「全部再発散」= 全 UUID 再発番・
死にコード diverge_idea_status の存在) がキー設計とスコープ判断を決めた。
この skill は観測された高品質計画の再現手順であり、失敗の修正ではなく水準の床上げが目的。
