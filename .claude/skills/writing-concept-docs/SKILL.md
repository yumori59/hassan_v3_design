# 構想資料 (Concept Doc) の作成

## Overview

構想資料は**「合意を作る物語」と「実装の骨格」の二層**を 1 つの文書で担う。
核心は 2 つ: (1) **書く前に前提を確定する** — 用途・スコープ・推奨案をユーザーと合意してから書く。(2) **シナリオは受入テストではなく共感装置** — ユーザーの思考過程を併記し、機能の必然性を読者に体感させる。

## When to Use

- 「資料に起こしたい」「構想をまとめたい」— requirements 化の前段
- 使わない: requirements.md / plan.md を書く段階 (→ `aidlc-planner`)、小さな改修

## プロセス

1. **現状調査を先に** — Explore agent で既存フロー・再利用可能資産を把握してから質問する (質問の質が上がる)
2. **前提を AskUserQuestion で 1 問ずつ確定** — 定番 5 問を順に:
   | 順 | 質問 | 決まること |
   |---|---|---|
   | 1 | 資料の用途・読者 (開発起点/提案/両方) | 技術詳細の深さ |
   | 2 | 既存 UI/フローとの関係 (置換/併存/検証用別画面) | スコープ |
   | 3 | 情報ソース・制約 (multiSelect) | 実現手段の幅 |
   | 4 | シナリオの粒度・本数 | 分量と形式 |
   | 5 | 推奨アーキ案 — **preview に ASCII 構成図**を付けた 2-3 案比較 | 資料の推奨軸 |
3. **設計をセクション毎に提示・確認** (200-300 語ずつ)。ユーザーが「最後までやり切って」と言ったら**残りの設計判断は自分で確定して書き切る** (再確認に戻らない)
4. **資料の型 (下記) で書く** → `aidlc-docs/inception/<feature>/concept.md`
5. 確定回答は**資料末尾の付録に `[Answer]:` 証跡**として残す

## 資料の型 (章構成)

| 章 | 必須要素 |
|---|---|
| 1. 背景と課題 | 現行フロー図 + 課題表 (C-1〜、現状の具体像つき) |
| 2. コンセプトと提供価値 | 一言の主張 (例:「主導権の反転」) + 現行との対比表 + UI イメージ (ASCII) |
| 3. グッドシナリオ | 王道 1 本をフル対話で (書き方は下記) |
| 4. パターンカタログ | 可変な振る舞いの一覧表: パターン名/目的/**トリガー発話例**/ソース/出力形式 + 設計原則 |
| 5. アーキテクチャ | 推奨案の図と責務表 + **代替案比較表** + 既存資産の再利用マップ + 新規要素 |
| 6. ロードマップ | 増分ごとに「**検証したい問い**」を紐付け |
| 7. リスクと論点 | 対応方針つき表。既知バグパターン (feedback_review_patterns.md) との接続を含める |
| 付録 | 確認済み前提の `[Answer]:` 証跡 |

**参照実例** (この型で書かれ採用された成果物): `aidlc-docs/inception/conversational-ideation/concept.md` (git e7bfc81)。
章構成・シナリオ・付録の `[Answer]:` 証跡 (同 497-505 行) は初出のまま通り、後続修正は §5 アーキテクチャの技術参照の正確化 12 行のみ (2a4c1b9)。迷ったらこの実例の粒度に合わせる。

## シナリオの書き方 (最重要)

- **実在感のある題材**: リポジトリ内の実データ (登録済みアセット等) から選ぶ。ペルソナには立場と動機 (例: 上長への説明責任) を与える
- **幕構成** (起点→調査→深掘り→絞り込み→実行→成果、5〜7 幕) で対話レベルに書く
- 各幕に **💭 ユーザーの思考** を併記 — 発話の裏の疑念・納得・関心の移動を書く。これが機能の必然性の説明になる
- **AI 側からの論点提起を最低 1 箇所仕込む** (聞かれたことに答えるだけの受け身 Q&A にしない)。実例: 市場規模の回答に「機器にお金が払われるかは別問題」と収益化の論点を足し、ユーザー思考側で「鋭い指摘」と受けて次の幕の深掘りへ接続 (参照実例 concept.md 幕 3、215 行・347 行)
- 末尾に**幕→設計要件の対応表**を置き、物語を要件に接続する

## Common Mistakes

| 間違い | 修正 |
|---|---|
| シナリオを Given/When/Then の受入テスト形式で書く | それは requirements の仕事。concept ではユーザー心理を書く |
| 前提質問を飛ばして目次から書き始める | 用途・スコープ次第で資料が別物になる。定番 5 問が先 |
| アーキ推奨を資料内で初出しする | 質問 5 (preview 比較) で先に合意を取る |
| 質問回答を会話に置き去りにする | 付録の `[Answer]:` 証跡に必ず書き戻す |
| いきなり requirements.md を作る | concept.md が前段。合意後に `aidlc-planner` へ |
