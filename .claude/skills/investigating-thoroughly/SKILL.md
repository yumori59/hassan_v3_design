# 徹底調査 (結論の前に全経路と反証)

## Overview

調査の失敗は 2 種類ある。**見つけ損ない** (単一の検索軸・単一の層で打ち切る) と
**誤認** (見た目の類似を検証なしに「同一」と報告する)。網羅は複数軸の探索で、
正確さは主張単位の裏取りで担保する — この 2 つは独立で、片方では代替できない。
「詳細な報告」は「正確な報告」を意味しない。報告の読者は検証せずに転記するので、
誤認は成果物・意思決定まで到達する。

## ステップ

### ① 問いの確定

何を判断するための調査か (答えの使われ方) を 1 文にしてから探し始める。
依頼が曖昧なら解釈を列挙して最有力を選び、選んだ解釈を報告に明記する。

### ② 多軸探索 — 1 つの軸で打ち切らない

- 軸: **名前** (シンボル/ファイル名) / **内容** (文言・エラーメッセージ・数値) /
  **利用側** (呼び出し元・import) / **テスト** / **履歴** (`git log -S`)
- このリポジトリは同じ知識が 3 層に散る: **Go コード・frontend/・prompts/**。
  コード層だけ調べて終えない (BE-2 の hard cap 散在が典型)
- 「見つからない」と結論するのは、別の軸で 2 回探してから

### ③ 経路の完全列挙

同じ機能に複数の実行経路がないかを必ず確認する
(例: managed/raw、DB あり/インメモリ (BE-5)、engine=api/agent)。
1 経路を精読しただけで機能全体を結論しない。未使用に見える系統は
「入口の呼び出し元が非テストコードに無い」ことを grep で確認してから未使用と書く。

### ④ 比較主張の裏取り — 「同等」は検証済み主張として読まれる

「A も B と同様」「同等の処理」と書く前に、比較次元
(入力ソース・既定値・クランプ/上限・設定参照・エラー処理) ごとに**両方のコードを
実際に読んで**差分を確認する。片方を精読し、もう片方を見た目で推測するのが誤認の最大源。
差分があれば「同等」ではなく差分そのものを報告する。

### ⑤ 反証探索

結論を書く前に、結論に反する証拠を 1 回探す:
条件分岐の else 側、feature flag / 環境変数による分岐、例外ケース、
既存テストの期待値が自分の結論と矛盾しないか。

### ⑥ 報告 — 事実と推測の分離、カバレッジの正直さ

- 確認した事実は file:line 付き。推測は「推測」と明記して確信度を添える
- **調べていない範囲を明記する** (「FE 側は未調査」「実行時挙動は未確認」)。
  「見つからなかった」と「存在しない」を区別して書く
- 表・リストへ転記する数値・文言は転記時に一次ソースへ再照合する
  (丸め・表記ゆれ・行番号ズレが混入しやすい)

## よくある間違い

| 間違い | 現実 |
|---|---|
| 片方の経路を精読し、似た経路を「同等」と報告 | 比較は次元表で両方読む。「同等」の一語が既知の挙動差を上書きする |
| 最初のヒットで結論 | 知識は Go/FE/prompts の 3 層に散在。多軸で 2 周目まで回す |
| 「見つからなかった」=「存在しない」 | 軸を変えて再探索してから「未発見」と書く (「無い」とは書かない) |
| 推測を事実の顔で書く | 読者は検証せず転記する。誤認は成果物まで到達する |
| 網羅できたので正確なはず | 網羅 (見つけた数) と正確さ (主張の裏取り) は独立。両方やる |
| 呼び出されていない = 無関係として省略 | 未使用系統の食い違う値は将来の不整合リスク。存在は報告する |

## 実例 (本リポジトリ: アイデア生成数の調査)

2026-07-05 のベースライン検証で、sonnet 調査エージェントは生成数の knobs を
3 層 + 未使用系統まで発見する優れた網羅を見せた。しかし raw 経路
(`cmd/devui/diverge_raw.go`) を「既定15・上限50で一致 / 同等処理」と報告した —
実際は `settings.IdeaCount` を参照せず上限クランプも無い (managed 経路との
既知の挙動差、memory: project_idea_count_knobs)。managed 経路を精読した後、
raw 経路は**見た目の類似から挙動を推測した**ことが原因。④はこの再発防止。
