## 0. 本書の位置づけ

**LLM を主機能とするプロダクトで、可観測性は「あとで足す」ことができない**。
計測点は呼び出し経路の内側にあるため、後付けは全経路の改修になる
(PoC がまさにその状態: 発散経路だけ計測され、他は計測なし)。

本書は **ログ / メトリクス / LLM 利用量 / アラート** の設計を確定する。
分散トレースは初期増分では採らない (§2 O-G)。

## 1. 現状 (v2 / PoC) と継承可否

| 観点 | v2 の現状 | PoC の現状 | v3 で継承できるか |
|---|---|---|---|
| ログ形式 | zap の JSON (`hassan-v2-backend/logger/logger.go:10` が常に `zap.NewProduction()`) | 標準出力への ad-hoc ログ | **形式は継承可** (zap JSON) |
| リクエストログ | **prod では出ない** — `RequestLoggerMiddleware` は `AppEnv` が local/dev のときだけ登録 (`hassan-v2-backend/router/router.go:50`〜`:51`) | なし | **継承不可**。全環境で出す |
| 相関 ID | ミドルウェア共通ではなく、個別のエラーログで手動付与 | なし | **継承不可**。共通化する |
| ログの集約先 | CloudWatch Logs (`awslogs` ドライバ / ロググループ `/ecs/hassan-v2-api`。`hassan-v2-backend/stacks/prod/ecs-task-def.json`) | なし (ローカル標準出力) | **継承可** |
| LLM の利用量 | **OpenAI 実装のみが `TokenUsage` を詰める** (`hassan-v2-backend/llm/openai/service.go:178` が唯一の書き込み)。**主系モデルは Gemini** なので主要経路で取得できない。読み出しは 1 箇所、**DB 保存なし**、単価はハードコード | 発散経路のみ (`claude_managed_agents/internal/agent/diverge/result_helpers.go` の `EstimateUSD`) | **継承不可**。全プロバイダ対応で作る |
| `stop_reason` | **公開型に存在しない** (`hassan-v2-backend/llm/types.go`) | 一部の経路で検出 | **継承不可**。抽象に必須フィールドとして持たせる |
| メトリクス | 未確認 (CloudWatch の標準メトリクスのみと推測) | なし | 新規設計 |
| 監査ログ | `activity_logs` / `event_logs` テーブルが**稼働中** ([v2-auth-tenancy.md](../analysis/v2-auth-tenancy.md)) | なし | **継承可** (方式を踏襲) |
| アラート | 未調査 | なし | 新規設計 |

**要点**: 継承できるのは「zap JSON」「CloudWatch Logs への集約」「監査ログの方式」の 3 つだけで、
**リクエストログ・相関 ID・LLM 計測・stop_reason・アラートはすべて v3 で新規に作る**。

## 2. 設計判断

| # | 論点 | 採用案 | 却下案と理由 |
|---|---|---|---|
| O-A | ログ形式と集約先 | **zap の JSON を全環境で出力し、`awslogs` で CloudWatch Logs へ集約**。ログレベルは環境変数で切替 (prod=info, dev=debug) | (a) prod で抑制 (v2 現状): 本番の障害調査ができない。**v2 の現状を継承しない最大の理由** (b) 外部 SaaS (Datadog 等) を初期から導入: 初期スコープとコストが膨らむ。CloudWatch で不足が出た時点で再検討 |
| O-B | 相関 ID | **`request_id` を Controller のミドルウェアで生成** (`X-Request-Id` ヘッダがあれば尊重)。`context.Context` に載せて全層へ伝播し、**すべてのログ行に必須フィールドとして出す** | (a) 個別のログで手動付与 (v2 現状): 付け忘れが構造的に発生し、障害時に追跡が途切れる (b) ログのみに埋め、context に載せない: Service / Repository のログから消える |
| O-C | LLM 計測の位置 | **計測点と記録点を分ける** (§3 の図): **① 1 呼び出しの計測値 (`CallMeta`) の生成 = `gateway/<プロバイダ>` の単一関門** / **② ターン単位の集計 (ツール呼び出し回数・累積トークン・安全弁の打ち切り判定) = `service/conversation.Runner`** / **③ 明細の永続化とメトリクス送出 = `usecase/<domain>`**。層の定義は [architecture.md](architecture.md) §3.3 / §3.8.3 が SSOT。**機能実装側に計測コードを書かせない** — 全 LLM 呼び出し (Agent 経路・直接 API 経路・移植ドメインの経路) が gateway を通るため、経路を追加しても計測が漏れない。**永続化を gateway に置かない理由**: 依存規則 **L-4 (`gateway` → `repository` の import 禁止。[architecture.md](architecture.md) §3.5.1)** により gateway は DB を触れないため、gateway が戻り値で返す `CallMeta` を呼び出し元の UseCase が記録用 Repository へ渡す | (a) 各 UseCase で計測を実装 (PoC 方式): 経路追加のたびに計測漏れが起きる (発散経路だけ計測されている現状がその結果) (b) **別プロセスの LLM プロキシを挟む**: 運用対象が増え、ローカル開発が複雑になる。**本項の `gateway/` は同一プロセス内のパッケージ層であり、この却下案 (別プロセスのプロキシ) とは別物である** — 却下済み案の再提案ではない (c) **Service 層の単一ラッパ 1 箇所 (旧 O-C)**: 外部 API 呼び出しが `gateway/` に移ったため ([architecture.md](architecture.md) の D-A''')、Service に置くと直接 API 経路が別の関門になり計測点が 2 つに割れる |
| O-D | 利用量の永続化 | **append-only の DB テーブル + CloudWatch メトリクス**の二段構え。DB は明細 (監査・請求根拠・分析)、メトリクスは集計と即時アラート。**実施時期は 2 つに分かれる** (§6.1 の表が SSOT): **明細の永続化 = v3 第 1 リリース前** (明細は append-only なので取り損なった期間を後から遡って補完できない — 本番で課金が発生し始めた時点で明細が無いと請求根拠が永久に失われる) / **メトリクス送出と集計 = v2 併用期間中** (既存の明細から後付けで再計算できる) | (a) ログのみ (v2 現状): アカウント単位の集計にログ検索が必要で、遅く高価 (b) DB のみ: 即時アラートに向かない (c) メトリクスのみ: 明細が残らず、事後の内訳分析ができない (d) 明細も併用期間中に先送り: **append-only のため先送りした期間の明細は永久に得られない** |
| O-E | コスト制御 | **課金上限による拒否は設けない** (ユーザー決定 C-12)。可視化 + しきい値アラートで運用する。**別途「暴走の安全弁」を機能要件として実装する** (§4.4) | (a) アカウント月次上限で拒否: ユーザー決定により却下 (b) 安全弁も設けない: **却下** — 会話フローは LLM がツールを繰り返す構造で、打ち切りが無いと停止条件が LLM 任せになる。これはコスト制限ではなく無限ループ対策 |
| O-F | 失敗の可観測性 | **LLM 起因の失敗を 5 分類し、warn ログ + メトリクスの両方に出す** (§4.3)。握り潰し禁止。**実施時期 = 初期実装 (第 1 増分)** (§6.1 の ⑧。§6.1 の表が実施時期の SSOT) — **⑦ の「利用量・コスト系メトリクスの先送り」の対象ではない** | (a) エラーログのみ: 発生率の推移が見えず、劣化に気付けない (b) メトリクスのみ: 個別事象の原因調査ができない (c) メトリクスを利用量系と同じく v2 併用期間中へ先送り: **失敗は明細から後付けで再計算できない** — 発生した事実が残らないと遡れない |
| O-G | 分散トレース | **初期増分では導入しない** (先送り)。`request_id` によるログ相関で代替する。**再検討の契機**: サービスが 2 つ以上に分割されたとき / 外部呼び出しのレイテンシ内訳が問題になったとき | (a) OpenTelemetry / X-Ray を初期から導入: 単一サービス構成では相関 ID で足り、計装コストが先に立つ。**先送りであって「不要」ではない** ことを明記する |
| O-H | 単価テーブル | **モデル単価は設定として外部化**する。**トークン単価の行型に加えて「1 リクエストあたりの単価」の行型を持つ** (外部検索 API 用 = §4.2 の `external_search` の注 / **画像生成 1 枚あたりも同じ行型で表す** = §4.2.2) (コード内ハードコードにしない。置き場は `config`。[architecture.md](architecture.md) §3.9②)。更新日を持たせ、**古い単価で計算し続けていることが分かる**ようにする。**実施時期 = v2 併用期間中** (§6.1 の表): 単価テーブルはコスト算出の入力であり、**明細に 4 種のトークン数が残っていれば後から遡って再計算できる**。逆に明細のカラムが欠けていると再計算できないため、**O-D の明細を先に入れる** | (a) ハードコード (v2 現状): 単価改定・モデル追加のたびにデプロイが必要で、実態と乖離しても気付けない (b) 単価テーブルを明細より先に入れる: 再計算可能な側を先に作ることになり、**後から遡れない明細の実装が遅れる** |

## 3. 構成

```
  controller/ (gin)
    │  ① request_id 生成 (X-Request-Id 尊重) → context へ
    │  ② リクエストログ (全環境)
    ▼
  usecase/<domain>  ── ③ 所有者スコープ (account_id / contract_id) を context へ
    │
    │  (Agent 経路)          ┌──────────────────────────────────────────────┐
    ├───────────────────────▶│ service/conversation.Runner                   │
    │                        │  ⑤ ターン単位の集計 (④ を N 回分束ねる)      │
    │                        │     tool 呼び出し回数 / 累積トークン /        │
    │                        │     安全弁の打ち切り判定 (§4.4)              │
    │                        └───────────────┬──────────────────────────────┘
    │  (直接 API 経路)                       │
    │  ┌─────────────────────────────────────┘
    │  │
    ▼  ▼
  ┌──────────────────────────────────────────────────────────────────────────┐
  │ gateway/<プロバイダ>            ★ 計測点 (1 箇所)                        │
  │  ④ 1 呼び出しごとに CallMeta を戻り値で返す                              │
  │     provider / model / usage 4 カウンタ (in・out・cache_read・cache_write)│
  │     / stop_reason / duration_ms                                          │
  │  ※ L-4 により repository を import できない = ここでは永続化しない        │
  └───────────────────────────────┬──────────────────────────────────────────┘
                                  │ CallMeta を戻り値で受け取る
                                  ▼
  ┌──────────────────────────────────────────────────────────────────────────┐
  │ usecase/<domain>                ★ 記録点 (1 箇所)                        │
  │  ⑥ 明細を repository へ (append-only)                                    │
  │  ⑦ 利用量・コスト系の集計メトリクスを送出 (CloudWatch)                   │
  │     ※ 失敗系の warn メトリクス (§4.3 / §4.5) は別枠 = ⑧ (初期実装)       │
  └───────────────────────────────┬──────────────────────────────────────────┘
                                  ▼
                    ┌───────────────┬────────────────────┐
                    │ 明細テーブル   │ CloudWatch         │
                    │ (append-only) │ メトリクス          │
                    └───────────────┴────────────────────┘

  すべてのログ ──(awslogs)──▶ CloudWatch Logs ──▶ メトリクスフィルタ / アラーム ──▶ 通知
```

**計測は「計測点 1 つ (gateway) + 記録点 1 つ (usecase)」の 2 段構成**である (O-C)。
分かれている理由と、機能追加時に計測コードを書かせない仕組みは次のとおり:

- **④ 計測点を `gateway/` に置く**: **全 LLM 呼び出しが gateway を通る**ため、経路を追加しても計測が漏れない。
  Agent 経路・直接 API 経路に加え、**v2 から移植するドメインの LLM 呼び出しも gateway 経由を必須にする**
  (ユーザー決定 2026-07-30。[questions-layering.md](../../aidlc-docs/inception/productionization/questions-layering.md) Q-L11=A-1)。
  これが O-2 (全経路の計測) を守る唯一の現実的な方法である
- **⑥⑦ 記録点を `usecase/` に置く**: 依存規則 **L-4 (`gateway` → `repository` の import 禁止。
  [architecture.md](architecture.md) §3.5.1)** により gateway は DB を触れない。
  gateway は `CallMeta` を戻り値で返すだけで、**永続化とメトリクス送出は呼び出し元の UseCase が行う**
- **⑤ ターン集計を `service/conversation.Runner` に置く**: 停止条件と安全弁は業務ルールであり、
  プロバイダごとの実装 (gateway) に置くと重複する ([architecture.md](architecture.md) の D-D)
- **LLM 計測の実施時期は 3 段に分かれる** (§6.1 の表が SSOT): **④ と ⑤ は初期実装** /
  **⑥ は v3 第 1 リリース前** / **⑦ (利用量・コスト系の集計メトリクス) とコスト算出・アラートは v2 併用期間中**。
  **これとは別に、失敗系の warn メトリクスとメトリクス基盤そのもの (§6.1 の ⑧) は初期実装**である —
  本図には現れない (出所は §4.3 / §4.4.1 / §4.5)。**⑦ と ⑧ は別物**で、
  本図の ⑦ は「利用量明細から集計するためのメトリクス」だけを指す

## 4. 仕様

### 4.1 ログの必須フィールド (O-1 / AC-2.4)

すべてのログ行が持つ:

| フィールド | 内容 | 備考 |
|---|---|---|
| `ts` / `level` / `msg` | zap 標準 | — |
| `request_id` | リクエスト単位の ID | ミドルウェアで生成。`X-Request-Id` があれば尊重 |
| `account_id` | 認証済みアカウント | 未認証リクエストでは空 |
| `contract_id` | 契約 (テナント) | テナント軸の集計に使う |
| `route` / `method` / `status` / `duration_ms` | リクエストログのみ | 全環境で出す |
| `session_id` | 会話セッション | 会話系のログのみ |

**禁止**: プロンプト本文・LLM の応答本文・アセットの中身・個人情報をログに出さない。
デバッグに必要な場合は**文字数と先頭 N 文字のハッシュ**に留める (dev 環境のみ本文を許可するかは §8 の残課題)。

### 4.2 LLM 呼び出しレコード (O-2 / AC-2.1)

Agent 経路・直接 API 経路の**両方**で、1 回の LLM 呼び出しごとに記録する:

| フィールド | 内容 |
|---|---|
| `request_id` / `account_id` / `contract_id` / `session_id` | 4.1 と同じ相関キー |
| `feature` | 機能識別子 (例: `conversation.turn` / `plan.generate` / `asset.extract`)。**Go の const 群として `entity/` の 1 ファイルに列挙し、リテラルの直書きを禁止する** — 追加は同一 PR でこの const 群に足す。**この const 群が [testing.md](testing.md) §10 の存在検査 #5 (LLM 経路のテスト存在検査) の対象集合になる**ため、定義が無いと検査が 0 件を検査して緑になる (同 §13.3)。値は `<ドメイン>.<操作>` 形式 |
| **`theme_id`** | **テーマ単位のコスト集計に必要** (NULL 可)。**NULL になるのはテーマに紐づかない経路だけ** — アセット抽出・ナレッジ検索・通常モードのナレッジ会話。**会話経路は最初の呼び出しから必ず埋まる** (CV-Q8=A でテーマ必須になり `conversation_sessions.theme_id` が NOT NULL になったため。2026-08-01 に「テーマが確定する前の呼び出しがある」を撤回した)。列定義と FK を張らない判断は [data-model.md](data-model.md) §4.10 (2026-07-30 追加) |
| `route_kind` | `managed_agent` / `direct_api` / **`external_search`** / **`image_generation`** (2026-08-02 追加。§4.2.2) (Exa 等の外部検索 API。Anthropic 呼び出しではないが**課金を伴うため計測対象に含める** — [llm-migration.md](llm-migration.md) §4 の P-12 / C-5)。**値の追加はこの表を SSOT として行う** |
| `provider` / `model` | 実際に使われたプロバイダとモデル |
| `input_tokens` / `output_tokens` | **全 LLM プロバイダで取得する** (v2 は OpenAI のみ — 継承不可)。**`route_kind=external_search` は対象外** (トークン課金ではなくリクエスト課金のため。下記の注) |
| `cache_read_input_tokens` / `cache_creation_input_tokens` | **プロンプトキャッシュのトークン。単価が通常入力と異なるため、これが無いとコストが構造的に誤る**。Managed Agents は既に 4 カウンタを返している (`claude_managed_agents/internal/stream/processor.go:65`〜`:68` が `InputTokens` / `OutputTokens` / `CacheReadInputTokens` / `CacheCreationInputTokens` を受け取っている)。**明細は append-only なので、取り損なった分は後から復元できない** |
| `duration_ms` | 呼び出し時間 |
| `stop_reason` | **抽象に必須フィールドとして持たせる** (v2 に無い)。**`route_kind=external_search` では NULL** (検索 API に停止理由の概念が無い) |
| `tool_calls` | そのターンでのツール呼び出し回数 (Agent 経路) |
| `estimated_cost` / `price_table_version` | 単価テーブル (O-H) から算出。**どの版で計算したか**を残す |
| `outcome` | `ok` / `truncated` / `parse_error` / `timeout` / `tool_error` / `canceled` |

**`route_kind=external_search` (Exa 等の外部検索) の扱い** (2026-07-30 に追加。
[llm-migration.md](llm-migration.md) §4 の P-12 / C-5 が対象):

- **同じ明細テーブルに載せる**。理由: コストは「LLM + 検索」の合計で見なければ AL-4 (日次コストの急増) が
  総額を捉えられず、検索の回数だけが増えた場合に検知できない
- **トークン系 4 カウンタと `stop_reason` は NULL 可**とする (トークン課金ではないため)。
  **この 5 フィールドについて NULL を許すのは `external_search` と `image_generation` の 2 つの `route_kind` のみ** (後者は 2026-08-02 追加。§4.2.2) — LLM 経路で NULL は計測漏れであり、
  区別できる形にする。
  **相関キー (`session_id` / `theme_id`) はこの規則の対象外** — どの `route_kind` でも
  「値が無い経路が正当に存在する」ため NULL は計測漏れを意味せず、**計測漏れの CHECK にも掛けない**
  ([data-model.md](data-model.md) §4.10 と同じ書き分け。R-DM-8 の後半への対応)
- **単価テーブル (O-H) に「1 リクエストあたりの単価」の行型を持たせる** — トークン単価しか持たない設計だと
  `estimated_cost` が 0 になり、検索のコストが総額から丸ごと落ちる
- `provider` / `model` は検索 API の識別子を入れる (例: `provider=exa` / `model=search` · `deep`)

- **明細は append-only テーブルに保存する** (更新・削除しない)。
  **テーブル名は `llm_call_records`・スキーマは [data-model.md](data-model.md) §4.10 が SSOT**
  (2026-07-30 に確定)。本書は**フィールド要件**の SSOT であり、両者は対で維持する
  (フィールドを足したら同節のカラムも足す)
- 集計用に `feature` × `model` × 日付の粒度で CloudWatch メトリクスも送出する。
  **これは利用量・コスト系の集計メトリクスなので実施時期は v2 併用期間中** (§6.1 の ⑦)。
  明細 (上記) が残っていれば後から再計算できるため先送りできる —
  **失敗系の warn メトリクス (§4.3) は同じ扱いにしない** (§6.1 の ⑧)
- **単価テーブル (O-H) は 4 種のトークン単価を別々に持つ** (入力 / 出力 / キャッシュ書き込み / キャッシュ読み出し)。
  1 種の単価で概算すると、キャッシュを多用する Agent 経路で誤差が積み上がる

### 4.3 失敗の分類と検知 (O-4 / AC-2.3)

**5 分類すべてを warn ログ + メトリクスに出す**。握り潰し禁止。
**実施時期 = 初期実装 (第 1 増分)** — 本節のメトリクスは §6.1 の **⑧** に属し、
**§6.1 の ⑦ (利用量・コスト系メトリクスの先送り) の対象ではない**。
理由: 失敗は**発生した事実そのもの**が観測対象なので、利用量明細と違って**後から遡って再計算できない**。
実施時期の SSOT は §6.1 の表。

| # | 失敗 | 検知方法 | 由来 |
|---|---|---|---|
| F-1 | 出力の切り詰め | `stop_reason == max_tokens` | BE-6。**現行 v2 の抽象では検知不可能** (`stop_reason` が無い) |
| F-2 | JSON パース失敗 | 構造化出力のパースエラー | BE-6 (`claude_managed_agents/cmd/devui/idea_evaluate.go` で実際に発生) |
| F-3 | ツール引数の不整合 | LLM が渡した引数が schema と合わない / 必須欠落 | BE-8。**schema・handler・prompt の 3 者不一致の実害がここに現れる** |
| F-4 | タイムアウト / 打ち切り | 安全弁 (§4.4) の発火、context キャンセル | PoC はタイムアウト設定が無く、打ち切りはクライアント切断のみ |
| F-5 | SSE の異常終了 | 送出中の切断・書き込み失敗 | O-5。PoC は keep-alive のみ |
| F-6 | **認証エンドポイントのレート制限の発動** | 429 の応答件数 (キー: IP / エンドポイント / メールアドレス) | [auth.md](auth.md) §6.11-3 でアプリ層のレート制限を設ける決定。**発動そのものが攻撃の兆候**なので、失敗としてではなく**セキュリティイベント**として記録する |

**F-1 と F-3 は「静かに壊れる」種類の失敗**である (機能が動いているように見えて内容が欠ける)。
メトリクス化してしきい値アラートを張らないと、誰も気付かないまま品質が劣化する。
**この 2 つが「メトリクス基盤を第 1 増分に入れる」ことの根拠**である (§6.1 の ⑧) —
基盤を先送りすると、初回リリース期間の切り詰めと引数不整合が**記録にも残らないまま過ぎる**。
**F-6 は他と性質が異なる** (アプリの不具合ではなく外部からの試行) が、
握り潰すと総当たり・パスワードスプレーの検知手段が無くなるため同じ経路で観測する。

### 4.4 暴走の安全弁 (O-3 / AC-2.2)

**課金上限は設けない** (C-12) が、無限ループ対策の打ち切りは**機能要件**として実装する。
1 ターン (1 ユーザー発話に対する Agent 実行) 単位で:

| パラメータ | 初期値 (要調整) | 発火時の挙動 |
|---|---|---|
| ツール呼び出し回数の上限 | **20 回 / ターン** | ループを打ち切り、`outcome=tool_limit` で記録。ユーザーには「処理が長くなったため中断した」旨を SSE で通知 |
| 累積出力トークンの上限 | **モデル上限に依存 (設定値)** | 同上 (`outcome=token_limit`) |
| 1 ターンの実行時間上限 | **5 分** | 同上 (`outcome=timeout`) |
| SSE keep-alive 間隔 | **15 秒** | 送出継続 (打ち切りではない) |

- **初期値は根拠のある推定ではなく暫定値**。PoC はタイムアウト・回数上限を持たないため実測がない。
  **本番の実データで調整する前提**で、**設定値として外部化**する (再デプロイなしで変えられること)
- 打ち切りは**エラーではなく正常な終了**として扱う (ユーザーに理由を伝える。§4.3 の F-4 で記録)

#### 4.4.1 SSE 接続数のメトリクス (O-5。デプロイ判断の入力)

**rolling update で SSE は必ず切れる**前提のため (`design_memo.md` の決定ログ)、
**「今どれだけの会話が進行中か」を見てからリリースする**運用を成立させる計測項目を持つ。

| 項目 | 内容 |
|---|---|
| 名前 | `sse.active_connections` |
| 種別 / 単位 | ゲージ / 接続数 |
| 次元 | 環境・ECS タスク単位 (タスク間の偏りを見るため。合計はダッシュボード側で集約) |
| 出力元 | アプリから **EMF (CloudWatch Embedded Metric Format)** で出力。ログ経由のメトリクスフィルタは使わない (接続数はログ行ではなく現在値のため) |
| 出力間隔 | **30 秒** |

- **用途**: prod リリース前の確認 ([operations.md](operations.md) §6.3) と、リリース中の切断影響の把握
- **これが無いと** operations の「起動前に進行中セッション数を確認する」手順が実行不能になり、
  「利用の少ない時間帯に出す」という運用に退行する
- **実施時期 = 初期実装 (第 1 増分)** (§6.1 の ⑧)。**デプロイ判断の入力**なので、
  初回リリースの時点で必要になる — **§6.1 の ⑦ (利用量・コスト系メトリクスの先送り) の対象ではない**。
  本項が EMF による**現在値のゲージ**であり、利用量明細からの後付け計算が原理的にできないことも理由である

### 4.5 監査ログ (O-6 / AC-2.5)

- **v2 の `activity_logs` / `event_logs` の方式を踏襲する** (稼働中の仕組み)
- 記録対象: 生成 (アイデア / 企画書 / アセット抽出)・削除・共有設定の変更・**LLM を伴う操作の実行**・
  **アカウントの手動ロック / 解除** ([auth.md](auth.md) §6.9 で新設する API。
  トークン漏洩時の遮断手段であり、**誰が誰に対して実行したか**が追えないと不正利用の調査ができない)・
  **認証系の事象** (サインイン成否 / MFA 検証成否 / MFA リセット。**v2 に既存の 6 種を落とさない** —
  値域は §4.5.1、actor が確定しない場合の扱いは §4.5.2)
- 記録項目: 誰が (**actor**) / いつ / 何を (対象 ID と種別) / どの操作 / `request_id`
  (ロック / 解除では**対象アカウントの `account_id` を「何を」として記録**する)
- **actor は「種別 + ID」で持つ** (`{actor_type: "account" | "admin_account", actor_id: uuid}`) —
  [auth.md](auth.md) §6.2 の例外により**社内管理者によるロック解除**が入り、
  その実行者は `admin_accounts.id` を持ち `account_id` を持たない。
  **`account_id` 単独の項目では社内管理者の操作を記録できない** (O-6 の後退になる)。
  同 §10.2 R-5' が本節への申し送り
- **LLM 利用量の明細 (§4.2) とは別物**として持つ (目的が違う: 監査 vs コスト分析)。
  ただし `request_id` で相互に突き合わせられること
- **書き込み失敗時の挙動**: 別トランザクションの best-effort とし、**失敗を WARN ログ + メトリクスに出す**
  (`_ =` による無言破棄を禁止する)。判断と v2 の実測 (6 ファイル 17 箇所) は
  [architecture.md](architecture.md) §3.9③ が SSOT (ユーザー決定 Q-L2=B)。
  **この失敗メトリクスの実施時期 = 初期実装 (第 1 増分)** (§6.1 の ⑧) —
  ユーザー決定が「メトリクス必須」を含むため、**§6.1 の ⑦ の先送り対象にはできない**

#### 4.5.2 actor / contract が確定しない認証イベントの記録 (2026-07-31 追加 — R-AA-7④ / AA-D-21)

- **アカウントが解決できた失敗は両列を埋める** — NULL になるのは未登録メール・存在しない管理者アカウントへの試行のみ
- **メールアドレスを平文で保存しない**。**`detail.email_hash` = HMAC-SHA256 (サーバ側 pepper
  `AUDIT_EMAIL_HMAC_KEY`)** に入れる。同一アドレスへの試行を突き合わせられ、かつ辞書攻撃で復元されない。

  **素の SHA-256 も採らない** (既知アドレスの総当たりで復元できる)。pepper は [operations.md](operations.md) §4 の
  シークレット棚卸しの対象に含める
- **これが無いと v2 でできていた `signin_failed` / `mfa_verify_failed` が v3 で落ち、O-6 が v2 より後退する**。
  加えて [auth.md](auth.md) §6.11-3 が名指しで防ぐと宣言した**パスワードスプレー (多数アカウントに 1 回ずつ) の
  検知が「失敗の分布」でしか行えず**、保持期間の短いログでは月次の突き合わせができない

### 4.6 アラート (O-7)

> **重大度分類 (critical / warning) と環境差 (dev でどのアラートを通知するか)・通知経路 (SNS トピック構成) は
> [operations.md](operations.md) §7.5 が SSOT**。本節は**監視対象としきい値**の SSOT であり、
> 両者を混ぜない (同じ事実を 2 箇所に置かない)。

**実施時期の判断基準**: **そのアラートが依存するメトリクスが §6.1 の ⑦ / ⑧ のどちらの段にあるか**で決める。
⑧ (失敗系メトリクスとメトリクス基盤) に依存するものは**初期実装**、
⑦ (利用量・コスト系の集計メトリクス) に依存するものは **v2 併用期間中**。

| # | 監視対象 | しきい値 (初期値・要調整) | 実施時期 (§6.1) | 依存するメトリクス | 通知先 |
|---|---|---|---|---|---|

**AL-4 の先送りに対する代替** (ユーザー決定 2026-07-30): AL-4 が併用期間中まで無いと
**初回リリースからコスト急増の即時検知が無い**状態になる (⑦ の先送り理由「明細から後付けで再計算できる」が
担保するのは**遡及分析**だけで、**気付き**は担保しない)。したがって **AWS Budgets によるアカウント単位の
予算アラートを初回リリースで有効化する** — アプリのメトリクスに依存しないため ⑦ の成果物を待たずに使える。
**粒度は粗く** (テーマ別・機能別の内訳は出ない) AL-4 の代替にはならないが、**「気付かない」状態は解消する**。
**通知経路と重大度の設計は `operations.md` §7.5 が SSOT** — 本項はしきい値と有効化時期のみを定める。

**⑦ に属するのは AL-4 のみ**で、残る 6 件は初期実装である。**この配分は「アラート基盤を第 2 増分にはできない」
ことを意味する** — 初回リリース時点で AL-1 / AL-2 / AL-3 / AL-5 / AL-6 / AL-7 が動いていなければ、
O-4 (失敗の可観測性) と O-7 (アラート) は「事後調査専用」に退行する (§6.1 の ⑧ の趣旨)。

**AL-6 の位置づけ (§6.1 の分類から一意に決まらないため理由を添えて寄せた)**: AL-6 だけは
**アプリが出すメトリクスに依存しない** (ECS のタスク停止イベントと ALB のヘルスチェック結果は
CloudWatch の標準メトリクス)。したがって ⑦ / ⑧ のどちらの成果物も前提にしないが、
**⑦ (併用期間中) へ回す理由が無く、インフラ構築の時点 (dev 先行構築。[architecture.md](architecture.md) §5 の D-7 の①) から
有効にできる**ため、**初期実装側に寄せる**。

**アラートの無い可観測性は事後調査専用**である。上表は「誰が受けるか」まで決めて初めて機能する。
通知先の実体 (Slack チャンネル / メール) は運用設計で確定する。

## 6. 移行と運用

### 6.1 計測の実施時期 (LLM 計測の 3 段 + 失敗系メトリクスの位置づけ)

**「計測は第 1 増分から入れる」の対象は §3 の ④ (`CallMeta` の生成) と ⑤ (安全弁を含むターン集計) である**
— 後付けは全経路の改修になるため (§0)。**LLM 計測の記録・集計・コスト算出は同時ではなく 3 段に分かれる**
(**④⑤ / ⑥ / ⑦ の 3 段**。決定の一次ソース:
[questions-layering.md](../../aidlc-docs/inception/productionization/questions-layering.md) Q-L6 / Q-L10=B。
ユーザー決定 2026-07-29 — **この 3 段の線引きは変更しない**)。
**⑧ は 3 段の一部ではなく、「失敗系メトリクスがどの段にも属さない」ことを明示するための行**である
(本書を単独で読んだときに「メトリクス基盤ごと先送り」と誤読されるのを防ぐ)。
**本表が実施時期の SSOT** で、O-D / O-F / O-H / §3 の図 / §4.2 / §4.3 / §4.4.1 / §4.5 / §5 / §7 はここを参照する。

|---|---|---|
| **④ gateway の戻り型が usage 4 カウンタ (`input` / `output` / `cache_read_input` / `cache_creation_input`) と `stop_reason` を載せられること** / **§4.4 の安全弁 (⑤)** | **初期実装 (第 1 増分)** | **記録先は後から 1 箇所に足せるが、戻り型が usage を載せられない状態は後付けできない** (利用側の IF が全経路で壊れる)。v2 は OpenAI 実装のみ usage を詰め `stop_reason` を公開型に持たないため、計測が原理的に不可能だった ([v2-llm-inventory.md](../analysis/v2-llm-inventory.md))。安全弁は無限ループ対策であり、無いと停止条件が LLM 任せになる (O-E) |

後者は⑥⑦ (利用量の記録と集計) を指す。

### 6.2 運用に含めること

## 7. 実装リポへの引き渡し

- **計測値 (`CallMeta`) の生成は `gateway/<プロバイダ>` に実装する** (1 箇所)。
  Controller / UseCase / Service に計測コードを書かない。
  **ターン単位の集計は `service/conversation.Runner`**、**明細の永続化とメトリクス送出は `usecase/<domain>`**
  (**L-4 により gateway は `repository` を import できない**ため)。
  層の定義は [architecture.md](architecture.md) §3.3 (責務表) / §3.8.3 (計測点の表) が SSOT。
  **実施時期は層と別軸**なので混同しないこと (§6.1 の表が SSOT): **`CallMeta` の生成と安全弁は初期実装** /
  **明細の永続化は v3 第 1 リリース前** / **利用量・コスト系の集計メトリクスは v2 併用期間中** /
  **失敗系の warn メトリクスと SSE 接続数メトリクスは初期実装**
- **メトリクスの出力手段 (基盤) は第 1 増分で用意する** — 失敗系 (§4.3) ・監査ログ失敗 (§4.5) ・
  SSE 接続数 (§4.4.1) が初期実装だからである (§6.1 の ⑧)。
  **先送りされるのは「利用量・コストを集計するためのメトリクス」だけ**で、基盤ごと先送りにはしない
- **v2 から移植するドメイン (ナレッジ等) の LLM 呼び出しも `gateway/` 経由にする** (Q-L11=A-1。
  ユーザー決定 2026-07-30)。**層構成は v2 の 3 層のまま据え置き、変えるのは LLM を呼ぶ箇所だけ** —
  移植時の受入条件は「gateway を通らない LLM 呼び出しを残さないこと」
  ([architecture.md](architecture.md) §3.5.2)
- LLM 抽象は **usage / stop_reason / 未知モデルのエラー化** を満たすこと (D-B'')
- ミドルウェア (`request_id` 生成・リクエストログ) は Controller 層。**全環境で登録する**
  (v2 のように環境で登録を分けない)
- 参照すべき実装:
  - ログ基盤: `hassan-v2-backend/logger/logger.go` (形式は踏襲。**登録条件は踏襲しない**)
  - usage 取得の例: `hassan-v2-backend/llm/openai/service.go:178` (**他プロバイダにも同等の実装が必要**)
  - コスト推定の例: `claude_managed_agents/internal/agent/diverge/result_helpers.go` の `EstimateUSD`
    (単価ハードコードは踏襲しない)
  - SSE の取りこぼし対策: `claude_managed_agents/cmd/devui/conversation_stream.go` (BE-7 の修正済み実装)
