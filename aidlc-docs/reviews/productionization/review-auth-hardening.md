## 2. 重大 (Must Fix)

### 重大 1. `docs/design/auth.md:569-595` (§6.9) — 採用した失効経路「アカウントロック」を**起こす手段が v2 に存在せず、v3 でも設計されていない**。その前提で `jti` ブラックリストを却下している

**何が問題か**: §6.9 は「毎リクエスト DB 確認による失効経路を v3 も維持する」を採用し、
却下理由に「**アカウントロックによる一括失効で実用上の要件 (漏洩時の遮断) は満たせる**」(`:592-595`) と書く。
しかし v2 には**運用者がアカウントをロックする経路が無い**。

**根拠 (一次ソース。照合 #19)**:

| 事実 | 出典 |
|---|---|
| `last_locked_at` を設定する SQL は `UpdateFailedSignInAttempts` **1 本だけ**で、サインイン失敗の副作用として立つ | `hassan-v2-backend/db/queries/account.sql:56-64` |
| router 内の lock 関連ルートは**解除 2 本のみ** (`POST /accounts/unlock` / `POST /admin/accounts/unlock`) | `hassan-v2-backend/router/router.go:82`, `:211` |
| 手動ロックの route / handler / query | **0 件** (`Lock` / `nlock` 検索) |

したがって「漏洩を疑ったら失効させる」を実行する手段は、**攻撃者の代わりに N 回わざとサインインを失敗させる**か
**DB を直接更新する**しかない。§6.9 案 (a) は「ロック操作の実行経路 (管理画面か DB 直か) を確認する」(`:585`) と
書いているが、これは**採用案の中に未実施の調査を残している**状態であり、
「どちらでもよい」ではなく「**どちらも無いので作る必要がある**」が正解である (DR-5)。

**なぜ本番で問題になるか**: 実装者は §6.9 を読んで「失効は既存の仕組みで足りる」と理解し、
無効化 API を作らない。結果、v3 は**トークン漏洩時に最大 7 日間なにもできない**システムとして本番に出る。
`jti` ブラックリストの却下理由が成立しないため、代替手段も残っていない。

**どう直すか**:

1. §6.9 の採用に **「アカウント無効化 (= 発行済みトークンの一括失効) 操作を v3 の設計対象として新設する」**を加える。
   最低限決めること: **誰が呼べるか** (契約管理者 / HASSAN 管理者 / 本人)、**API 形状**、
   **監査ログに残すか** (O-6)、**解除経路と解除権限** (重大 2 と一体)。
2. `jti` ブラックリストの却下理由を「(1) の無効化 API で漏洩時の遮断要件を満たせるため」に書き換える
   (現在の理由は v2 に存在する機構を前提にしているので誤り)。
3. これは Q-A6 (有効期間 7 日据え置き / 短縮) の**どちらを選んでも必要**なので、
   **Q-A6 の回答待ちにしない** (現状は §6.9 全体が Q-A6 待ちの体裁になっている)。

### 重大 2. `docs/design/auth.md:629-632` (§6.11-2) — 踏襲すると決めたロック機構の**解除 API がテナント越境**しており (v2 の新規欠陥)、「総当たりは防げている」という事実認定が過大。解除側の設計が欠落している (BE-10)

**何が問題か**: §6.11-2 は「アカウント単位のロックは v2 の機構を踏襲する ... **これにより単一アカウントへの
総当たりは防げている**」と断定する。しかし v2 の**ロック解除**には所有権検証が無い。

**根拠 (一次ソース。照合 #20)**:

| 層 | 状態 | 出典 |
|---|---|---|
| router | 一般ユーザー認証のみ | `hassan-v2-backend/router/router.go:82` (`AuthRequiredMiddleware(auth.AuthRoleUser)`) |
| Controller | 契約内管理者かの 403 判定**だけ** | `hassan-v2-backend/controller/account.go:896-900` (`authAccount.AuthRoleID.IsAdmin()`) |
| UseCase | 受け取った email を素通し。**契約一致の検証なし** | `hassan-v2-backend/usecase/account/delete_last_locked_at.go:29-33` |
| Repository / SQL | email で `last_locked_at = NULL` + `failed_sign_in_attempts = 0` | `hassan-v2-backend/repository/account.go:258-259` → `hassan-v2-backend/db/queries/account.sql:66-70` |

→ **任意の契約の管理者が、他契約の任意アカウントのロックを email 指定で解除できる**。
これは `08-production-gates.md` A-4 が名指しした形 (「所有者 ID をパラメータで受け取る API で、
その所有者が呼び出し元と同じ契約に属することを検証しない」) であり、
既存レビューの F-15 (`theme` 一覧) と**同型の未記載の欠陥**である。

**なぜ本番で問題になるか**:

- しきい値ロックは「別契約に管理者アカウントを 1 つ持つ攻撃者」に無効化され得るため、
  §6.11-2 の「防げている」を根拠に **§6.11-3 の追加制限 (パスワードスプレー対策) の優先度が下がる**。
- より重いのは **重大 1 と組み合わせたとき**: v3 が「ロック = 失効」を採るなら、
  **解除 = 失効の取り消し**である。解除の権限設計を持たない失効機構は失効機構ではない。
  §6.11 はロック (書く側) だけを踏襲対象として書き、解除 (戻す側) に一言も触れていない — **BE-10** の型。

**どう直すか**:

1. §5 に **§5-10 として新規欠陥を追記**する (出典は上表)。§9 Q-A3 の「v2 側で修正するか」の対象リストに加える
   (§5-1 / §5-4 / §5-7 / §5-8 / §5-9 と同列)。
2. §6.11-2 の事実認定を
   「**しきい値ロックは有効だが、v2 の解除 API に契約一致検証が無いため防御は条件付き**」に訂正する。
3. §6.11 に **「ロック解除は (a) 契約一致検証を必須 (b) 監査ログ必須 (O-6) (c) レート制限の対象に含める」**を追加する。
   v3 が v2 の `/accounts/unlock` を再利用する予定がある場合 (`docs/design/API/settings.md` の再利用一覧に
   該当があるかは本レビューの範囲外) は、**再利用の可否をここで判定する**。

### 重大 3. `docs/design/auth.md:607-609` (§6.10-3) — 新設した CI 検査のスコープが「認証・トークン生成に関わるパッケージ」で未定義。**v2 §5-8 と同型 (汎用 util に置かれた乱数生成) を検出できない**

**なぜ本番で問題になるか**: 実装者は記述どおり検査対象を認証パッケージに限定して実装し、
**検査は通り続ける**。その一方で v3 の `util` 相当 (あるいは Service 層の共有ヘルパ) に
`math/rand` ベースの生成関数が置かれれば、§5-8 がそのまま再現する。
§6.10 自身が「これが無いと (1)(2) は『気をつける』に留まる」と書いているとおり、
**この検査が効かないなら §6.10 の 1・2 は設計として無効**。
これは既存の **重大 6** (「`-- name: Get*` 限定の検査が F-15 を検出できない」) と**同じ根の再発**である。
加えて「認証・トークン生成に関わるパッケージ」の範囲が文書に無いため、実装者判断に委ねられている (DR-5)。

**どう直すか**:

1. 検査を**リポジトリ全体**に掛ける — 「`math/rand` および `math/rand/v2` の import を**全パッケージで禁止**。
   例外は許可リストファイル (例: `scripts/allow-math-rand.txt`) にパスで列挙し、追加時は
   PR 説明に理由を書くことをレビュー条件にする」。
2. **裏側の検査も対で置く** — 「秘密文字列の生成は 1 パッケージ 1 関数に集約し、
   **`crypto/rand` を import できるのはそのファイルのみ**」(集約が崩れたことを検出できる形にする)。
   これで §6.10-1 の「1 つのユーティリティに集約」が宣言から検査可能な不変条件になる。
3. `docs/design/architecture.md` §5 の **D-2 行に検査を登録する** (中 4 と同時に閉じる)。

### 重大 4. `docs/design/auth.md:532-560` (§6.8) / `:682-687` (Q-A1) — **v2 の `JWT_KEY` は git 追跡下の `.env` に置かれ、イメージにも焼き込まれている**。「v2 と鍵を共有する」を選んだ場合の必須前提 (共有前のローテーション) が書かれていない

2. Q-A1 の説明に「共有を選ぶ場合、現行鍵の値は再利用できない (初回ローテーションが前提)」を明記する。
   共有の可否判断に影響する情報が抜けたまま回答されるのを防ぐ。
3. 併せて `ADMIN_JWT_KEY` も同じ経路であるため、§6.8-3 (鍵分離の維持) に同じ注記を付ける。

## 6. 良かった点

1. **新規に発見した v2 の欠陥 2 件 (§5-8 / §5-9) の質が高い**。特に §5-8 は
   「`GenerateSecureToken` という名前の関数が `math/rand` を使っている」という、
   **grep 1 発では出てこない (import 構成から解決先を判定しないと分からない) 欠陥**を捉えている。
   照合の結果、非 vendor コードの `crypto/rand` 使用は**本当に 0 件**で、
   `math/rand` を import するファイルも `util/util.go` の 1 件だけだった — 事実として正確。
   「認証の迂回経路にある欠陥。JWT 側をどれだけ固めても、ここが破られれば任意アカウントを乗っ取れる」
   という位置づけの説明も、A-1 の設計に対する優先度を正しく伝えている。

2. **却下理由が「利点が発生しない」まで踏み込んでいる**。§6.8 の RS256 却下は
   「v3 では署名者と検証者が同一プロセスなので**公開鍵方式の利点そのものが発生しない**」+
   「将来 v3 の外に検証だけを行う系統を作る場合は再検討する」という**再検討条件付き**の形になっている。
   一般論 (「RS256 の方が安全」) に流されず、自分の構成に照らして判断している。

3. **「名前が実装と矛盾している関数は移植すると危険」という移植判断**。§6.10-2 が
   `GenerateSecureToken` を「移植すると『安全な生成をしているつもりで安全でない』状態が v3 に運ばれる」
   として個別に名指しで却下している。BE-8 の「黙って死ぬ」性質と結び付けた却下理由は的確
   (検査のスコープは重大 3 だが、**却下の判断そのものは正しい**)。

4. **§6.7 後半の MFA ホワイトリスト化**。`hassan-v2-backend/auth/middleware.go:41` の
   `strings.HasPrefix(path, "/mfa")` を確認したうえで、
   「ルート名の付け方という**設計と無関係な要因で境界が動く**」を却下理由にしている。
   将来 `/mfa` を接頭辞に持つ別ルートで MFA を素通りできる、という具体的な事故形まで書いてある。

5. **§6.11-1 が v2 の「意図の不一致」を根拠にしている**。サインインは
   `hassan-v2-backend/usecase/account/sign_in.go:97` のコメントで**意図的に**マスクしているのに、
   リセット要求はしていない — という非対称を根拠に「片方だけマスクしても列挙は成立する」と結論している。
   v2 の設計意図を尊重しつつ、その実装の不徹底を v3 で揃える形になっている。

6. **Q-A4 が Q-A1 との一体性を帰結まで書いている**。「共有する場合、ローテーションは v2 と v3 の
   同時作業になり、(a) を選ぶなら **v2 側も複数鍵検証に対応する必要がある**」まで書けているため、
   ユーザーが回答するときに作業量を含めて判断できる。§9 の依存関係の書き方としては模範的
   (重大 4 の前提条件を足せば、この論点は完成する)。

#### 重大 3. `docs/design/auth.md:677-687` (§6.9 の設計表) / `:489-502` (§6.2) — ロック機構に**回復経路 (escape hatch) が無い**。v2 が持つ社内管理者による解除 (`POST /admin/accounts/unlock`) が無言で落ちており、ロックは時間経過でも解けない (BE-10 の型が再発)

**何が問題か**: §6.9 の表は**ロック / 解除の実行者を「契約内管理者」のみ**と決めた。
一方 §6.2 は「管理者 (`X-Admin-Token` 系) は**本増分の対象外**」としている。
この 2 つを合わせると、**契約内管理者が全員ロックされた場合、製品内に解除手段が存在しない**。

**根拠 (一次ソース。照合 #24 / #14 / #16)**:

| 事実 | 出典 |
|---|---|
| v2 は社内管理者用の解除 API を持つ。**対象は `accounts`** (`admin_accounts` ではない) で **ID 指定** | `router/router.go:211` → `controller/admin_account.go:487-515` → `usecase/admin_account/unlock_account_by_admin.go:26` → `repository/account.go:262-263` → `db/queries/account.sql:73-78` |
| 同 API は `adminAccountRoute.Use(AdminAuthRequiredMiddleware())` (`router/router.go:201`) の**後**に登録されており、社内管理者認証がかかる (= 意図的な運用経路) | `router/router.go:201`, `:211` |
| **ロックは時間経過で解けない** — ミドルウェアは `last_locked_at` が非ゼロなら無条件に 401 | `auth/middleware.go:70` |
| **第三者がロックを誘発できる** — 失敗回数の加算は **email 指定**で、しきい値超過で `last_locked_at` が立つ | `db/queries/account.sql:56-64` (`WHERE email = $2`) |
| v2 は「管理者を失う操作」に個別のガードを持つ (削除拒否 / 最後の管理者の降格拒否) が、**§6.9 のロック API には対応するガードが無い** | `usecase/account/delete_account.go:47`、`usecase/account/update_account_by_admin.go:64` |

**なぜ本番で問題になるか**: 3 つの経路で同じ終端 (契約全体のロックアウト) に到達する。

1. **攻撃**: 契約内管理者の email が分かれば、失敗サインインを N 回送るだけでロックできる
   (§6.11-3 のレート制限は**試行速度を落とすがロック成立を防がない** — ロックしきい値の方が小さい)。
   管理者が 1 名の契約は、これだけで全機能が使えなくなる。
2. **事故**: 管理者が自分のパスワードを忘れて N 回失敗する (最も起きやすい)。
3. **内部**: 新設した手動ロック API を使って、契約内管理者が他の管理者を含む全員をロックできる
   (最後の管理者を守るガードが無い)。

いずれの場合も復旧は **DB の直接 UPDATE** しかない。これは §6.9 が「失効手段を成立させる」ために
新設した機構が、**同時に新しい単一障害点を作っている**状態であり、
前回重大 1 / 重大 2 で指摘した **BE-10 (読む側と書く側を対で設計する) の第 3 の再発**である
(起こす側 → 塞いだ / 戻す側の権限 → 塞いだ / **戻す側が到達不能になるケース → 未設計**)。
加えて Q-A2 の原則「**v2 でできていたことは満たす**」に対する**無言の後退**でもある
(Q-A2 の事実収集は `grep IsAdmin()` = 契約内ロールのみを見ており、
**`X-Admin-Token` で保護された v2 の運用経路が視野に入っていない**)。

**どう直すか** (どれか 1 つでは足りない。1 + 2 は必須):

1. **回復経路を決める** — 次のいずれかを採用し、却下案と理由を書く。
   (a) 社内管理者による解除 (`POST /admin/accounts/unlock` 相当) を**本増分の対象に含める**
   — v2 に前例があり Q-A2 の原則と整合する。§6.2 の「管理者系は対象外」に例外を 1 行足す形になる。
   (b) **自動ロック解除 (時間経過)** を導入し、手動ロックのみ恒久にする
   — v2 の挙動 (恒久ロック) からの逸脱になるので理由を書く。
   (c) 対象外とするなら、**運用手順書での DB 直更新を先送り先として明記**する
   (`docs/design/operations.md`。ただし「本番で SQL を手打ちする」ことの承認が必要)。
2. **§6.9 の表に「最後の契約内管理者をロックできない」ガードを追加する**
   (`usecase/account/delete_account.go:47` / `update_account_by_admin.go:64` と同じ性質の制約。
   v2 に前例があるので逸脱にならない)。**自分自身をロックできるか**も決める。
3. §6.11-2 に **「ロックは時間経過で解けない」ことを事実として明記**する
   (`auth/middleware.go:70` を出典に)。踏襲の帰結として読者に見えるようにする。
4. §10.2 **R-3 に「メンバー一覧でロック状態を返す」を明記**する
   — v2 は `ListAccountsForAdmin` が `last_locked_at` を返している (`db/queries/account.sql:98`) ため
   移植対象に含まれるが、**「ロックされたことを管理者が知る経路」として名指しされていない**
   (BE-10 の読む側)。

### 14.5 Freeze をブロックする指摘 (Must Fix)

#### B1. `docs/design/auth.md:513-528` (§6.2) — ロック機構を捨てた代わりの防御「MFA 必須」が**v2 に器・経路・クレームのいずれも無く、§6.2 が宣言した「範囲 3 点」にも入っていない**。このまま渡すと、全契約横断の解除 API がパスワードのみで守られる

**根拠 (すべて一次ソース)**:

| 必要なもの | v2 の状態 | 出典 |
|---|---|---|
| MFA シークレットの保管先 | `admin_accounts` に MFA 列なし。`account_mfa_configs` は `account_id` が `accounts (id)` への FK で、**`admin_accounts` を参照できない** | `hassan-v2-backend/db/schema.sql:52-64` / `:68-77` |
| 検証状態の判定 | `AdminAuthRequiredMiddleware` に MFA 判定が無い (トークン → UUID → 実在確認のみ) | `hassan-v2-backend/auth/middleware.go:88-131` |
| トークンに載せる器 | 管理者トークンのクレームは **`uid` と `exp` のみ** (ユーザー側の `mfa_verified` に相当するものが無い) | `hassan-v2-backend/auth/client.go:92-95` |
| 必須化の判定材料 | ユーザー側は**会社単位** `companies.mfa_type` で判定する (§1.4)。社内管理者は会社に属さないため同じ機構が使えない | `docs/design/auth.md:114-115` |

**なぜ本番で問題になるか**: §6.2 は「ロック列を新設する案」を却下した理由として
「MFA 必須 + レート制限 + 監査の方が機構の総量が小さく穴も少ない」と書いているが、
**MFA 必須の機構の総量はロック列より大きい** (新テーブル + 登録・検証エンドポイント +
トークンクレーム変更 + デバイス紛失時のリセット経路)。しかも
`auth.md:503-512` の「含める範囲」表は**解除 / サインイン / 初期投入の 3 点しか挙げていない**ため、
実装者は「範囲 3 点」に従って MFA を落とす。結果として
**`POST /admin/accounts/unlock` (全契約のどのアカウントでも解除できる) が、
ロックもレート制限以上の第 2 要素も無いパスワード認証だけで守られる**。
これは §6.2 が却下した「回復経路が新たな攻撃面になる」状態そのものである。
加えて、MFA 必須は**デバイス紛失時に社内管理者が入れなくなる = 却下理由と同じロックアウト経路**を持つが、
その回復経路 (`:526-527` が却下 (a) で否定した DB 直更新以外の手段) が書かれていない。

**併せて範囲宣言の矛盾 3 件** (どれが正か実装者には判定できない):

| 箇所 | 示している範囲 |
|---|---|
| `auth.md:503-512` (§6.2) | 解除 + サインイン + 初期投入 (移行スクリプト)。**公開エンドポイントは 1 本増える** |
| `auth.md:576` (§6.3 の例外列挙) | **`register_admin_password_requests` を v3 が持つ**前提 (= v2 の公開 2 本 `router.go:199-200` に相当するパスワード登録フローが入る) |
| `auth.md:724` (§6.7 の公開系統) | 管理者系の公開は **`POST /admin/signin` の 1 本のみ** |

**何を書けば閉じるか**: §6.2 に「社内管理者認証の構成要素」の表を 1 つ置き、
**①MFA のシークレット保管先 (新テーブル名と、§6.3 の例外列挙への追加) ②登録・検証エンドポイント
(= §6.7 の系統表に追加。公開が何本になるか) ③管理者トークンに検証状態を載せるか
④デバイス紛失時のリセット経路と実行者 ⑤`register_admin_password_requests` を持つのか
(持たないなら §6.3 の列挙から外し、移行スクリプトが bcrypt ハッシュを直接投入すると明記)** を確定させる。
**あるいは「MFA は本増分では実装しない」と決め直し、代替として何で守るか
(IP 制限 / レート制限のしきい値を別枠にする 等) と先送り先を書く** — こちらの方が「機構の総量が小さい」
という却下理由と整合する。どちらでも 15 行程度で閉じる。

#### B2. `docs/design/auth.md:639-661` (§6.4 の許可される 5 種) — v3 が本増分で実装する 2 経路が 5 種のどれにも分類できず、「これに当てはまらないものは許可リストに載せない」で閉じているため実装者は誤分類か停止の二択になる (§12 重大 1 と同じ構造の再発)

**分類できない 2 経路 (いずれも v3 の対象と確定済み)**:

1. **招待リンク発行** (`auth.md:1111` の Q-A2 9 操作 / `API/settings.md:178` の移植対象) —
   v2 は `create_signup_link.go:45` で `GetAccountByEmail` を呼び、**レコードのフィールドを使う**:
   `:54` で `account.ContractID` との一致判定、`:59` で `GetCompanyByContractID(account.ContractID)`、
   `:75` で `account.Name` (招待メールの宛名)。`auth.md:650-651` の
   「**`entity.Account` を返す `GetAccountByEmail` を認証済み経路から呼べる形で残さない**」に対し、
   `:656` の例外は**サインインとパスワードリセット要求 (①) のみ**。**招待リンク発行の行き先が無い**。
2. **社内管理者による全契約横断の解除** (`auth.md:833`) — テナント検証を行わないため、
   対象アカウントの読み取り (404 判定・監査の対象記録) と更新が**所有者条件を持てない**。
   v2 の実体は `hassan-v2-backend/db/queries/account.sql:73-78`
   (`UnlockAccountByID` = `UPDATE accounts … WHERE id = $1`)。5 種の
   ②「所有者を決定するクエリ」は**認証ミドルウェアがトークンから自分を引く処理**であり、これには当たらない。

**なぜ本番で問題になるか**: 1 について実装者が取りうる行動は
(a) `GetAccountByEmail` (レコードを返す) を③として許可リストに載せる = **§6.4 が構造的に消したはずの
「認証済み経路からの無スコープ読み取り」が初回から復活する** か、
(b) 実装を止める。2 については、許可リストに載せられないまま `WHERE id = $1` のクエリを作ることになり、
**「許可リストに無い例外」が最初の 1 件目から発生して運用が破れる**
(`auth.md:581` は「列挙を増やす変更は認証系レビューの対象」と定めている)。

**何を書けば閉じるか**: (i) **⑥として「社内管理者 (`X-Admin-Token` 系統) の全契約横断クエリ」を追加**し、
「**§6.7 の管理者認証系統からのみ呼べること + 監査記録必須 + ロック解除 1 本に限る**」を条件として書く。
(ii) 招待リンク発行は **`GetAccountByEmailAndContractID(email, contractID)` に置き換える**と明記する
(契約条件を持つので許可リスト不要。v2 の `:54` の read-then-compare = §6.4 却下 (a) のパターン B を
同時に潰せるため、**v2 より強くなる**)。2〜3 行で閉じる。

#### B3. `docs/design/auth.md:622-626` (§6.4 の所有者 ID コンストラクタ) — 「認証済みコンテキストから生成する 1 本のみ」が同書 §6.9 / Q-A2 / `API/README.md` D-API-8 と矛盾し、既存 **重大 6 (F-15 型の越境) が閉じていない**

**根拠**: 判定の詳細は §14.3。要点は 3 つ。
①F-15 のクエリは所有者条件を**持っている** (`hassan-v2-backend/db/queries/theme.sql:16-22`) ため、
検査対象を `List*` に拡げても**合格する** (`usecase/theme/list_themes.go:56-62` が

②したがって F-15 を閉じるのは**コンストラクタ側だけ**である。
③その規約が「認証済みコンテキストからのみ」と書かれているため、
**リクエスト由来の所有者 ID を必要とする本増分の API** (手動ロック / 解除の対象指定 = `auth.md:819`、
社内管理者経路 = `:833`、メンバー管理 = `:1112`、`created_by` = `docs/design/API/README.md:106`)
に対する正当な生成経路が存在しない。実装者はコンストラクタを迂回するしかなく、
**08-production-gates A-4 が名指しした形が最高権限 API を含めて再発する**。

**何を書けば閉じるか**: コンストラクタを**用途別に有限個**にする —
①`FromAuthContext()` (呼び出し元自身の ID)
②`NewAccountIDInContract(raw string, caller ContractID) (AccountID, error)` =
**契約所属を DB で検証してから型を付ける** (`review-auth-api.md:318-321` の原案。
「存在確認は所有権の検証にならない」が型で担保される)
③社内管理者経路用 (契約検証なし・**監査必須**・B2 の⑥と対で使う)。
**この 3 本以外を作らないことを CI で検査する** (コンストラクタ関数の定義箇所と型変換 `AccountID(...)` の
出現を検査するだけで足りる) と書き、`docs/design/API/README.md` §1.4 の表にも 1 行足す。5〜8 行で閉じる。
