## 重大 (Must Fix)

### 重大 1. プリフライト (`OPTIONS`) の扱いが認証設計の SSOT に無い — 段階1 が起動しない可能性がある

- **箇所**: `docs/design/auth.md` §6.7 (`:993-1028`) / §10.3 の受信欄 R-FE-1 (`:1792`) /
  `docs/design/frontend.md` §12.3 (`:1186` 付近の「プリフライトが必ず発生する」)
- **問題**: 段階1 は全 BE 呼び出しに `X-Token` (カスタムヘッダ) を付けるため、
  **すべてのリクエストに `OPTIONS` プリフライトが先行する** (§12.3 / §6.1.1 の R-5 が自ら明記)。
  ところが `auth.md` §6.7 は「**公開エンドポイントだけを別グループに切り出し、認証必須をグループ既定にする**」
  「**ホワイトリストは有限列挙**」「**CI がルート定義と宣言の系統単位の一致を検査する**」と宣言しており、
  **プリフライトがどこで終端されるかが 1 行も無い**。`frontend.md` は「BE 側で `OPTIONS` を
  認証の対象外にすること」を §16.2-8 の **8-e** として起票しているが、宛先が
  「BE 側 (実装リポ / `API/README.md`)」であり、**機構 (系統宣言と CI 検査) を持つ `auth.md` §6.7 に届いていない**。
  `auth.md` §10.3 の受信欄 **R-FE-1 も 3 点 (AT 短縮 / Cookie / WAF) だけ**で CORS を含まない。
- **本番でどう出るか**: 認証ミドルウェアが `OPTIONS` を先に受けると **401 (本文なし) を返し、
  ブラウザはプリフライト失敗として本要求を送らない**。結果は「**FE の画面が 1 つも動かない**」で、
  しかも `frontend.md` §9 の「ネットワーク失敗」行が自ら書いているとおり
  **`fetch` は拒否理由をアプリに渡さないため「通信に失敗しました」に丸められる**。
  段階1 で最も起きやすく、最も切り分けにくい障害である。
- **v2 の事実 (転記されていない)**: v2 は CORS ミドルウェア内で
  `if c.Request.Method == "OPTIONS" { c.Status(200); c.Abort() }` により**認証より前に終端**している
  (`hassan-v2-backend/router/router.go:256-259` = `localCors` / `:273-276` = `cors`)。
  `auth.md` §6.13.1 のシーケンス図 (`:1478`) も M2 に CORS を置き AT より前に通しているが、
  **OPTIONS が M2 で終端して AT に到達しないことは書かれていない**。
- **修正案**:
  1. `auth.md` §6.7 に 1 行追加 — 「**プリフライト `OPTIONS` は CORS ミドルウェア (認証ミドルウェアより前) で
     終端し、`204/200` を返して abort する。系統宣言の対象外であり、CI の系統一致検査も `OPTIONS` を数えない**」
     (v2 の出典 `router/router.go:256-259` を付ける)
  2. `auth.md` §10.3 の R-FE-1 に **④ CORS / プリフライトの受け入れ**を追加し、状態を「未対応」で起票する
  3. `frontend.md` §16.2-8 の 8-e の宛先に **`auth.md` §6.7** を加える

### 重大 2. `Access-Control-Expose-Headers` が無いため、段階1 で 429 の `Retry-After` を FE が読めない

- **箇所**: `docs/design/frontend.md` §12.3 の決定 3 / §9 の 429 行
- **問題**: §9 の 429 行は「**再試行までの残り時間を表示し、送信ボタンを無効化**」を
  「BE の `message` + **`Retry-After`**」から作ると定めている。しかし `Retry-After` は
  **CORS-safelisted response header ではない**ため、BE が `Access-Control-Expose-Headers: Retry-After` を
  返さない限り**ブラウザの JS から読めない**。§12.3 の決定 3 は**リクエスト**ヘッダの許可リスト
  (`Content-Type` / `X-Token` / `X-Admin-Token` / `X-Request-Id`) と許可メソッドしか決めておらず、
  **レスポンスヘッダの露出が抜けている**。
- **v2 に倣っても埋まらない**: v2 の CORS ミドルウェアにも `Access-Control-Expose-Headers` は無い
  (`hassan-v2-backend/router/router.go:246-278` に該当行なし)。v2 は通常 API をサーバ経由で叩いていた
  (V-23) ため問題にならなかった。
- **DR-10 の典型**: 段階2 (Route Handler 中継) なら**サーバが `Retry-After` を読めた**ため、
  この担保は「構造の副産物」だった。**構造を変えた差分で代替の機構が用意されていない**。
- **本番でどう出るか**: 認証系のレート制限 (`auth.md` §6.11-3) が発動したときに、
  ユーザーへ「あと何秒待てばよいか」を出せない。仕様どおり実装した FE が**必ず** `undefined` を掴む。
- **修正案**: §12.3 の決定 3 に
  「**`Access-Control-Expose-Headers` に `Retry-After` を含める** (段階1 で FE が読む必要がある唯一の
  レスポンスヘッダ。増やす場合は本表に追記する)」を加え、§16.2-8 の 8-e に列挙する。
  併せて §9 の 429 行に「`Retry-After` の読み取りは §12.3 の露出設定に依存する」の参照を付ける。

### 重大 3. `auth.md` §10.2 の R-5 が「CORS の論点が消える」のまま (DR-8)
