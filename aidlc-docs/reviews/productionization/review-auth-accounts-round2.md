### 重大 1. `audit_logs` の設計が本書 / `observability.md` / `data-model.md` で**別物**になっており、R-AA-19 の状態列「未対応」がそれを隠している (BE-10 / BE-12 / DR-8 / O-6)

- **箇所**: `docs/design/API/auth-accounts.md:353` (AA-D-21)、`同:737` (R-AA-19。状態列 = **未対応**)、
  `同:691` (§4 の O-6 行「この 2 件が反映されるまで `signin_failed` は実装できず」)、
  `同:694` (§4 の D-5 行「`AUDIT_EMAIL_HMAC_KEY`」)
- **事実 (現物)**: `data-model.md` は **2026-07-31 に既に改訂済み**で、**本書が却下した案を採用している**。

  | 論点 | 本書 AA-D-21 (+ `observability.md:281`-`:287` = 一致) | `data-model.md` の現物 | 
  |---|---|---|
  | actor の表現 | **`actor_type` に値を足さない**。`actor_id` / `contract_id` を NULL 可にする。**却下 (c) = `actor_type` に値を足す案** (「値を増やすと 3 通りになる」) | `:700` **`actor_type` (`account`\|`admin_account`\|`unauthenticated`)** を採用 (`:742`「**採用**」) |
  | CHECK の条件 | 「**両方 NULL になれるのは `action` が認証失敗系のときだけ**」(AA-D-21②) | `:744`-`:745` **`actor_type = 'unauthenticated'`** を条件にした CHECK |
  | メールの秘匿 | **HMAC-SHA256 + pepper `AUDIT_EMAIL_HMAC_KEY`**。**「素の SHA-256 は既知アドレスの総当たりで復元できるため採らない」と明示** | `:748` **`{"email_hash": "<SHA-256>"}`** (素の SHA-256) |
  | インデックス | `(contract_id, …)` を**部分**インデックス化 + `(action, occurred_at DESC)` | `:700` `(contract_id, …)` は**部分化せず**、`(action, occurred_at DESC) **WHERE actor_type='unauthenticated'**` |

- **なぜ本番で問題になるか**:
  1. **本書の指示どおり実装すると INSERT が実行時に失敗する**。本書は「アカウントが解決できた失敗は
     両列を埋める / 未登録メールは両方 NULL」とし `actor_type` は 2 値のままだが、スキーマ側の CHECK は
     `actor_type='unauthenticated'` でないと NULL を許さない。**`signin_failed` の書き込みが
     CHECK 違反で落ちる** — 監査は best-effort (`observability.md` §4.5) なので **WARN が出るだけで
     機能は静かに死ぬ** (重大 2 で解こうとした BE-10 の再演)
  2. **秘匿方式の後退**。`data-model.md` の素の SHA-256 は、本書と `observability.md` が
     「辞書攻撃で復元できる」として明示的に却下した方式である。**`data-model.md:748` 自身が
     「値域と記録項目の SSOT は `observability.md` §4.5」と書いており、その §4.5.2 は HMAC + pepper** —
     参照先と本文が矛盾している。どちらで実装されるかは実装者の読んだ順で決まる
  3. **検出できない**。本書 §5 の R-AA-19 の状態列は「**未対応 (2026-07-31 のレビュー重大 2)**」であり、
     受け手が**別案で反映済み**であることが読み取れない。§4 の O-6 行も「反映されるまで実装できない」と
     書いたままで、**割れの存在自体がどこにも記録されていない**
  4. **AA-D-21 の前提事実がすでに偽**。AA-D-21 の書き出しは「`contract_id` は `NOT NULL` を維持すると
     明記されている (`docs/design/data-model.md:694`-`:695`) ため、**現状のスキーマでは `signin_failed` が
     書けない**」だが、当該記述は `:732`-`:735` で反転済み (「旧記述は『NOT NULL を維持できる』だったが…改訂した」)。
     **問題提起の根拠が消えた状態で、解決方針だけが残っている** (DR-1)
- **修正案 (本書側)**:
  1. R-AA-19 の状態列を「**対応済み・ただし採用案が本書と異なる (2026-07-31)**」に変え、
     **相違 3 点 (actor_type / CHECK の条件 / SHA-256 か HMAC か) を明記**する
  2. **どちらを正とするかを決める**。少なくとも**メールの秘匿は HMAC + pepper に寄せる**
     (本書 §4 の D-5 が `AUDIT_EMAIL_HMAC_KEY` を秘密の棚卸し対象に加えており、
     SHA-256 を採るなら D-5 の 3 件目を撤回する必要がある = 波及先が本書内にある)。
     `actor_type` の 3 値化を受け入れるなら **AA-D-21 の却下 (c) を「採用に転じた」と書き換え**、
     §3.7 の「両方 NULL」の記述を `actor_type='unauthenticated'` に合わせる
  3. AA-D-21 / R-AA-19 の `data-model.md:694`-`:695` / `:662` の引用を**節番号 (§4.10) へ置き換える** (中 6)
