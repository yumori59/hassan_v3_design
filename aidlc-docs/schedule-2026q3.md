## 0.1 実行方式

**実装は大分類を跨いで並列にしない**。**B 認証 → A インフラ → C 発散** の順に、
1 つの大分類を完了させてから次に着手する。**分類内では issue 単位の並列を許す** (§3.1 / §4.1 / §5.1)。

**実装を伴わない 2 本だけを B と並走させる** — **A-0 (インフラ理解)** と **C-0 (発散の設計)**。
どちらも読む・書く・起票するだけで実装レーンを進めないため、直列性を壊さない。

| | 内容 |
|---|---|
| **順序** | B 認証 + 設定 (8/13〜8/26) → A インフラ (8/27〜9/9) → C 発散 (**9/10〜9/30 = 3 週間**) |
| **B の裏で進めるもの** | **A-0** (§3.2) と **C-0 = 発散の設計と起票** (§3.3)。C-0 を先に済ませることで、C の 3 週間を実装と検証だけに使える |
| **C の期間** | **3 週間を確保する**。tool 契約 (C-3) と会話ターン (C-4) に BE-8 / BE-10 / BE-12 が集中し、**末尾に通し検証 (C-7) を 4 日置く** |
| **テーマ** | **スコープ外** — 別の開発者が担当する。ただし `POST /conversations` は `theme_id` 必須のため**依存が残る** (§7 の R-12) |
| **設定** | **v2 にあった設定機能を B-9 として入れる** (§3 の B-9)。A から 3 日を移した — **A が本計画で最も薄い部分になる** (§7 の R-14) |
| **期限** | 9/30 固定。並列時に 3 分類へ分割していた稼働を 1 分類へ集中させる前提で、各中分類の所要を圧縮している |
| **バッファ** | **C-7 の通し検証 4 日が実質のバッファも兼ねる**。それを超える遅延は C-6 → C-5 の版・復元 の順に削る (§7 の R-6) |

## 1. 律速はマージである

**実測**: 実装リポの `origin/main` は 10 コミット・マージ済み PR 4 本 (8/03〜8/06) で、**8/06 以降のマージはゼロ**。
そのあいだに issue は 23 本に積み上がり、**レビューまで終わった #6 / #7 が 3 日滞留している**。
一方このスケジュールは **40 issue / 7.4 週 = 5.4 本/週**のマージを要求する。

止まっているのは実装ではなく **H-1 (人間の approve とマージ)** であり、
その機構であるブランチ保護・environment が未設定 (実装リポ rules 04 §4) であることと同根である。
**直列では 1 本の PR の滞留がそのまま全体の停止になる**。

| 運用として決めること | 内容 |
|---|---|
| **マージの頻度** | **週 6 本以上**。滞留が **1 本でも 2 日を超えたら**マージを最優先にする |
| **観測** | 週次で `gh pr list --state open` の本数と最古の PR の経過日数を見る。**進捗は issue のクローズ数で測る** (ブランチの本数で測らない) |
| **待ち時間の使い道** | マージ待ちで手が空いたら **A-0 (インフラ理解) に充てる**。実装レーンを先へ進めない |

## 1.5 AI 駆動開発の前提 (1 issue のコスト構造)

**本計画は実装リポの S-1〜S-10 ループ (`hassan-v3/.claude/rules/01-construction-loop.md`) の上に載っている**。
各中分類の所要は複数 issue ぶんのループを内包する。

| 要素 | ループ上の位置 | 日程への現れ方 |
|---|---|---|
| **計画** | S-3 (`hassan-v3/docs/plans/<issue番号>-<slug>.md` が V-12 で backend の全 issue に必須) | 各中分類の所要に内包 |
| **Red → Green** | S-4 → S-5 (実装 SA。**裏取りは OR** — 自己申告を受理しない) | 同上 |
| **検証** | S-6 (OR 自身が実行。SA の報告を流用しない) | 同上 |
| **レビューの往復** | S-7 → S-8 → S-6 → 再レビュー。**上限 2 巡**。3 巡目に入らず**停止して人間へ** (rules 01 §3) | **各表の「想定巡数」列**。上限到達時は R-7 |
| **着手前の計画承認** | **H-5** (S-2)。該当 issue は `needs-human` ラベルで**停止する** | **各表の「H-5」列**。該当条件は rules 04 §1.2 |
| **マージ** | **H-1** (S-10)。人間のみ | §1 の律速 |
| **DB マイグレーション適用 / Agent 再発行** | **H-2 / H-3**。GitHub environment の承認 | A-6 の停止点 |
| **`terraform apply`** | **人間のみ** (rules 01 §0 の自律範囲) | A の各中分類の停止点 |
| **並列実行** | 異なる issue は**触るファイルが重複しなければ `git worktree` 隔離で並列可** (rules 01 §5)。同一 issue の S-4→S-5→S-6→S-7 は直列必須 | **各表の「分類内並列」列** |

**承認待ちの時間は所要日数に含めない**。停止点の数だけを表に持たせ、影響は R-7 / R-8 で扱う。

- **実装レーンの矢印は 1 本** (`B → A → C`)。B の遅れは A と C を、A の遅れは C を押し出す
