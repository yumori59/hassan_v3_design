## 0.1 実行方式: 開発を進めながらインフラの理解を積む (実装は直列 1 レーン)

**実装は大分類を跨いで並列にしない**。**B 認証 → A インフラ → C 発散** の順に、
1 つの大分類を完了させてから次に着手する。

ただし**インフラの「理解」は実装レーンとは別**に、**B の実施中から週次の学習ブロック (A-0)** として常時入れる。
**A-0 は成果物を持たない学習であり、実装レーンではない** — したがって「分類を跨いだ並列」には当たらない。

| | 内容 |
|---|---|
| **実装の順序** | **B 認証 → A インフラ → C 発散**。手を動かせる #6 / #7 から始め、インフラは理解が溜まってから着手する |
| **理解の進め方** | **A-0 (週次のインフラ理解ブロック)** を B の期間中に置く。§4 の A-1 着手時点で「何を・なぜ作るか」を自分で説明できる状態にするのが完了条件 |
| **期限** | **9/30 を固定する**。並列時に 3 分類へ 3 分割していた稼働を 1 分類へ集中させる前提で、**各中分類の所要を「1 週」から「1〜4 日」に圧縮**した (§8 の日付割りが正) |
| **代償 1** | **B (認証) の受入確認を dev 実機で行えない** — dev 環境の成立が A-6 (9/12) のため、**B の全期間はローカルと UT に限られる**。§7 の R-10 |
| **代償 2** | **バッファがゼロ** (並列時の予備週は消えた)。遅延は他レーンに吸収されず、**必ず最後尾の C-6 (評価・CSV) を削る形で現れる**。§7 の R-9 |
| **利点** | **A-3m (dev 限定の Agent 手動発行) が不要**になった — A が C より前に完了するため、`apply_agent` の正規経路が C-4 の着手時点で通っている。初版にあった二重管理リスク (旧 R-5) も消える |

## 1. 律速はマージである (直列では、より直撃する)

**実測**: 実装リポの `origin/main` は 10 コミット・マージ済み PR 4 本 (8/03〜8/06) で、**8/06 以降のマージはゼロ**。
そのあいだに issue は 23 本に積み上がり、**レビューまで終わった #6 / #7 が 3 日滞留している**。
一方このスケジュールは **40 issue / 7.4 週 = 5.4 本/週**のマージを要求する。

止まっているのは実装ではなく **H-1 (人間の approve とマージ)** であり、
その機構であるブランチ保護・environment が未設定 (実装リポ rules 04 §4) であることと同根である。

**直列化はこの問題を悪化させる**。並列 3 レーンなら 1 レーンがマージ待ちで止まっても他の 2 レーンが進んだが、
**直列では 1 本の PR の滞留がそのまま全体の停止**になる。**この 2 つを片付けない限り、下の表は絵に描いた餅になる。**

| 運用として決めること | 内容 |
|---|---|
| **マージの頻度** | **週 6 本以上**を維持する。**直列では「滞留 3 本超で新規着手を止める」では遅い** — 滞留が **1 本でも 2 日を超えたら**その時点でマージを最優先にする |
| **観測** | 週次で `gh pr list --state open` の本数と最古の PR の経過日数を見る。**「実装が進んでいる」を issue のクローズ数で測る** (ブランチの本数で測らない) |
| **待ち時間の使い道** | マージ待ちで手が空いたら **A-0 (インフラ理解) に充てる**。実装レーンを先へ進めない |

### 4.1 A を AI 駆動ループに乗せる (§1.5 の適用)
