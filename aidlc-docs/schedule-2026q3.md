## 0.1 実行方式: 分類を跨いだ並列をしない (直列 1 レーン)

**大分類 A / B / C を同時に走らせない**。**A (インフラ) → B (認証) → C (発散)** の順に、
**1 つの大分類を完了させてから次に着手する**。同一大分類の中では、中分類が依存順に並ぶ。

| | 内容 |
|---|---|
| **順序** | **A インフラ → B 認証 → C 発散**。dev 環境を先に立てることで、B・C の受入確認を最初から実機で行える |
| **期限** | **9/30 を固定する**。並列時に 3 分類へ 3 分割していた稼働を 1 分類へ集中させる前提で、**各中分類の所要を「1 週」から「2〜3 日」に圧縮**した (§3〜§5 の日付割り) |
| **代償** | **バッファがゼロになる** (並列時の予備週 B-9 / C-7 は消えた)。遅延は他レーンに吸収されず、**必ず最後尾の C-6 (評価・CSV) を削る形で現れる**。§7 の R-9 |
| **利点** | **A-3m (dev 限定の Agent 手動発行) が不要になった** — A が C より前に完了するため、`apply_agent` の正規経路が C-4 の着手時点で通っている。初版にあった二重管理リスク (旧 R-5) も消える |

期間は 7 週 + 3 日。日付割りは §8 の直列ビューが正。

## 1. 律速はマージである (直列では、より直撃する)

**実測**: 実装リポの `origin/main` は 10 コミット・マージ済み PR 4 本 (8/03〜8/06) で、**8/06 以降のマージはゼロ**。
そのあいだに issue は 23 本に積み上がり、**レビューまで終わった #6 / #7 が 3 日滞留している**。
一方このスケジュールは **40 issue / 7.4 週 = 5.4 本/週**のマージを要求する。

止まっているのは実装ではなく **H-1 (人間の approve とマージ)** であり、
その機構であるブランチ保護・environment が未設定 (実装リポ rules 04 §4) であることと同根である。

**直列化はこの問題を悪化させる**。並列 3 レーンなら 1 レーンがマージ待ちで止まっても他の 2 レーンが進んだが、
**直列では 1 本の PR の滞留がそのまま全体の停止**になる。**この 2 つを片付けない限り、下の表は絵に描いた餅になる。**

| 運用として決めること | 内容 |
|---|---|
| **マージの頻度** | **週 6 本以上**を維持する。**直列では「滞留 3 本超で新規着手を止める」では遅い** — 滞留が **1 本でも 2 日を超えたら**その時点でマージを最優先にする |
| **観測** | 週次で `gh pr list --state open` の本数と最古の PR の経過日数を見る。**「実装が進んでいる」を issue のクローズ数で測る** (ブランチの本数で測らない) |

## 6. 依存関係

```
P-1 (GitHub 設定) → P-2 (#6/#7 マージ) → P-3 (#31 OIDC) → P-4 (AC カタログ) → P-5 (系統数の判定)
                                                                  │
        ┌─────────────────────────────────────────────────────────┘
        ↓
  A-1 → A-2 → A-3 → A-4 → A-5 → A-6 → A-7        (8/13〜9/2)
                                        │
                                        ↓
  B-3 → B-4 → B-5 → B-6 → B-7 → B-8               (9/3〜9/15)
                                        │
                                        ↓
  P-6 → C-1 → C-2 → C-3 → C-4 → C-5 → C-6         (9/16〜9/30)
```

- **分類を跨ぐ矢印は 1 本ずつしかない** — これが直列化の意味である。A の遅れは B と C の両方を、B の遅れは C を、そのまま押し出す
- **P-2 → B・C**: 認証ミドルウェアが `main` に無いと、追加したエンドポイントが `check-route-auth.sh` (A-1 / AC-1.1) で落ちる
- **A-6 → B・C の受入確認**: dev への自動デプロイが成立するのは A-6 (8/31) 以降。**直列では B・C の全期間がその後ろにある**ため、両分類とも最初から実機で確認できる (並列時は 9/20 以降に限られていた)
- **A-6 → C-4**: 正規の `apply_agent` は段 5・段 8 の後ろにしか来ない。直列では A-6 がそれを満たすので、**手動発行の代替経路 (旧 A-3m) は不要**
