# 第 1 節: ユーザー確定済み (2026-08-23)

## PV-Q1. 評価軸を v4 の 3 軸に差し替えるか

**背景 (事実)**:

- v4 の評価基準定義 `_evalCriteriaState` は **3 軸** — 市場魅力度 (weight 40) / 優位性 (weight 35) /
  実現可能性 (weight 25)。各軸に**サブ基準 3 つ (配点 4/3/3 = 軸内合計 10)** と**数値アンカー 5 段
  (score 10/8/6/4/2)** を持つ (`docs/prototype/hassan_agent_prototype_v4.html:17061`〜`:17126`)
- 同ステートは **`history` (変更履歴)** を持ち、「戦略適合性を廃止 (3 軸に集約) / 重みを 40/35/25 に再配分」
  「実現可能性を新設 (旧: 新規性を廃止)」の記録がある (`同:17120`〜`:17125`)。
  コメントに「**組織で共有・管理者のみ編集可**」とある (`同:17060`)
- 現行設計は **主軸 5 つ** (`novelty` / `mission_fit` / `market_size` / `market_cagr` / `tech_feasibility`) +
  **補助軸 4 つ** で、重み式は `novelty*0.20 + mission_fit*0.20 + market_size*0.25 + market_cagr*0.15 +
  tech_feasibility*0.20` ([ideas.md](../../../docs/design/API/ideas.md) §6.3 / `:648`)
- v2 の評価軸は 4 つ (`uniqueness` / `mission_alignment` / `market_size` / `cagr`) で、
  総合は単純合計 0〜40 (`hassan-v2-backend/util/score_calculator.go:135`)

**選択肢**: A. v4 の 3 軸を採用 (増分 1 は 3 軸化のみ) / B. 現行 5 軸を維持 /
C. v4 の 3 軸 + 契約ごとの編集機能まで増分 1 で作る / D. Other

> 推奨: **A**。理由: ①3 軸は v4 で「7 軸 → 4 軸 → 3 軸」と 3 回の縮約を経た結果であり、
> ユーザー側の運用判断が既に入っている ②契約ごとの編集は DB スキーマ・settings API・変更履歴テーブルを
> 伴い、増分 1 (第 1 リリース) の 3 週間 ([schedule-2026q3.md](../../schedule-2026q3.md) §5) に入らない。

**この回答が左右するもの**: `ideas.md` §6.1〜§6.3 の全面改訂 / `data-model.md` の `ideas` の軸カラム /
CSV の列 / v2 既存データの移行写像 / `llm-migration.md` の LM-R6 の再オープン。

[Answer]: **A で確定** (2026-08-23 ユーザー回答)。**v4 の 3 軸 (市場魅力度 weight 40 / 優位性 weight 35 /
実現可能性 weight 25。各軸にサブ基準と数値アンカー、判定ランク A/B+/B/C) を採用する**。
> **ただし増分 1 は「3 軸化のみ」**:
> - **重み・アンカー・判定条件は現行設計どおり Go 定数 (`entity/idea`) を SSOT とする** (DB にも settings にも持たない)
> - **「契約ごとに編集できる機能 + 変更履歴 + settings の評価基準 CRUD」は増分 2 へ明示的に先送りする** —
>   **先送り先を設計書に書く** (無言の省略 = DR-2 にしない)

## PV-Q3. 3 軸化により v2 の 2 軸が消えることを承認するか (C-16)

**背景 (事実)**: [v2 仕様の引き継ぎ方針 C-16](requirements.md) は「v2 にある操作は落とさない。

①`ideas` の説明文列 (`uniqueness` / `mission_alignment`) ②スコア列 (`uniqueness_score` /
`mission_alignment_score`) ③CSV の 4 列 (9 / 10 / 12 / 13 列目) を占めている
([ideas.md](../../../docs/design/API/ideas.md) §2.6 / §3.3)。
加えて `mission_fit` の廃止は「**会社ミッションを評価入力に渡す**」という判断 (同 §6.2 の該当行) の前提を消す。

**選択肢**: A. 軸の廃止を承認する / B. 3 軸 + ミッション整合を補助軸として残す / C. 3 軸化を見送る / D. Other

> 推奨: **A**。理由: v4 の変更履歴 (`:17123` 「実現可能性を新設 (旧: 新規性を廃止)」) が
> ユーザー側で既に廃止判断を経ていることを示している。

[Answer]: **A で確定** (2026-08-23 ユーザー承認)。**3 軸化により `mission_alignment` と `uniqueness` が
軸として消えることを承認する**。承認の証跡は [requirements-proto-v4.md](requirements-proto-v4.md) §3 に残す。
> **承認の範囲は「軸としての廃止」に限る** — **v2 の CSV 列・説明文列を落とすことは本承認に含まれない**
> (PV-Q7 の判断ルールに従い、既定は列を維持する)。

# 第 2 節: 設計書で確定させる論点 (ユーザーに聞かない。判断ルールを与える)

## PV-Q4. 判定ランク A/B+/B/C の閾値の具体値

**背景 (事実)**: **v4 プロトタイプの数値尺度は 3 系統に分裂している**。

| 尺度 | 値 | 出典 |
|---|---|---|
| **軸のアンカー** | **0〜10** (score 10/8/6/4/2 の 5 段)。サブ基準の配点は 4/3/3 = 軸内 10 点 | `:17073`〜`:17079` |
| **判定ランクの条件** | **0〜5 前提**。A =「加重 4.4 以上 かつ 全軸 6 点以上」/ B+ =「4.0〜4.4」/ B =「3.5〜4.0」/ C =「3.5 未満 or 実現性 < 4」 | `:17115`〜`:17118` |
| **アーティファクト表示の総合** | **0〜40**。`overallScore >= 32 ? high : >= 24 ? mid : low`。モックの値は `marketAppealScore: 8, diffScore: 8, feasScore: 8, overallScore: 32` = **3 軸の和 24 ではなく旧 4 軸の和 32** | `:10033` / `:13636` |

**A の条件は算術的に矛盾している** — 軸が 0〜10 で重みの和が 100% なら「全軸 6 点以上」⇒「加重 6.0 以上」であり、
「加重 4.4 以上」の条件は意味を持たない。ボード表示の `verdict: "A・4.6"` (`:13421`) も 0〜5 尺度である。
さらに「**7 軸スコア (加重)**」の見出し (`:8161`) が残っており、**プロトタイプは過渡状態**である。

> 判断ルール (これに従って設計書で確定させる):
> 1. **尺度は D-IDA-4 (0.0〜10.0 の重み付け平均) を維持する**。v4 の 3 尺度はいずれも採らない (DR-7)
> 2. **構造だけを採る** — 4 段 (A / B+ / B / C) + 「加重の下限」+ 「特定の軸の下限条件」の組み合わせ
> 3. **具体値は 0.0〜10.0 尺度に載せ替えて設計書 ([ideas.md](../../../docs/design/API/ideas.md) §6.3) で数値として確定する**。
>    「適切に」「実装時に調整」で残さない (DR-5)
> 4. **バンドの SSOT は `entity/idea` の 1 関数**。発散直後の `grade` と評価後の `grade` で 2 箇所に持たない (BE-2 / D-IDA-6)
> 5. **旧バンド (8.0 / 6.0 / 4.0 の A/B/C/D) からの変更**であることを明記し、波及先を全件挙げる (AC-PV-2.3)

[Answer]: **設計書で確定する** (上記 5 つの判断ルールに従う。ユーザー確認は不要 — 尺度の維持は D-IDA-4 の既決事項、
構造は PV-Q1 で承認済み、具体値は既存の 0.0〜10.0 尺度への載せ替え計算)。

## PV-Q5. v4 のレンズ集合と tool 引数の enum の対応

**背景 (事実)**:

- 現行 `research_market` の `industry_mode` は `cross_industry` / `balanced` / `intra_industry_novel` の 3 値
  ([conversation.md](../../../docs/design/API/conversation.md) §4.1)。**PoC では実質 `cross_industry` のみが挙動を変え**、
  他の値は空の接尾辞になる ([poc-conversation-flow.md](../../../docs/analysis/poc-conversation-flow.md) の (e))
- 現行 `generate_ideas` の `approach` は `domain` / `trend` / `usage` / `spec` の 4 値 (同 §4.1)。
  PoC ではこの 4 値が「3 者一致」している (同 (g))
- v4 のレンズは**アセット経路 3 種 + ゼロベース経路 3 種**で、どちらも上の enum 値と 1:1 に対応しない。
  v4 のツール呼び出し表示は `search_markets(lens="…", strategy="untapped")` (`:11083`)
- v4 には **`LENS_META` に「主軸」4 種 (高精度 / 非侵襲・非破壊 / 低コスト化 / 既存顧客活用)** が残るが、
  3 質問フローは差別化要素の質問を飛ばす (`:11557` のコメント「skip the differentiator question」)。
  legacy 経路 (`:11684`〜`:11689`) からのみ到達する — **死にコードに近い**

> 判断ルール:
> 1. **2 階層を潰さない** — 発散方針 (3 種) とレンズ (経路ごとに 3 種) を 1 つの enum に畳まない
> 2. **enum 値は「3 者一致検査が成立する形」を優先する** — schema・ハンドラ・
>    `prompts/conversation/orchestrator.md` の 3 者に同じ値集合が書けること (BE-8。CV-D13 / §4.6)
> 3. **PoC で挙動を変えなかった値を惰性で残さない** — `balanced` / `intra_industry_novel` は
>    「残す / 廃止する」を明示的に判定する (DR-1: 「PoC にあるから」を理由にしない)
> 4. **`LENS_META` の「主軸」4 種は採らない** — v4 の生きた経路を通らない (死んでいるコードを手本にしない)
> 5. **enum を変える場合は D-6 の Agent 再発行が発生する**。`operations.md` §5.2 の手順と
>    [schedule-2026q3.md](../../schedule-2026q3.md) の H-3 停止点に対応づける
> 6. **tool の本数を増やさない方向を既定とする** (CV-D5 の足切り基準)。増やす場合は
>    `scripts/check-endpoint-mapping.sh` の検査⑤ の期待値を同じ差分で更新する (DR-9)

[Answer]: **設計書 ([conversation.md](../../../docs/design/API/conversation.md) §4.1) で確定する** (上記 6 つの判断ルールに従う)。

## PV-Q7. v2 の CSV 列と説明文列 (新規性 / ミッション整合性) の扱い

**背景 (事実)**: [ideas.md](../../../docs/design/API/ideas.md) §2.6 の CSV は **16 列**で、
そのうち 4 列が廃止軸に紐づく — 9 列目「新規性」(`uniqueness`) / 10 列目「ミッション整合性」(`mission_alignment`) /
12 列目「新規性スコア」/ 13 列目「ミッション整合性スコア」。
同節は「**本表の行数が列数の定義元**」と宣言し、**v2 の列ずれバグを v3 で是正する**決定 (16 列すべてに値を書く) と
**リリースノート告知**を含む。PV-Q3 の承認は「軸としての廃止」に限られ、列の廃止を含まない。

> 判断ルール:
> 1. **既定は「16 列のヘッダ集合を維持する」** — C-16 は出力の消失も対象にする。
>    3 軸のサブ基準 (優位性の「技術的優位性」など) へ意味的に吸収できるなら、**列名を保ったまま中身を差し替える**
> 2. **列名を変える / 列を減らす案を採る場合は、変更前後の対応表を §2.6 に置き、
>    リリースノート告知 (同節の決定 4) の対象に加える**
> 3. **列を減らす案はユーザー承認を別途取る** — PV-Q3 の承認範囲外である。
>    承認が取れるまでは①の維持案を採る (設計を止めない)
> 4. **列数を変える場合は「本表の行数が列数の定義元」との整合を保つ**。
>    件数を別文書へ転記しない (DR-9)
