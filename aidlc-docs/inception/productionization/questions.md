## Q-1. データモデルの統合方針 (最重要)

PoC と v2 の双方に themes / assets / ideas / 企画書 が存在する (ギャップ G-4)。

- **A. v2 の既存テーブルを拡張して統合する** — 既存データ・既存機能を活かす。移行と後方互換が重い
- **B. v3 用の新テーブル群を追加し、v2 とは参照 (account_id 等) で連携する** — 独立性が高い。二重管理のリスク
- **C. 新システムとして分離し、v2 から段階的に移行する** — クリーンだが移行コスト最大
- E. Other

> 推奨: **B** (新テーブル + 参照連携)。理由: PoC の会話型フローはデータ構造が v2 と大きく異なり
> (台帳・版管理・機能ツリー)、A は既存テーブルへの破壊的変更を伴う。B なら既存 v2 機能を止めずに
> 出せて、統合は後から段階的に選べる。ユーザー・アカウント基盤だけは v2 を共有する。

[Answer]:検討中

### 判断材料 (Q-5=C の回答を受けて。2026-07-28 追記)

**Q-5 で「C. 既存機能を置き換える全面切替」が選ばれたことで、選択肢の意味が変わった**。
全面切替 = v3 が v2 を置き換える前提なので:

| 案 | 全面切替との相性 | 効いてくる点 |
|---|---|---|
| A. v2 テーブルを拡張 | **○** | 既存データがそのまま使える。切替時のデータ移行が不要。ただし v3 backend が v2 の DB を直接触る形になり、リポジトリを分けた (Q-2=A) 意味が薄れる |
| B. 新テーブル + 参照連携 | **△** | 併存前提の案。全面切替なら「併存のための二重管理」がコストだけになる。**切替時に既存データの移行が必須** |
| C. 新システムとして分離・段階移行 | **○** | 全面切替の素直な形。移行スクリプトとデータ移行期間の設計が要る |

> **推奨を B → C に変更する**。理由: Q-5=C (全面切替) を前提にすると、B の利点 (併存できる) が
> 消え、欠点 (二重管理 + 結局あとで移行) だけが残る。C なら v3 のスキーマを制約なく設計でき、
> 移行は「一度だけの ETL + 切替」に集約できる。
> **ただし A も有力** — 既存データ量が多く、移行のダウンタイムを避けたい場合は A が現実的。
> **判断に必要な追加情報**: v2 本番の既存データ量 (themes / ideas / business_plans の件数) と、
> 切替時にどこまでのデータを引き継ぐ必要があるか (全件か、直近のみか、引き継がないか)。

## Q-2. リポジトリ構成

[design_memo.md](../../../docs/design/design_memo.md) で FE = **Next.js on Vercel**、BE = Go / AWS ECS と指定されている
(= v2 frontend への相乗りではなく、独立したデプロイ単位)。その前提でのリポジトリ分割:

- **A. v3 用に backend / frontend / infra の 3 リポジトリを分ける**
- **B. v3 用のモノレポ 1 つ (backend/ frontend/ infra/)**
- **C. backend + infra を 1 リポ、frontend を別リポ (Vercel 連携の単位で切る)**
- E. Other

> 推奨: **C**。理由: Vercel は 1 リポ = 1 プロジェクトの連携が素直で、FE のデプロイ単位と一致する。
> 一方 backend と Terraform はデプロイ順序 (インフラ → アプリ) が連動するため同居が扱いやすい。
> B (モノレポ) は CI の条件分岐が増え、Vercel のビルド対象指定も追加設定が要る。

[Answer]:A

[Answer 2]: (2026-08-03) **方針転換 — A を撤回し、D を採用する** (ユーザー決定)。

- **D. app モノレポ 1 つ (`backend/` + `frontend/` + `api/`) + infra リポ 1 つ = 計 2 リポジトリ**

**採用理由 (3 点)**:

1. **モノレポの利得は「BE→FE の契約ドリフトが 1 PR / 1 CI で検出できる」ことに集中しており、その契約 (OpenAPI) は
   A のままでは穴が残っていた** — 出力先が設計で確定しておらず、リポ間の受け渡し方法も未設計だった
   (**旧版** `templates/backend-repo/STRUCTURE.md` §5 の
   「OpenAPI 定義の出力先は設計で確定していないため、ディレクトリを作っていない」= コミット `0448a12` 時点。
   **現行の [../../../templates/app-monorepo/backend/STRUCTURE.md](../../../templates/app-monorepo/backend/STRUCTURE.md)
   は本判断の結果として「OpenAPI 定義の出力先 (2026-08-03 に確定)」に書き換わっており、当該文字列は無い** —
   方針転換の根拠は**転換前の状態**なので、現行ファイルを引用すると正反対に読める)。
   FE/BE 同居 + `api/openapi.yaml` を契約の SSOT にすることで、再生成漏れを CI の必須チェックで機械的に閉じられる
2. **1 機能の変更が 3 リポに跨るとき PR が 3 本になる代償** ([../../../templates/README.md](../../../templates/README.md)
   の「3 分割の代償」) のうち、**FE/BE 跨ぎの分が消える**。順序の担保が人手 (issue の依存欄 + 横断完了判定) から
   1 PR の CI に移る
3. **infra だけは分離を維持する** — 理由は 2 点。
   ①**ライフサイクルの非対称性**: **infra は「PR マージ ≠ 反映」** (`apply` が人手ゲートで、
   `apply` 済みが app の着手条件。[../../../docs/design/infrastructure.md](../../../docs/design/infrastructure.md) §6.3 / §4.4) だが、
   app は PR マージで dev へ自動デプロイされる。同居させると「マージしたが未 apply の infra 変更」と
   「マージ = 反映済みの app 変更」が同一の `main` と同一の `gate` に混ざり、着手条件を PR 単位で表現できない。
   ②**AWS の変更権限を分けたい**: モノレポでは**書き込み権限をサブツリー単位で分けられない**
   (旧 A の却下案 (b) が挙げた「AWS 変更権限を分けにくい」がそのまま生きる)。

   > **⚠️ 訂正 (2026-08-05。design-reviewer 指摘 D-1)**: 当初ここに
   > 「**app と infra の間にはコード上の契約が無く (受け渡しは SSM / Secrets Manager 経由)、
   > 同居しても検査が増えない**」と書いたが、**これは誤りだった**。
   > `infrastructure.md` §4.2 のとおり **ecspresso が tfstate からクラスタ名 / subnet ID / SG ID /
   > ターゲットグループ ARN / シークレット ARN を解決する契約が実在する**。
   > **「契約が無い」と書かれた契約には誰も検査を設計しない**ため、
   > この契約は [../../../docs/design/architecture.md](../../../docs/design/architecture.md) §3.11.4 の
   > 残課題として起こし直した (対処 = `ecspresso verify` をデプロイ前に必須化)。
   > **なお分離の判断そのものは①②で成立するため、結論は変わらない**

**却下した案**:

- **A (backend / frontend / infra の 3 分割。旧回答)**: 上記 1・2 の理由で撤回。
  OpenAPI の受け渡しを新規に設計する必要があり、その設計コストがモノレポ化のコストを上回らない
- **B (backend / frontend / infra を全部 1 リポ)**: 上記 3 の理由で却下。`apply` の人手ゲートと
  app の CI を同居させる設計を追加で作り込む必要がある
- **C (backend + infra を 1 リポ、frontend を別リポ。旧推奨)**: BE→FE の契約がリポを跨いだままなので、
  モノレポ化の主目的 (利得 1) を満たさない

**旧 A の却下理由 (「CI の条件分岐と Vercel のビルド対象指定が増える」) は事実として残るため、
省略ではなく機構として明示設計で受ける** — **MR-1〜MR-6 の 6 機構**と「サブツリー自己完結」原則が実体。
**SSOT は [../../../docs/design/architecture.md](../../../docs/design/architecture.md) §3.11**
(本節に機構表を複製しない)。

## Q-3. 移植スコープ (第 1 増分)

PoC の機能のうち、本番化の第 1 弾に含める範囲。

- **A. 会話型アイデア創出フロー (`/api/conversation` + 9 tools) のみ**
- **B. 会話型 + アセット管理 (登録・抽出・機能ツリー)**
- **C. PoC 全機能 (テーマ管理・発散・評価・企画書・アセット)**
- E. Other

> 推奨: **A**。理由: 会話型フローは PoC で最も新しく、v3 プロトタイプ (Chat + Artifact) の中心。
> 単独で価値が出せる最小単位であり、認証・テナント・計測の本番基盤をこの範囲で作り込んでから
> 横展開する方が、全機能同時移植より事故が少ない。アセットは参照 (list/load) のみ先行対応する。

[Answer]:検討中

### 判断材料 (Q-4 / Q-5 の回答を受けて。2026-07-28 追記)

**Q-5=C (全面切替) と Q-4 (Dify 廃止) により、「第 1 増分のスコープ」と「最終的な移植範囲」を
分けて考える必要が出た**。全面切替の対象は最終的に v2 の全機能だが、それを 1 回で出すかは別問題。

| 案 | 全面切替までの道のり | リスク |
|---|---|---|
| A. 会話型のみ | 第 1 増分は小さく、本番基盤 (認証・計測・デプロイ) を確実に作れる。ただし**切替は複数回**になり、その間 v2 と v3 が並走する | 並走期間の運用が二重になる |
| B. 会話型 + アセット | アセットは会話フローが `list_assets` / `load_asset` で参照するため、**どのみち読み取りは必要**。登録・抽出まで含めると増分が 2 倍程度に | 中 |
| C. PoC 全機能 | 1 回で切り替えられる。**ただし PoC 59 ハンドラ + FE 296 ファイル相当を 4 層で書き直す**規模 | 最大。認証・テナント・計測を全機能分同時に作り込むことになる |

> **推奨は A のまま**。理由: 全面切替が目的でも、**最初のリリースで全部を切り替える必要はない**。
> 認証・テナント境界・LLM 計測・デプロイという「土台」を会話型 1 本で作り切ってから横展開する方が、
> 全機能を同時に本番品質へ引き上げるより確実。並走期間の運用コストは、
> Q-9 (Dify 廃止の移行方針) で「v2 に残す機能」を決めれば限定できる。
> **判断に必要な追加情報**: 全面切替の目標時期。時期が近いなら B/C を検討する必要がある。

[Answer 2]:(2026-07-29) リリースの進め方が確定: **まず dev 環境を構築する (アプリ開発と並行してインフラ先行)。アプリがある程度動くようになったら順次 dev へ上げてテストする。本番リリースは全部開発し終えてから 1 回で行う** (= 本番への段階リリースはしない。dev への継続デプロイで検証する)。

### 回答の含意 (2026-07-29 追記)

- **本番切替は 1 回**なので、案 A の弱点だった「v2/v3 並走期間の二重運用」は発生しない
- 代わりに案 C の注意点「全機能を同時に本番品質へ」が残る — これは **dev への継続デプロイで機能単位に検証を積む**ことで緩和する (開発順序は認証・テナント・計測の土台 → 会話型 → 横展開、を維持)
- **インフラ (Terraform + ecspresso の dev 環境) が最優先タスクになる** — Task-3e (infrastructure.md) を前倒し
- 残る確認: 「全部」の範囲 = v2 既存機能 (アイデア・企画書・リサーチチャット等) の移植まで含めてから切替か、PoC 由来機能が揃った時点で切替か → [Answer 3] へ

[Answer 3]:(2026-07-29) **(b) — 第 1 リリースの「全部」= PoC 由来の新機能セット (テーマ・アセット・会話型アイデア創出)。v2 既存機能の移植完了を待たずにリリースし、v2 とは併用期間を設ける** (ユーザー発言「v2 とは併用の期間が発生すると思います」)。**v2 既存機能は併用期間中に順次 v3 へ移植し、完了後に v2 を廃止する**

## Q-7. IaC の範囲と v2 インフラとの関係

[design_memo.md](../../../docs/design/design_memo.md): 「全部 IaC でやりたい / Terraform?」。
一方 v2 は ecspresso + タスク定義 JSON (`hassan-v2-backend/stacks/prod/ecspresso.yml`) で
**サービス定義のみ**をコード化している。

- **A. Terraform で全て管理する** (VPC / RDS / ECS サービス / IAM / Secrets)。ecspresso は使わない
- **B. Terraform で基盤 (VPC / RDS / IAM / ECS クラスタ)、アプリのデプロイは ecspresso** (v2 と同じ手触りを残す)
- **C. v2 のインフラごと Terraform に取り込み、v2 / v3 を同じ IaC で管理する**
- E. Other

> 推奨: **B**。理由: 「全て IaC」の要求は基盤を Terraform 化すれば満たせる。デプロイ (タスク定義の
> 差し替え) を Terraform で回すと、アプリのリリースのたびに plan/apply が必要になり CD が重くなる。
> C は v2 の稼働中インフラの import が必要で、本番化の初期スコープを大きく超える。
>
> **前提の欠落**: 必要なインフラ構成要素の一覧が未確定 (memo の TODO)。この回答の前に
> VPC / ALB / RDS / Secrets / CloudWatch / WAF 等の要否を確認する必要がある。

[Answer]:ecspressoとは何か

### 解説: ecspresso とは (2026-07-28 追記)

**ECS へのデプロイ専用の小さな CLI ツール** (OSS)。「ECS のサービス定義とタスク定義を JSON で
リポジトリに置き、`ecspresso deploy` で反映する」だけのもの。v2 が使っている
(`hassan-v2-backend/stacks/prod/ecspresso.yml` + `ecs-task-def.json` + `ecs-service-def.json`)。

| | ecspresso | Terraform |
|---|---|---|
| 守備範囲 | **ECS のサービス/タスク定義のみ** | AWS 全リソース (VPC / RDS / IAM / ALB / Secrets …) |
| 主な用途 | **アプリのリリース** (新イメージへの入れ替え) | **インフラの構築・変更** |
| 実行頻度 | デプロイのたび (1 日に何度でも) | インフラを変えるときだけ |
| 状態管理 | 無し (AWS の現状に対して差分適用) | tfstate ファイルで管理 |

**なぜ両方を使う案 (推奨 B) があるのか**: Terraform でアプリのデプロイまで回すと、
リリースのたびに `terraform plan/apply` が必要になる。tfstate のロック待ちが発生し、
インフラ変更とアプリリリースが互いをブロックする。そのため
**「インフラ = Terraform / アプリのリリース = 別の仕組み」**と分けるのが一般的。

ただし ecspresso は必須ではない。代替:

| 代替 | 内容 | 向き |
|---|---|---|
| ecspresso | 専用 CLI。v2 で実績あり | v2 と運用を揃えたい場合 |
| GitHub Actions の公式アクション | `aws-actions/amazon-ecs-deploy-task-definition` を使う。ツール追加不要 | 依存を増やしたくない場合 |
| AWS CodeDeploy | Blue/Green デプロイが要る場合 | 段階的切り替えが必要な場合 |

**「全部 IaC」は Terraform で基盤を管理すれば満たせる**。アプリのリリース手段はその外側の話。

> 推奨 (再掲・更新): **B**、ただし ecspresso にこだわらず
> **「Terraform = 基盤 / GitHub Actions の ECS デプロイアクション = アプリのリリース」**でよい。
> 新規構築で v2 の運用を踏襲する理由が薄いなら、ツールを 1 つ減らせる。

[Answer 2]:今はespressoを使用しているのか

### 回答: v2 は現在 ecspresso を使っている (2026-07-28 実測)

**使っている**。v2 のデプロイは GitHub Actions から ecspresso を呼んでいる:

| 事実 | 出典 |
|---|---|
| GitHub Actions で ecspresso をセットアップ | `hassan-v2-backend/.github/workflows/dev-deploy.yml:59` (`uses: kayac/ecspresso@v2`) |
| dev へのデプロイ実行 | `hassan-v2-backend/.github/workflows/dev-deploy.yml:65` (`ecspresso deploy --config=stacks/dev/ecspresso.yml`) |
| prod へのデプロイ実行 | `hassan-v2-backend/.github/workflows/prod-deploy.yml:23` / `:29` |
| 設定 (cluster / service / 定義ファイル) | `hassan-v2-backend/stacks/prod/ecspresso.yml` (cluster・service とも `hassan-v2-api`) |

**v2 の現行デプロイフロー** (`dev-deploy.yml` を読んだ結果):

```
main へ push
  → タグ生成 (日付 + short hash)
  → jq で stacks/{dev,prod}/ecs-task-def.json の image タグを書き換え、
     **その変更をリポジトリにコミット & push**
  → docker build → ECR へ push
  → ecspresso deploy (タスク定義を適用してローリング更新)
```

**注意点** (v3 で踏襲するか判断が要る箇所): このフローは **CI が自分のリポジトリにコミットを push する**
(image タグの記録)。履歴にデプロイ用コミットが混ざり、`main` の保護ルールとも噛み合いにくい。
GitHub Actions の ECS デプロイアクションを使う場合、タスク定義はレンダリングするだけで
コミットしない構成が一般的。

> つまり Q-7 は「**v2 の運用 (ecspresso + task-def をコミット) を踏襲するか、
> 新規構築を機に GitHub Actions 標準のデプロイに寄せるか**」の選択です。
> 推奨は後者 (Terraform 基盤 + GitHub Actions のデプロイアクション) — ツールが 1 つ減り、
> デプロイ用コミットも不要になる。ただし**チームに ecspresso の運用ノウハウが既にある**なら、
> 踏襲した方が学習コストは低い。

[Answer 3]:B — **Terraform 基盤 + ecspresso** (2026-07-29 確定)。役割分担: Terraform = 基盤 (VPC / ALB / RDS / IAM / Secrets / ECS クラスタ)、ecspresso = ECS サービス定義 + タスク定義 + リリース (tfstate 連携で Terraform 側リソース ID を参照)。採用理由: サービス定義 (desiredCount / ヘルスチェック / LB 紐付け) をコードで一元管理でき、`diff` / `rollback` の運用コマンドが標準で得られ、v2 の運用経験も活かせる。ただし **v2 の「イメージタグを自リポジトリへ commit する」運用は廃止**し、CI 内でタスク定義をレンダリングする。v2 稼働中インフラの Terraform import は行わない (全面切替で v2 は廃止予定・IaC 資産ゼロのため新規構築)

## Q-8. 環境戦略とリリースの切り分け

[design_memo.md](../../../docs/design/design_memo.md): 「Dev と Prod」「開発環境に入っている修正を切り分けて
本番リリースできるようにしたい」「DB 更新を自動化できないか」。

- **A. trunk-based + フィーチャーフラグ** — main を常時リリース可能に保ち、未完成機能はフラグで隠す。
  DB マイグレーションはデプロイパイプラインで自動適用 (前方互換な変更のみ)
- **B. リリースブランチ運用** — dev ブランチ → release ブランチ → prod。DB 適用は承認付き手動
- **C. 環境ごとにブランチを固定** (dev ブランチ = dev 環境、main = prod)。DB 適用は環境ごとに手動
- E. Other

> 推奨: **A**。理由: 「開発環境の修正を切り分けて本番に出す」の最も確実な解はブランチ運用ではなく
> **フラグによる分離**。ブランチ分岐で切り分けると、cherry-pick 漏れとマージ衝突が恒常的に発生する。
> DB は「前方互換なマイグレーションのみ自動適用 / 破壊的変更は 2 段階リリース」で自動化できる。

[Answer]:フラグはどこにどうやってつけるのか

### 解説: フィーチャーフラグの実体 (2026-07-28 追記)

**「この機能を今このユーザーに見せるか」を、コードを変えずに切り替えるスイッチ**。
実体は「設定値を読んで if で分岐する」だけで、特別な技術ではない。**どこに置くか**で 3 段階ある:

| 方式 | 実体 | 切り替え方 | 向き |
|---|---|---|---|
| **① 環境変数** | ECS タスク定義 / Vercel の環境変数に `FEATURE_CONVERSATION=true` | 値を変えて**再デプロイ** | 最小構成。環境 (dev/prod) 単位で ON/OFF するだけなら十分 |
| **② DB テーブル** | `feature_flags` テーブル (flag 名 / 有効 / 対象アカウント ID) を読む | 管理画面か SQL で**即時**切り替え | **アカウント単位の限定公開**ができる。今回の Q-5 のような段階開放向き |
| **③ SaaS** | LaunchDarkly 等 | 管理 UI から即時 | 大規模・多数のフラグを扱う場合。今回は過剰 |

**コードのどこに書くか** (4 層のどこか):

```
Controller  … ルーティングの有効化。フラグ OFF なら 404 を返す      ← 機能まるごとの ON/OFF
UseCase     … 分岐したい処理の直前で判定                            ← 挙動を差し替える場合
Service     … 使う LLM プロバイダの切り替え等                       ← 実装の差し替え
FE (Next.js)… メニュー・ボタンの表示可否                            ← 導線を隠す
```

**FE と BE の両方に要る**のがポイント。FE だけ隠すと API は叩けてしまい、
BE だけ塞ぐと画面にボタンが出て 404 になる。**判定の正は BE**、FE は「導線を隠すだけ」と決めると、
フラグの二重管理が事故になりにくい (FE は `/api/features` のような 1 本の API で
有効フラグ一覧を受け取る形が扱いやすい)。

**Q-5=C (全面切替) を選んだ場合との関係**: 全面切替なら「段階開放のためのフラグ」は不要に見えるが、
**未完成機能を main に入れたまま本番に出さない**目的では依然として要る
(= design_memo の「開発環境に入っている修正を切り分けて本番リリースしたい」への直接の答え)。
その用途なら **① 環境変数で十分**で、DB テーブルは不要。

> 推奨 (再掲・更新): **A (trunk-based + フラグ)**。フラグは
> **① 環境変数方式から始める** (ECS タスク定義 / Vercel の env)。
> アカウント単位の限定公開が必要になった時点で ② DB テーブルへ移行する。

[Answer 2]:ちょっと検討したい (未確定。暫定既定は推奨案 A = trunk-based + 環境変数フラグ)

## Q-9. Dify 廃止の移行方針 (Q-4 の回答から派生。2026-07-28 追加)

Q-4 の回答「**Dify は廃止**。エージェントにしたいところは Managed Agent、不要なところは既存 API 使用
(使用モデルは見直し)」を受けて、v2 側の Dify 依存をどう扱うかを決める必要がある。

**実測 (2026-07-28)**: v2 の Dify 依存は `hassan-v2-backend/dify` の 9 ファイル
(`business_plan.go` / `chatbot.go` / `research_chat.go` / `idea.go` / `extract_asset_titles.go` /
`generate_asset_descriptions.go` / `comany_info_from_url.go` / `client.go` / `extract_json.go`) と
`workflow` ディレクトリ。参照しているのは 14 ファイル (`hassan-v2-backend/usecase/business_plan`、
`hassan-v2-backend/usecase/idea`、`hassan-v2-backend/prompt/template.go` 等)。

**追い風となる事実**: v2 には既に LLM 抽象 (`hassan-v2-backend/llm`) があり、
**gemini / claude / openai / exa** の実装が存在する (`hassan-v2-backend/llm/factory.go`)。
= 「既存 API 使用」の受け皿は既にある。

- **A. v3 側で作り直す** — Dify 依存機能を v3 の 4 層 + Managed Agent / llm パッケージで再実装し、v2 は停止
- **B. v2 に残したまま、Dify 呼び出しだけ `llm/` 経由に差し替える** — 機能はそのまま、LLM 基盤だけ置換
- **C. 機能ごとに振り分ける** — 会話・エージェント性のあるもの (research_chat / chatbot / business_plan) は
  v3 で Managed Agent 化、単発変換 (extract_asset_titles / generate_asset_descriptions /
  company_info_from_url) は v2 に残して `llm/` へ差し替え
- E. Other

> 推奨: **C**。理由: 単発の抽出・要約タスクにエージェントは不要で、v3 へ移す価値も薄い
> (`llm/` への差し替えは 1 ファイル単位で完結し、リスクが小さい)。一方、対話・生成の中核は
> v3 の会話フローと重複するため、v3 側に寄せた方が二重実装を避けられる。
> A は Dify 廃止と v3 移行を同時にやることになり、切り替え時のリスクが最大化する。

[Answer]:A — v3 で全部作り直す

### 回答の含意 (2026-07-28 追記)

**A を選んだ結果、v3 のスコープは「PoC の会話型フロー」だけでは閉じない**。
v2 の Dify 依存機能 (企画書生成 / research_chat / chatbot / idea / アセット抽出系) も
v3 側で再実装する対象になるため:

1. **Q-3 (移植スコープ) の答えが実質的に狭まる** — 「会話型のみ」で第 1 増分を切っても、
   最終的な移植対象は「PoC 全機能 + v2 の Dify 依存機能」になる。
   増分計画 (plan.md) は最終形を見据えた順序で組む必要がある
2. **データモデル (Q-1) は最終形で決める必要性が上がる** — v2 の business_plans /
   research_chats 相当も v3 に来るため、第 1 増分だけを見たスキーマ設計だと 2 度目の移行が発生する
3. **切替のリスクが集中する** — Dify 廃止と v3 移行が同時になるので、
   機能単位の段階切替 (どの機能から v3 に寄せるか) を運用設計で明示する必要がある

## Q-10. 新規契約の作成経路 — 社内管理者向けの契約管理 API を本増分に含めるか (2026-08-25 追加)

**起票の経緯**: [auth-accounts.md](../../../docs/design/API/auth-accounts.md) §6.3 の仮定 2 は
「**契約 (`contracts`) と会社 (`companies`) の作成経路は移行スクリプトのみ**」と置き、同 §2.7 で
「契約の作成・削除 (v2 `hassan-v2-backend/router/router.go:219-221`) は**対象外**」と確定していた。
同じ仮定 2 が「**v3 で新規契約を獲得する運用が必要になると、社内管理者向けの契約作成 API
(v2 の `POST /admin/companies`) が本増分の対象に戻る**」と後続条件を明記している。
**2026-08-25 にオーナーが「新規契約を作る手段は必要」と判断し、この後続条件が発火した**。

**実装リポ hassan-v3 の現状** (2026-08-25 実測): `backend/db/queries/account/contract.sql` と
`company.sql` は Get / Update のみで **INSERT が 1 本も無い**。`backend/common/auth/whitelist.go` に
**`TierAdmin` の route が 0 本** (`POST /admin/signin` は公開系統) で、ミドルウェア `RequireAdmin` と
`admin_accounts` テーブルは実装済みだが**系統だけが未使用**。移行スクリプト
(`backend/cmd/migrate-from-v2`) も未実装のため、**製品内にも運用手順にも契約を作る手段が存在しない**。

- **A. 本増分に含める — 契約管理 4 本 (作成・一覧・詳細・更新) を `X-Admin-Token` 系統に追加する**
- **B. 含めない — 新規契約も移行スクリプト / 手動 SQL で投入する運用を続ける**
- **C. 最小 — 作成 1 本だけ追加する**
- D. Other

> 推奨: **A**。
> **B の却下理由**: 契約獲得のたびに人間が ECS RunTask か手動 SQL で本番 DB に INSERT することになる。
> 実装リポの `.claude/rules/04-human-checkpoints.md` §3.3 は「エージェントに prod の DB 接続情報を配らない」を
> 担保の中心に置いているが、**運用手順の側が恒常的に本番 DB への直接書き込みを要求する**形になり、
> 承認機構 (H-2) の外側に書き込み経路が常設される。
> **C の却下理由**: 作成だけでは**作った契約を製品内で確認する手段が無い**。一覧が無いと投入の成否を
> 本番 DB を見に行って確かめることになり、`feedback_review_patterns.md` の **BE-10 (読む側と書く側を
> 対で設計する)** と同型の穴になる。v2 も `GET /admin/companies` を持っていた
> (`hassan-v2-backend/router/router.go:215`)。

[Answer]:(2026-08-25) **A**。下表の 9 点もすべて推奨どおりで確定。

### A の付随決定 (回答と同時に確定した 9 点)

| # | 決めたこと | 確定 | 根拠 / 却下案 |
|---|---|---|---|
| 1 | エンドポイントの範囲 | **`POST` / `GET /admin/contracts`・`GET` / `PUT /admin/contracts/{contract_id}`** | v2 の `/admin/companies` を踏襲しない — v3 で作る主体は `contracts` で `companies` は従属して作られる (下の 3)。v2 のパス名は会社と契約を同一視しており、契約内ユーザー向けの `GET /company` と紛らわしい |

| 3 | `companies` 行を同時に作るか | **同一トランザクションで作る** (会社名を作成の必須項目にする) | 作らないと `PUT /company` が 404 のままで会社情報を保存できない。**AA-D-14 が upsert を却下した根拠 (行が無い = 移行の失敗として観測する) は変えない** — 行を作るのは契約作成 API だけ、という形を維持する |
| 4 | 代表者への招待メール | **送る** (v2 と同じ) | ただしリンクの形は v2 と別物 — v3 は平文を保存せず `token_hash` で引き、参照は `POST /accounts/signup-links/lookup` (AA-D-4 / AA-D-5)。実装リポの既存部品 (`usecase/account/create_signup_link.go` / `sign_up.go`) を流用できる |
| 5 | `signup_links.contract_id` | **作成した契約の ID をそのまま入れる** | DM-A4 = B で `NOT NULL` + FK が確定済み。同一トランザクション内なので解決できる |

### 回答の含意 (2026-08-25 追記)
