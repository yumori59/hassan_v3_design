## 1. 目的とスコープ

PoC (`claude_managed_agents`) で検証済みの価値を、**認証・テナント分離を備えた本番システム**として
提供する。本リポジトリ (hassan_v3) のスコープは**設計・仕様・移行計画の確定**であり、
実装は別リポジトリで行う。

**スコープ外**: 実装コード、インフラの実構築、v2 既存機能の改修
(ただし v3 と接続する境界の設計は含む)。

## 3. 非機能要件 (確定)

`.claude/rules/08-production-gates.md` の 3 領域を本番化の必須要件として扱う。
**「PoC では対象外だった」を省略の理由にしない**。

### 3.1 認証・テナント分離・権限 (A)

- **AC-1.1** v3 の API エンドポイントは、**公開エンドポイントのホワイトリストに明示列挙されたものを除き**、
  すべて認証ミドルウェア (v2 の `AuthRequiredMiddleware` 相当を v3 で実装) を通り、
  未認証リクエストを 401 で拒否する設計であること。
  **ホワイトリストは「パス → 要求する認証系統 (公開 / ユーザー認証 / 社内管理者認証 / 社内管理者認証 (MFA 未検証で可))」の宣言として
  1 箇所で管理され、ルート定義と宣言の系統単位の一致が機械的に検査される**こと
  (`docs/design/auth.md` §6.7)。**「認証あり / なし」だけの検査では不十分** —
  社内管理者向け API がユーザー認証グループに登録された場合を検出できない
  (全契約横断の操作が契約ユーザーに開く)。
  ※ 認証系 API を v3 で実装する決定 (同 §9.3 Q-A8) により、v3 は `signin` / `signup` /
  パスワードリセット等の**本質的に未認証のエンドポイントを持つ**。「すべてが認証を通る」という
  表現では判定できないため、ホワイトリスト方式での判定に改めた
- **AC-1.2** v3 が新規に持つ**機能テーブル**は所有者列 (`account_id` = 個人 / `contract_id` = 契約) を
  **1 段で**持ち、**どちらの境界かがテーブル定義から一意に読める**こと。
  **例外は `docs/design/auth.md` §6.3 の有限の列挙に限り、列挙外のテーブルに所有者列が無い状態が
  機械検査で検出される**こと。取得・一覧・更新・削除のクエリ条件に所有者が入る設計であること
  (**読み取り系は `Get*` / `List*` / `Count*` / `Search*` すべてが検査対象。例外は同 §6.4 の
  許可リストに限る**)
- **AC-1.3** **LLM custom tool の実行が、呼び出しユーザーの所有者スコープでのみデータへ到達する**
  設計であること。LLM が渡した ID の所有者不一致は「該当なし」として扱い、
  エラー内容から他テナントのリソース存在を推測できないこと
- **AC-1.4** 401 / 403 / 404 / **429** の使い分けが API 設計書に一覧化されていること
- **AC-1.5** **JWT 署名鍵の管理とトークン失効手段**が定義されていること: 鍵の保管先、
  **ローテーション方式** (実行してもサービスが止まらないこと)、**v2 の既存鍵を継承する場合の前提**、
  および**トークン漏洩時に対象アカウントを即座に遮断する手段**。
  「有効期限が切れるのを待つ」以外の失効経路が設計上存在すること
- **AC-1.6** **認証エンドポイント (未認証で叩ける経路) の濫用対策**が定義されていること:
  メールで送る秘密文字列を**暗号論的乱数で生成**すること、アカウントの存在有無を
  **応答から判別できない**こと、**レート制限**の実装層と超過時の応答、
  および**制限の発動を観測できる**こと。
  **各対策の実装先 (v2 / v3) が明示されていること** — 実装先の無い対策は設計として未完成とみなす

### 3.2 可観測性・LLM コスト (O)

- **AC-2.1** **すべての LLM 呼び出し経路**でモデル・入出力トークン・所要時間・`stop_reason`・
  ツール呼び出し回数が記録される設計であること (経路ごとの実装ではなく共通層で行うこと)
- **AC-2.2** アカウント単位・セッション単位の**コスト集計**と、**アラートのしきい値・通知先**が
  定義されていること (C-12 により**課金上限による拒否は設けない**)。
  併せて**暴走の安全弁** (1 セッションあたりのツール呼び出し回数・トークン・実行時間の打ち切り) が
  定義されていること — これはコスト制限ではなく、無限ループを止めるための機能要件
- **AC-2.3** LLM 起因の失敗 (JSON パース失敗・`max_tokens` 切り詰め・ツール引数の不整合・
  タイムアウト) が警告として観測可能で、握り潰されない設計であること
- **AC-2.4** 構造化ログにリクエスト ID / アカウント ID / セッション ID が含まれること
- **AC-2.5** 生成・削除操作の監査記録の方針が定義されていること

### 3.3 CI/CD・デプロイ・IaC (D)

- **AC-3.1** local / dev / prod の 3 環境と、環境別設定・シークレットの受け渡し方法が定義されていること。
  **PoC の `.env` 自動書き換え方式を採らないこと**
- **AC-3.2** PR で機械強制する CI ゲート (build / vet / test / 型 / lint / 生成物の再生成漏れ) が
  定義され、実装リポの雛形に反映されていること
- **AC-3.3** **Managed Agent の発行・更新がデプロイ手順に組み込まれている**こと。
  system prompt / tool schema の変更がコードだけ先行してデプロイされない仕組みがあること
- **AC-3.4** DB マイグレーションの方式・適用タイミング・後方互換・ロールバック手順が定義されていること
- **AC-3.5** **全面切替 (C-11 / C-15) の手順**が定義されていること: **dev 先行構築 → dev への継続デプロイ → 本番一括切替**の各段階の完了条件を含め、 既存 v2 データの移行方式・
  切替時のダウンタイム有無・切り戻し手順・切替前後で参照が壊れないことの確認方法
- **AC-3.8** **Dify 廃止 (C-9) の移行手順**が定義されていること: v2 の Dify 依存機能ごとの
  **v3 での実装形態** (Managed Agent / 直接 LLM API / 廃止) — C-13 により v2 側に残す選択肢は無い —、
  **使用モデルの見直し結果**、機能単位の切替順序、切替時の品質確認方法
- **AC-3.6** AWS インフラ構成要素 (VPC / ALB / ECS / RDS / Secrets / ログ・監視) が洗い出され、
  **IaC の管理範囲と、範囲外にする場合の理由**が定義されていること (C-7)
- **AC-3.7** **開発環境の未リリース変更を本番に出さずに済む仕組み** (ブランチ運用またはフィーチャーフラグ) と、
  **DB マイグレーションの自動適用範囲** (自動適用してよい変更 / 手動承認が要る変更の区別) が定義されていること

### 3.4 アプリ構造・開発手法 (C-5 / C-8)

- **AC-5.1** 4 層 (Controller → UseCase → **Service** → Repository) **+ `entity/` / `gateway/` の計 6 パッケージ層**の
  **責務境界と禁止依存**が定義され、代表ユースケース 1 本で「どの処理がどの層に置かれるか」が
  具体例として示されていること (C-5)。**禁止依存は依存規則 L-1〜L-6 として具体化する**
  ([requirements-layering.md](requirements-layering.md) §4。AC-6.2 / AC-6.3 / AC-6.4 / AC-6.5 が詳細化する)
- **AC-5.2** 実装リポジトリのハーネス (CI ゲート・pre-commit・エージェント定義) が
  TDD と lint 強制を機械的に担保していること (C-8)

### C-13 (Dify 依存機能を v3 で作り直す) の含意 — Q-3 との関係

C-13 + C-11 (全面切替) により、**v3 の最終的な移植範囲は「PoC 全機能 + v2 の Dify 依存機能」**になる。
Q-3 (第 1 増分のスコープ) が「会話型のみ」でも、それは**増分の切り方**であって最終範囲ではない。

設計上の帰結:

1. **データモデル (§5 / Q-1) は最終範囲を見据えて決める** — 第 1 増分だけを見たスキーマだと、
   企画書 / research chat 相当を後から載せる際に 2 度目の移行が発生する
2. **機能単位の切替順序を運用設計に含める** (AC-3.5 / AC-3.8) — 全面切替は一度に起きるのではなく、
   「機能ごとに v3 へ寄せていき、最後に v2 を止める」形になる
3. **v2 に残す機能はゼロが前提** — 並走期間中は v2 が稼働し続けるが、
   Dify 依存部分に手を入れる (差し替える) 選択肢は採らない

なお C-5〜C-8 ([design_memo.md](../../../docs/design/design_memo.md) 由来) と C-9〜C-12 (Q 回答由来) は
推奨案ではなく**ユーザー指定の確定制約**として扱う。

### C-12 (コスト上限なし) についての注記

上限を設けない判断はユーザー決定として設計に反映する。設計側で担保するのは次の 2 点:

1. **可視化とアラート** — アカウント/セッション単位の集計、しきい値超過の通知 (AC-2.2 / O-7)
2. **暴走の安全弁** — 1 セッションのツール呼び出し回数・トークン・実行時間の打ち切り。
   これは課金制限ではなく**無限ループ対策**であり、上限なし方針とは独立に必須
   (PoC の会話フローは LLM がツールを繰り返し呼ぶ構造のため、打ち切りが無いと停止条件が LLM 任せになる)
