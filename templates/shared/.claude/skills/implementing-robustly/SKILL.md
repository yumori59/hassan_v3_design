# 堅牢な実装 (着手前の影響半径測定と完了前セルフレビュー)

## Overview

実装の品質は「書いたコードが正しいか」だけでは閉じない。**変更の影響半径を着手前に測り、
完了前に diff を第三者の目で読み直す**。TDD・検証ゲート・平仄 (既存 rules / agent 定義) は
プロセスを保証するが、「どこまでが影響範囲か」「何をテストすべきか」の判断はこの skill が埋める。

最頻の失敗は **file-local 思考**: 変更したファイル内の関連には気づけるのに、
package 境界の外にある呼び出し元・保存済みデータへの影響を探索しないまま完了報告する。

## ステップ

### ① 着手前: 影響半径の測定 (file-local 思考の禁止)

コードを書く前に必ず:

1. **変更対象シンボルの全参照をリポジトリ横断で grep する** — 自パッケージ内だけで止めない
   (`grep -rn "SymbolName" --include="*.go"` / FE は `frontend/src` 全体)。
   呼び出し元それぞれに「この変更で挙動が変わって困るか」を 1 行で判断する
2. **永続データとの契約を確認する** — 変更する関数の出力が DB・ファイル・localStorage に
   保存されているか。**正規化キー・ハッシュ・dedup キー・シリアライズ形式は特に危険**:
   保存済みデータは旧ロジック産なので、新旧キーの突き合わせが起きる箇所で一致しなくなる。
   互換性影響は「気づいたら書く残課題」ではなく実装前の設計判断として扱う
3. **コード外の知識重複を列挙する** — tool schema ↔ Go handler ↔ prompt の 3 者一致 (BE-8)、
   既定値・hard cap の散在 (BE-2: コード/FE/prompts の 3 層)、README・CLAUDE.md の記述。
   1 箇所直したら全箇所直す
4. 類似既存実装を 1 つ精読して平仄を合わせる (agent 定義のとおり)

### ② テスト設計: 受入基準 + エッジケースの機械的列挙

Red のテストを書くとき、受入基準そのままに加えて次を機械的に舐める:
**空/nil/ゼロ値・境界値・処理済み入力の再入力 (冪等性)・異常系・並行/再実行・巨大入力**。
全部テスト化する必要はない — 舐めた上で「該当しない」と判断した項目はそれでよい。

### ③ 実装中

TDD (Red→Green)・平仄・エラーハンドリングは既存 rules と agent 定義が正。ここでは繰り返さない。

### ④ 完了前セルフレビュー: diff を通読する

報告を書く前に `git diff` を頭から読み直す:
消し忘れ (debug print・コメントアウト)、スコープ外の巻き込み変更、命名の一貫性、
レビュアー向け説明コメントの混入。**①で列挙した影響箇所が全て「対応済み」か
「残課題に記載」のどちらかになっているか照合する**。

### ⑤ 報告: 影響半径の調査結果を含める

検証ゲートの証拠 (①変更ファイル ②検証コマンドと結果 ③残課題) に加えて、
**①で見つけた影響箇所とその扱い (対応済み / 対象外と判断した理由 / 残課題) を報告する**。
呼び出し元を調べていないなら「調べていない」と書く — 調査済みのふりをしない。

## よくある間違い

| 間違い | 現実 |
|---|---|
| 変更したファイル内の関連だけ確認して完了 | 影響は package 境界を越える。リポジトリ横断 grep が先 |
| 「純粋関数の改善だから安全」 | 出力が保存されていれば旧データとの突き合わせで壊れる |
| 互換性影響を口頭確認もせず黙って完了報告 | 残課題に 1 行書くだけで統合後の手戻りが消える |
| 指示された検証コマンドだけ実行 | 影響半径が package 外に及ぶなら関連 package のテストも回す |
| diff を読み直さずそのまま報告 | 消し忘れ・巻き込みはセルフレビューでしか見つからない |
| エッジケースを「思いついた分だけ」テスト | ②の固定リストを機械的に舐める。抜けは網羅感の錯覚から生まれる |

## 実例 (本リポジトリ: NormalizeForDedup の全角正規化)

2026-07-05 のベースライン検証で、sonnet 実装エージェントは TDD・検証ゲート・
全角ハイフンを含める設計判断まで正しくこなしたが、**`NormalizeForDedup` の出力が
DB に保存されている事実 (`internal/db/asset_bulk_store.go` — asset_patents.patent_number は
正規化済み文字列を格納) を見落とした**。旧ロジックで保存済みのキーと新ロジックの
キーが一致せず、既存アセットとの重複検出が壊れる。同一ファイル内の関連
(`hasValidPatentFormat`) には言及できていた — 欠けていたのは「リポジトリ横断の参照 grep」の
1 手だけ。①-1/①-2 はこの再発防止。
