# 頻出バグ・設計欠陥パターン (SSOT)

このファイルが**頻出パターンの単一の正 (Single Source of Truth)**。
`rules/04-review.md` / `agents/design-reviewer.md` / `agents/architecture-designer.md` は本ファイルを参照する。
**重複コピーを各所に置かない** (更新時のドリフト防止)。

2 つのセクションからなる:

- **DR-x (設計レビュー)** — このリポジトリで発生する設計上の欠陥。レビューで検出したら追記する
- **BE-x / FE-x (PoC 由来)** — PoC で実際に起きたバグ。**本番設計で構造的に潰すべき既知の落とし穴**。
  「実装時に気をつける」ではなく「設計でその余地を無くす」観点で使う

| # | パターン | 検出観点 |
|---|---|---|
| DR-1 | **出典なしの断定** | PoC / v2 の挙動を「〜になっている」と書きながら パス:行 の出典がない。転記された誤認は実装リポまで運ばれる |

| DR-4 | **PoC 実装のコピー設計** | PoC のハンドラ構造 (net/http・手書き store・`http.Error` JSON) をそのまま本番設計に持ち込んでいる。本番は v2 規約 (3 層・sqlc/wire・`CodedError`) が正 |
| DR-5 | **曖昧語による実装者への丸投げ** | 「適切に」「必要に応じて」「後で検討」が判断ポイントに使われている。受入基準に落ちない記述は設計未完成 |
| DR-6 | **AC の宙吊り** | requirements の AC-ID が plan / 設計書のどこからも参照されていない (`make check-traceability` が検出)。逆に、設計判断に対応する AC が無い場合も要件漏れ 。**検査が「対象 0 件」を検査して緑になる形に注意** (2026-08-02 追加): `check-traceability.sh` の AC 抽出正規表現が `AC-[0-9]` 形式のみだったため、**増分ごとに名前空間を分けた `AC-CV-*` 39 件が 1 件も照合対象に入らないまま「全カバー」と表示されていた**。**新しい ID 体系を導入したら、検査がその ID を拾うかを故障注入で確かめる** (「検査が通った」は「検査が対象を見た」を意味しない。同型の穴は `feature` const の存在検査 = `observability.md` §4.2 にもある)。**さらに、新しい ID 体系は「既存の名前空間と衝突していないか」を導入時に grep で確かめる** (2026-08-04 追加): モノレポ機構に `M-1`〜`M-6` を振ったところ、**`M-x` は既に 4 つの名前空間** (`03-model-escalation.md` のモデル判定 `M-1`〜`M-4` / `llm-migration.md` の移送段 `M-0`〜`M-9` / `data-model.md` の `M-1`〜`M-20` / **過去レビューの Must-fix 連番**) **に使われていた**。衝突は「issue コメントや PR 本文の『M-1』がどの定義か判別できない」形で実害になり、**件数を機械照合しようとした瞬間に誤検知として露見した** (照合スクリプトが他名前空間の `M-x` を拾った)。`MR-x` へ改名して解決。**ID を新設する前に `grep -oE '<接頭辞>-[0-9]+'` で全リポを見る** |
| DR-7 | **プロトタイプを仕様として扱う** | `docs/prototype/*.html` の画面を根拠に仕様を確定している。プロトタイプは設計入力であって仕様ではない (実装されていない挙動が含まれる) |
| DR-8 | **修正の波及漏れ (自己申告の範囲だけ直す)** | 設計判断を変更したとき、**思考の対象になった節だけを直し、同じ事実に依拠する他の記述が旧版のまま残る**。auth.md のレビュー 4 巡で **3 回連続**発生 (①方針反転を §4/§5 に書いて §2/§6 が旧記述 ②AC-1.1 を改訂して AC-1.2 が旧前提 ③§6.3/§6.4 を改訂して §7 の回答表が旧記述)。**検出法**: 変更した主張のキーワード (「すべてのテーブル」「v2 再利用」「公開は `GET /alive` のみ」等) を `docs/` `aidlc-docs/` 全体に grep し、ヒット全件を確認してから完了とする。**「反映済み」と報告する前に grep の出力を証拠にする** |
| DR-9 | **件数・集合サイズの転記が複数文書に散る** | 「N 件」「N テーブル」「N 種」のような**数え上げた値が定義元と別の文書・別の節に転記されている**。1 件の追加・削除で連動箇所が爆発し、**キーワード grep では構造的に取り残しが出る** — 定義元の集合に属する条件 (例: `account_id` を持つなら §3.4.2 の 3 分類にも必ず入る) を辿らないと連動先が見えないため。**実測 (2026-07-31)**: `data-model.md` に `idea_tags` を **1 テーブル追加した連動は 15 箇所**で、**見積りが 2 回外れた** (起草側の初版 6 件 → 3 巡目レビュー 9 件 → 実測 15 件)。うち **4 箇所は CI 検査の期待値**であり、ずれると「設計どおりに実装した検査が必ず落ちる」形で実装リポに出る。**対処**: レビュー観点に置かず**機械強制する** — 定義元の表を数えた実測値を正として転記先を照合するスクリプトを作り `make check` に入れる (`scripts/check-table-counts.sh` が実例。**故障注入 7 種で検出力を確認済み — 7/7 検出**。内訳と経緯は `aidlc-docs/reviews/productionization/review-round4.md` §1.6 / §6.2。**2026-07-31 に唯一の盲点だった「同一文言の 2 個目に旧値が残る」を `pick()` の多重ヒット検査で塞ぎ、除外リスト件数・グループ行ラベルの検算を追加した** — 照合は 22 → 36 件)。**新しく「N 件」を書くときは、同時に検算の対象に加えるか、書かずに定義元へのリンクにする** 。**「影響範囲は N ファイル・N 箇所」型の数値も同じ**(2026-08-02 追加): 却下理由として書かれた「『8 タブ』の記述が 12 ファイル・54 箇所に存在する」が、**書いた時点から実測とずれていた** (docs/ の実測は 11 ファイル・53 箇所)。**却下理由の説得力は数値の大きさではなく連動の構造にある**ので、**数えた値を書かずに再現コマンド (`grep -rl` 等) を書く**。**tool の本数は 2026-08-02 に機械強制へ移した** (`check-endpoint-mapping.sh` の検査⑤。tool の増減は D-6 の再発行を伴うため必ず起きる)。**「文書そのものの数」も同じ** (2026-08-05 追加): `docs/design/README.md` の「**18 ファイル・約 12,000 行**」が **5 箇所に転記**され、実測 (22 ファイル・15,170 行) から乖離していた。「API/ 7 ファイル」「同ディレクトリ 6 ファイル」も **6 箇所**で旧値のまま (別増分で 3 ファイル増えた)。**索引の規模を示す数値は、増分ごとに必ず動くのに検算対象に入れにくい** — **したがって数値を書かず「1 セッションで読み切れない規模」+ 再現コマンド (`ls … | wc -l`) にした**。**判断の目安**: その数え上げが (a) 検査の期待値になるなら**機械強制**、(b) 説明のための規模感なら**書かずに再現コマンド**、(c) 定義元が別文書にあるなら**リンクだけ** |
| DR-10 | **構造変更が「無償で成立していた担保」を黙って外す** | **リポジトリ・ディレクトリ・CI の構造を変えたとき、その構造が副産物として担保していた性質が消える**。消えたことは**どの検査にも現れない** (検査自体は緑のまま) ため、DR-6 (検査が対象を見ていない) の親戚だが、こちらは**検査の対象ではなく前提条件が壊れる**。**実測 (2026-08-03。3 リポ → app モノレポ + infra リポの 2 分割)**: ①**リポジトリ境界が担保していた「破壊的 API 変更の 3 段は別 PR になる」が消えた** — 3 リポでは FE と BE が別リポだったため物理的に別 PR だったが、モノレポでは 1 PR に同梱できる。規約も CI も何も壊れないまま、順序だけが守られなくなる (対処 = MR-6: PR テンプレートの宣言欄 + H-1 の確認観点)。②**path filter を入れた瞬間にブランチ保護の必須ステータスチェックが機能しなくなる** — **skip されたジョブは status を返さない**ため、個別ジョブを必須に指定すると PR が**永久に pending** になる (対処 = MR-1: `if: always()` の gate ジョブ 1 本だけを必須にする)。**検出法**: 構造を変えるとき「**この性質は機構が守っているのか、構造の副産物だったのか**」を性質ごとに問う。副産物だったものには**代替の機構を同じ差分で用意する** (「規約に書く」だけで済ませない — 3 リポ時代はリポ境界が機構だったので、文書化されていないことすらある)。**設計判断の「代償」欄に、失う担保を明記する** (`architecture.md` §3.11.2 の MR-6 が実例)。**3 例目 (2026-08-04 のレビューで検出)**: ③**リポジトリ単位のアクセス権限**。3 リポ構成は「FE 開発者に BE リポの **write** を渡さない」を権限で担保できたが、**モノレポでは書き込み権限をサブツリー単位で分けられない** — `CODEOWNERS` は**レビュー要求**であって write の制限ではないため**代替にならない**。起草側は MR-4 の代償に「レビュー担当の分離が消える」とだけ書き、**権限の分離が消えることを書いていなかった**。**「CODEOWNERS で置き換えた」と書くときは、置き換えられていないもの (write 権限・Dependabot の単位・`git blame` の分離) を同じ行に列挙する**。**加えて「機構がある」と書いた機構は故障注入で殴る** — 本レビューは故障注入 3/3 非検出で「`make check` の緑がモノレポ機構を何も見ていない」ことを暴いた。**9 例目 (2026-08-05 の 3 巡目レビューで検出)**: ④**サブツリー間のマージ独立性**。**必須チェックを `gate` 1 本に集約 (MR-1) × 「Require branches to be up to date before merging」**の組み合わせで、**他サブツリーのマージが、無関係な PR まで out of date にして再実行を要求する** — 3 リポ構成では別リポ = 別の up-to-date 判定だったため無償で独立していた。**この例が示す教訓は「単体では正しい 2 つの設定の組み合わせで担保が消える」こと** — DR-10 の検出法 (性質ごとに「機構が守っているか / 構造の副産物か」を問う) に加えて、**新設した機構と既存の設定の組を 1 つずつ確かめる**。**現れ方が遅い** (規約も CI も壊れず、PR 同時数が増えたときに初めてマージの直列化として出る) ため、**代償欄に「いつ・何を観測したら見直すか」まで書く** (`architecture.md` §3.11.2 の MR-1 が実例) |

## 運用

- `design-reviewer` は本表を必ずチェックリストとして使う (DR 全件 + 変更が触れる BE/FE)
- **DR-9 は機械強制済み** — 件数の整合は `make check-table-counts` が見る。レビューでは「**新しく増えた「N 件」が検算の対象に入っているか**」を見る (検算されない件数が増えると DR-9 が復活する)
- **DR-8 の再検査 grep は「数値語」だけでは足りない** (2026-07-31 追加。5 巡連続再発の原因)。**状態語も必ず grep する** — `未了` / `未実装` / `未設定` / `未登録` / `未着手` / `含まれていない` / `是正要求` / `必要` / `無い`。3 巡目の反映は数値語 3 パターン (`存在検査 5 種` / `6 種の「必須テスト` / `#4 / #5`) だけで再検査し、**「登録は未了」「是正要求を…出した」に一致しないため構造的に取り残した**
- **DR-8 には受信側がある** (2026-07-31 追加)。5 巡目の波及漏れ 11 件のうち **7 件は「他書が自分宛てに起票した是正要求を受け取っていない」型**で、**自分の文書内の grep では検出できない**。**是正要求を受ける文書は「受信欄」(起票元・ID・状態) を持つこと** — 実例は `docs/design/auth.md` §10.3
- `architecture-designer` は設計時に BE/FE 表を読み、**該当パターンを構造で潰したか**を設計書に書く
- 新規に観測したパターンは 1 行追記する (レビュー結果 → 本表への還流)
