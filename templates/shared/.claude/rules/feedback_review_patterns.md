# 頻出バグ・設計欠陥パターン (SSOT)

このファイルが**頻出パターンの単一の正 (Single Source of Truth)**。
`rules/04-review.md` / `agents/design-reviewer.md` / `agents/architecture-designer.md` は本ファイルを参照する。
**重複コピーを各所に置かない** (更新時のドリフト防止)。

2 つのセクションからなる:

- **DR-x (設計レビュー)** — このリポジトリで発生する設計上の欠陥。レビューで検出したら追記する
- **BE-x / FE-x (PoC 由来)** — PoC で実際に起きたバグ。**本番設計で構造的に潰すべき既知の落とし穴**。
  「実装時に気をつける」ではなく「設計でその余地を無くす」観点で使う

## DR: 設計ドキュメントの欠陥

| # | パターン | 検出観点 |
|---|---|---|
| DR-1 | **出典なしの断定** | PoC / v2 の挙動を「〜になっている」と書きながら パス:行 の出典がない。転記された誤認は実装リポまで運ばれる |
| DR-2 | **本番観点の無言の省略** | `08-production-gates.md` の ID に回答も「対象外の理由」も無い。特に A-6 (LLM のテナント越境)・O-2 (全経路の LLM 計測)・D-6 (Agent 再発行) が落ちやすい |
| DR-3 | **既存データの不在** | 新スキーマ・新キー設計に、**v2 本番 DB の既存データ**との共存・移行・ロールバックが書かれていない |
| DR-4 | **PoC 実装のコピー設計** | PoC のハンドラ構造 (net/http・手書き store・`http.Error` JSON) をそのまま本番設計に持ち込んでいる。本番は v2 規約 (3 層・sqlc/wire・`CodedError`) が正 |
| DR-5 | **曖昧語による実装者への丸投げ** | 「適切に」「必要に応じて」「後で検討」が判断ポイントに使われている。受入基準に落ちない記述は設計未完成 |
| DR-6 | **AC の宙吊り** | requirements の AC-ID が plan / 設計書のどこからも参照されていない (`make check-traceability` が検出)。逆に、設計判断に対応する AC が無い場合も要件漏れ 。**検査が「対象 0 件」を検査して緑になる形に注意** (2026-08-02 追加): `check-traceability.sh` の AC 抽出正規表現が `AC-[0-9]` 形式のみだったため、**増分ごとに名前空間を分けた `AC-CV-*` 39 件が 1 件も照合対象に入らないまま「全カバー」と表示されていた**。**新しい ID 体系を導入したら、検査がその ID を拾うかを故障注入で確かめる** (「検査が通った」は「検査が対象を見た」を意味しない。同型の穴は `feature` const の存在検査 = `observability.md` §4.2 にもある) |
| DR-7 | **プロトタイプを仕様として扱う** | `docs/prototype/*.html` の画面を根拠に仕様を確定している。プロトタイプは設計入力であって仕様ではない (実装されていない挙動が含まれる) |
| DR-8 | **修正の波及漏れ (自己申告の範囲だけ直す)** | 設計判断を変更したとき、**思考の対象になった節だけを直し、同じ事実に依拠する他の記述が旧版のまま残る**。auth.md のレビュー 4 巡で **3 回連続**発生 (①方針反転を §4/§5 に書いて §2/§6 が旧記述 ②AC-1.1 を改訂して AC-1.2 が旧前提 ③§6.3/§6.4 を改訂して §7 の回答表が旧記述)。**検出法**: 変更した主張のキーワード (「すべてのテーブル」「v2 再利用」「公開は `GET /alive` のみ」等) を `docs/` `aidlc-docs/` 全体に grep し、ヒット全件を確認してから完了とする。**「反映済み」と報告する前に grep の出力を証拠にする** |
| DR-9 | **件数・集合サイズの転記が複数文書に散る** | 「N 件」「N テーブル」「N 種」のような**数え上げた値が定義元と別の文書・別の節に転記されている**。1 件の追加・削除で連動箇所が爆発し、**キーワード grep では構造的に取り残しが出る** — 定義元の集合に属する条件 (例: `account_id` を持つなら §3.4.2 の 3 分類にも必ず入る) を辿らないと連動先が見えないため。**実測 (2026-07-31)**: `data-model.md` に `idea_tags` を **1 テーブル追加した連動は 15 箇所**で、**見積りが 2 回外れた** (起草側の初版 6 件 → 3 巡目レビュー 9 件 → 実測 15 件)。うち **4 箇所は CI 検査の期待値**であり、ずれると「設計どおりに実装した検査が必ず落ちる」形で実装リポに出る。**対処**: レビュー観点に置かず**機械強制する** — 定義元の表を数えた実測値を正として転記先を照合するスクリプトを作り `make check` に入れる (`scripts/check-table-counts.sh` が実例。**故障注入 7 種で検出力を確認済み — 7/7 検出**。内訳と経緯は `aidlc-docs/reviews/productionization/review-round4.md` §1.6 / §6.2。**2026-07-31 に唯一の盲点だった「同一文言の 2 個目に旧値が残る」を `pick()` の多重ヒット検査で塞ぎ、除外リスト件数・グループ行ラベルの検算を追加した** — 照合は 22 → 36 件)。**新しく「N 件」を書くときは、同時に検算の対象に加えるか、書かずに定義元へのリンクにする** 。**「影響範囲は N ファイル・N 箇所」型の数値も同じ**(2026-08-02 追加): 却下理由として書かれた「『8 タブ』の記述が 12 ファイル・54 箇所に存在する」が、**書いた時点から実測とずれていた** (docs/ の実測は 11 ファイル・53 箇所)。**却下理由の説得力は数値の大きさではなく連動の構造にある**ので、**数えた値を書かずに再現コマンド (`grep -rl` 等) を書く**。**tool の本数は 2026-08-02 に機械強制へ移した** (`check-endpoint-mapping.sh` の検査⑤。tool の増減は D-6 の再発行を伴うため必ず起きる) |

## BE: バックエンド (PoC で実際に起きたもの)

| # | パターン | 本番設計での潰し方 |
|---|---|---|
| BE-1 | **LLM プロンプトのデータ参照ミス** | ブラッシュアップ/再評価で旧バージョンを参照して数値が食い違う。**どのバージョンを渡すかを設計で明示**する |
| BE-2 | **生成数の hard cap 散在** | 既定/上限がコード・FE・prompts の 3 層に散る。**設定値の SSOT を 1 箇所に決める**設計にする |
| BE-3 | **`WriteEnv` のキー脱落** | `claude_managed_agents/internal/config/dotenv.go` は固定キーのみ書き出し、`DATABASE_URL` 等が消える。**本番は `.env` 自動書き換え方式を採らない** (D-5) |
| BE-4 | **評価の stale ガード** | source_hash と read-time 照合。**派生物 (評価・企画書) が元データの変更で無効化される関係を設計に書く** |
| BE-5 | **DB 未接続フォールバック** | PoC は `DATABASE_URL` 未設定でインメモリ動作 (CI もこの経路前提)。**本番ではフォールバックを持たない** (静かなデータ喪失になる) |
| BE-6 | **LLM JSON の MaxTokens 切り詰め** | 出力フィールド増で JSON が途中で切れ「valid JSON でない」になる。同一パラメータ再試行は同じ deadline を共有し `context deadline exceeded` を誘発 (`claude_managed_agents/cmd/devui/idea_evaluate.go`)。**出力規模に対する MaxTokens 余裕と `stop_reason==max_tokens` 検出を設計に含める** (O-4) |
| BE-7 | **SSE のマルチライン取りこぼし** | agent メッセージが複数行・空行を含むと、bridge が先頭行しか流さず本文後半や `<options>` が欠落する (`claude_managed_agents/cmd/devui/conversation_stream.go`)。**除外リスト方式 (既知プレフィックスのみ捨てる) + 空行も本文として通す**を仕様に書く |
| BE-8 | **tool schema と handler args の乖離** | schema の引数名と handler のパースが食い違うと、LLM の引数が黙って捨てられ機能が死ぬ。**schema・handler・prompt 説明の 3 者一致を CI か起動時チェックで機械化する** (D-6) |
| BE-9 | **Agent Update の tools 全置換** | `Tools` は全置換のため、更新時に既存の web_search 等が消える。**Agent 定義の管理をコード化 (宣言的) する** |
| BE-10 | **台帳 (SSOT) への write-through 欠落** | 前提チェックが読む台帳フィールドに、書き込む経路がどこにも無く機能が即失敗する (`claude_managed_agents/cmd/devui/conversation_ledger.go`)。**「読む側」と「書く側」を対で設計する** |
| BE-11 | **バージョン採番の固定 Insert** | ver 固定 Insert が UNIQUE 違反で再実行時にサイレント失敗 (`claude_managed_agents/cmd/devui/conversation_tools_plan.go`)。**採番規則と冪等性を設計に書く**。Insert 失敗を握り潰さない |
| BE-12 | **生成物の還流でフィールド契約が食い違う** | 読み手の構造体が、書き手に存在しないフィールドを期待している (PoC 実例: grounding 還流の読み手 `claude_managed_agents/cmd/devui/conversation_plan_grounding.go:100`〜`:102` が `finding`/`notes:string` を期待するが、書き手 `conversation_tools_deepdive.go:168`〜`:176` に `finding` は無く `notes` は `[]string`)。**テストが合成 JSON を渡していると契約違反が隠れる** — 読み手・書き手・テストを同じスキーマ定義から導くこと |

## 運用

- `design-reviewer` は本表を必ずチェックリストとして使う (DR 全件 + 変更が触れる BE/FE)
- **DR-9 は機械強制済み** — 件数の整合は `make check-table-counts` が見る。レビューでは「**新しく増えた「N 件」が検算の対象に入っているか**」を見る (検算されない件数が増えると DR-9 が復活する)
- **DR-8 の再検査 grep は「数値語」だけでは足りない** (2026-07-31 追加。5 巡連続再発の原因)。**状態語も必ず grep する** — `未了` / `未実装` / `未設定` / `未登録` / `未着手` / `含まれていない` / `是正要求` / `必要` / `無い`。3 巡目の反映は数値語 3 パターン (`存在検査 5 種` / `6 種の「必須テスト` / `#4 / #5`) だけで再検査し、**「登録は未了」「是正要求を…出した」に一致しないため構造的に取り残した**
- **DR-8 には受信側がある** (2026-07-31 追加)。5 巡目の波及漏れ 11 件のうち **7 件は「他書が自分宛てに起票した是正要求を受け取っていない」型**で、**自分の文書内の grep では検出できない**。**是正要求を受ける文書は「受信欄」(起票元・ID・状態) を持つこと** — 実例は `docs/design/auth.md` §10.3
- `architecture-designer` は設計時に BE/FE 表を読み、**該当パターンを構造で潰したか**を設計書に書く
- 新規に観測したパターンは 1 行追記する (レビュー結果 → 本表への還流)
