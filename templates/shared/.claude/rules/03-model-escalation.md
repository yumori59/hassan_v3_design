# Rule 03: モデル選択とエスカレーション (backend / frontend / infra 共通)

**どのサブエージェント (SA) をどのモデルで呼ぶか**、**いつ・誰が・何を根拠に昇格 / 降格するか**を定める。
このファイルはオーケストレーター (Claude Code のメインセッション。以下 **OR**) の判断規範であり、
**3 リポジトリ共通** (`templates/shared/` から各実装リポの `.claude/rules/` にコピーされる)。

ここが**既定モデルと昇格 / 降格の基準の SSOT**。次は他が持つ (ここに複製しない):

| 事項 | SSOT |
|---|---|
| 作業ループの順序・担当・停止条件、昇格トリガーの**発火位置** (S-4 / S-7 / S-3・S-5) | [`01-construction-loop.md`](01-construction-loop.md) §1.2 |
| Red の受理条件・「意図した失敗」の定義 | [`01-construction-loop.md`](01-construction-loop.md) §2 |
| レビュー差し戻しの反復上限 (2 巡) と上限到達時の停止手順 | [`01-construction-loop.md`](01-construction-loop.md) §3 |
| 設計リポへの差し戻し判定 (§4.1 / §4.2) と手順 | [`01-construction-loop.md`](01-construction-loop.md) §4 |
| 各 SA の責務・観点・禁止事項 | `.claude/agents/*.md` (frontmatter の `model:` が既定値の実体) |
| issue の粒度・完了条件 | rule `02-issue-granularity.md` |
| 人間承認点の一覧と機構 | rule `04-human-checkpoints.md` |

> 本ルールが満たす設計リポ hassan_v3 の受入基準 (feature `construction-workflow`):
> **AC-3.1** §1 (既定モデルと tier 原則) + §2 (判断主体・タイミング・根拠) + §4 (デエスカレーション) /
> **AC-3.2** §3 (実行中の昇格トリガー)。
> ステップ ID **S-1〜S-10 は本ルールで再定義しない** — 定義は `01-construction-loop.md` §1.1 が正。

## 0. 用語

- **tier**: `haiku` < `sonnet` < `opus` の順序。「tier 以上」はこの順序で比較する
- **昇格 (エスカレーション)**: 委譲時に `model:` を明示指定して既定より上の tier で呼ぶこと
- **降格 (デエスカレーション)**: 同様に既定より下の tier で呼ぶこと
- **既定モデル**: 各 SA 定義の frontmatter `model:` の値。`model:` を明示しない委譲はこの値で走る

昇格 / 降格は**呼び出し側 (OR) が委譲時に指定する**。SA 定義の frontmatter を書き換えて行わない
(リポジトリ全体の既定が変わり、他 issue の委譲まで巻き込むため)。

## 1. 既定モデル (AC-3.1)

| SA | 役割 | 既定モデル | 根拠 |
|---|---|---|---|
| `go-developer` | backend 実装 | **sonnet** | 4 層 + `entity/` / `gateway/` の計 6 パッケージ層・sqlc/wire・エラー規約が既存コードに前例として揃っており、定型の比率が高い |
| `react-developer` | frontend 実装 | **sonnet** | 同上 (生成型 + 既存コンポーネントの前例) |
| `infra-engineer` | infra 実装 (`plan` まで) | **opus** (例外) | 誤変更が RDS の replace・ECS 全断・IAM 過剰付与に直結し、差分 1 行の読み違いの被害が実装規模と無関係に最大化する |
| `code-reviewer` | backend レビュー | **opus** | 見落とし (False Negative) の被害が最大。実装前に潰せる最後の関門 |
| `frontend-reviewer` | frontend レビュー | **opus** | 同上 |
| `infra-reviewer` | infra レビュー | **opus** | 同上。実装が opus であるため tier 原則からも opus が下限 (定義ファイルは `.claude/agents/infra-reviewer.md`) |

### 1.1 原則: reviewer は実装者の tier 以上

**1 つの issue の中で、S-7 のレビュー SA を S-4 / S-5 の実装 SA より低い tier で呼ばない**。
実装を opus に昇格させた issue は、その issue のレビューも opus で行う (既定が opus なので追加指定は不要)。
逆に実装を haiku へ降格させた場合、レビューは sonnet 以上であればよい (§4)。

理由: レビューは実装より多くの文脈 (層間の整合・テナント境界・頻出パターン全件) を同時に保持する必要があり、
実装より低い tier のレビューは「実装が気付かなかったことに同じく気付かない」形で通過する。

却下案と理由:

- **レビューを実装と同 tier に揃える (常に sonnet 実装 + sonnet レビュー)** — コストは下がるが、
  本番リポでの見落ち 1 件の被害 (テナント越境・認証漏れ) がレビュー費用を大幅に上回るため却下
- **実装も常に opus (Q-5 の選択肢 C)** — 判断は不要になるが、typo 修正・配線変更・生成物追従といった
  定型作業のコストが恒常的に上がるため却下。代わりに §2 の着手前判定 + §3 のトリガーで補う
- **`infra-engineer` を sonnet に揃える** — 3 リポで既定を統一できるが、Terraform は
  「差分を読み違えても文法・`validate` が通る」ため機械ゲートで守れない。データ消失側に振れる
  リスクを取らないため却下 (この例外は SA 定義 `.claude/agents/infra-engineer.md` の記述と一致させる)

### 1.2 判断より先に、指示を具体化する

**曖昧な指示のまま opus に丸投げするより、指示を具体化して sonnet に渡す方が良い結果になることが多い**。
昇格を検討する前に、委譲プロンプトに次が書かれているかを確認する: 対象 AC-ID / 触ってよいファイル /
参照すべき既存実装のパス / 設計書の該当節 / 該当する頻出バグパターン番号 / 実行すべき検証コマンド。
これらが埋まっていない委譲の失敗は、モデルの能力不足ではなく**指示の不足**として扱う (再委譲は昇格に数えない)。

## 2. 着手前判定 (S-2) (AC-3.1)

- **判断主体: OR**。SA の自己申告 (「この実装は非自明なので opus で」) では判定しない —
  難しい実装ほど「難しさに気付かないまま進む」方に外れるため
- **タイミング: S-2 (着手前判定)**。S-3 の計画で触るファイルが判明して判定が変わった場合は、
  S-4 の委譲前に判定をやり直す
- **記録: issue コメント** (§2.3 の形式)。委譲時に指定した `model:` と食い違わせない

### 2.1 判定表 (4 観点)

| # | 観点 | 既定モデルで委譲 (左) | 昇格して委譲 (右) |
|---|---|---|---|
| M-1 | **触るファイル数** (S-3 の計画で列挙した数。テストを含む) | 5 以下 | 6 以上 |
| M-2 | **新規ドメインか** | 既存ドメインへの追加・変更で、同種の実装がリポ内に前例としてある (参照先のパスを issue に書ける) | リポに前例のないドメイン (新テーブル群・新エンドポイント群・新しい LLM / Agent 経路・新モジュール) |
| M-3 | **並行処理・状態機械を含むか** | 含まない (同期の CRUD・単純な変換・スタイル調整・変数化) | goroutine / channel / `context` キャンセル / SSE ストリーム / リトライ・冪等性 / 複数トランザクションの順序 / FE の多段状態遷移 のいずれかを含む |
| M-4 | **設計書に前例があるか** | 設計書に実装形が具体で書かれている (層・テーブル・カラム・エンドポイント・ステータス・所有者スコープが特定できる) | 設計書の記述が方針レベルで、実装形の選択が残る |

### 2.2 判定ルール (機械的に適用する)

1. **M-2 / M-3 / M-4 のいずれかが右列 → 昇格して委譲する** (sonnet 既定の SA は opus で呼ぶ)
2. **M-1 だけが右列で M-2〜M-4 が左列 → 既定モデルのまま**。件数が多いだけの横断変更
   (命名の一括変更・生成物の追従・同型ハンドラの追加) は tier ではなく分割で対処する。
   触るファイルが 15 を超えるなら **issue を分割する**判定を先に行う (rule `02-issue-granularity.md`)
3. **M-4 が右列のときは、昇格の前に設計リポ差し戻しの判定を行う** —
   [`01-construction-loop.md`](01-construction-loop.md) §4.1 に該当するなら**着手せず差し戻す** (§3 のトリガー ③ と同じ扱い)
4. 既定が opus の SA (`infra-engineer`) は右列に該当しても昇格先が無い。この場合は
   **「人間の計画承認を S-2 の条件に追加する」**で代替する (Q-3 の条件付き着手前承認の該当扱い)

### 2.3 issue への記録形式

```markdown
## モデル判定 (S-2)

- 実装 SA: `go-developer` / 委譲モデル: **opus** (既定 sonnet から昇格)
- 判定: M-1 触るファイル 8 (右) / M-2 新規ドメイン: 該当 (右) / M-3 並行処理: なし (左) / M-4 設計書の前例: `docs/design/api/themes.md` §3 に具体あり (左)
- 昇格理由: M-2 (テーマ横断のアセット参照は本リポに前例なし)
- レビュー SA: `code-reviewer` / **opus** (tier 原則: 実装 opus 以上)
```

昇格しない場合も同じ形式で「既定のまま」と記録する (判定を省略したのか既定を選んだのかを後から区別するため)。

## 3. 実行中の昇格トリガー (AC-3.2)

着手前判定は難易度を読み違える。**実行中の観測で昇格する**。発火位置は
[`01-construction-loop.md`](01-construction-loop.md) §1.2 が定める 3 点で、本節は**検知条件と昇格先**を定める。
判定者はいずれも **OR** (SA の報告を受け取った側)。

ID の対応: **T-1 = `01-construction-loop.md` §1.2 の ①** (発火位置 S-4) / **T-2 = 同 ②** (S-7 の 2 巡目) /
**T-3 = 同 ③** (S-3 または S-5)。

| ID | トリガー | 検知条件 (この形で判定する) | 昇格先と行動 |
|---|---|---|---|
| **T-1** | Red が意図した失敗にならない | 同一 SA への S-4 委譲が **2 回連続**、`01-construction-loop.md` §2.1 の受理条件を満たさない (assertion 失敗を観測できない / コンパイル・型エラーのみ / テスト名に AC-ID が無い) | **opus で S-4 をやり直す**。同じ SA を 3 回目は呼ばない |
| **T-2** | レビューの重大指摘が反復する | S-7 の **2 巡目**のレビュー結果に重大 (Must Fix) が 1 件以上残る | **3 巡目に入らない**。issue にコメントして停止し**人間へエスカレーション**。人間が続行を指示した場合、その指摘反映 (S-8) を **opus** で行う |
| **T-3** | 設計書に無いパターンに到達 | S-3 の計画時、または S-5 で SA が差し戻し報告を上げた時点で、`01-construction-loop.md` §4.1 の 1〜4 のいずれかに該当する | **昇格しない**。まず**設計リポへの差し戻し**を判定する (同 §4)。§4.2 に該当するだけ (実装側で決めてよい) だった場合のみ、**opus で 1 回だけ再委譲**する |

### 3.1 T-1 の運用

昇格して S-4 をやり直すとき、委譲プロンプトに**2 回の不受理の内容をそのまま書き写す** (どの出力が
受理条件のどれを満たさなかったか)。同じ指示で opus に投げ直すのは §1.2 の禁止事項に当たる。
opus でも受理条件を満たさない場合、原因は AC の翻訳不能 (`01-construction-loop.md` §4.1 の 4) の
可能性が高いため、**T-3 の差し戻し判定に切り替える**。

### 3.2 T-2 の運用 (Q-6 = 差し戻し 2 回までとの関係)

- 上限判定が**先**。2 巡目に重大が残った時点で `01-construction-loop.md` §3 のとおり停止し、
  PR は draft のまま `needs-human` ラベルを付ける
- opus での S-8 は**人間が「この方針で修正して進めてよい」と判断した後**に実施する。
  OR が独断で opus に昇格して 3 巡目のレビューへ進めることは禁止 (上限が無効化される)
- 1 巡目の指摘反映 (S-8) は既定モデルのままでよい。1 巡目の指摘は具体的であり、
  この時点での昇格は「収束しない原因が設計側にある」ケースを覆い隠す

### 3.3 昇格の上限と記録

- **昇格は 1 issue につき tier を 1 段 (sonnet → opus) まで**。opus で同じトリガーが再発火したら
  **人間へエスカレーションする** (モデルを変える手段が尽きているため、反復しても収束しない)
- 昇格したら issue にコメントする: 発火した トリガー ID / ループ位置 (S-x) / 変更前後のモデル /
  昇格後にやり直すステップ。この記録は `01-construction-loop.md` §6 のループ位置コメントに含めてよい
- **昇格しても裏取り責務は OR に残る** (`01-construction-loop.md` §2)。opus の報告だからといって
  Red / Green の出力確認と S-6 の自前実行を省略しない

## 4. デエスカレーション (AC-3.1)

**軽微な差分に限り**、次を許可する。判断主体は OR、タイミングは S-2。

| 対象 | 許可する指定 |
|---|---|
| 実装 (S-4 / S-5) | 既定 (sonnet) のまま。`model: haiku` の明示指定も可 |
| レビュー (S-7) | `model: sonnet` を明示指定してよい (既定 opus から降格) |

**「軽微な差分」の条件 (すべて満たすこと)**:

1. 触るファイルが **2 以下**
2. **振る舞いを変えない**変更である — typo・コメント・ログ文言・設定値の変更・定数の値変更・
   生成物の再生成・フォーマット・スタイルのみの調整
3. **テスト先行を省略できる**区分に該当する (各実装 SA 定義の TDD 節の「省略可」。
   [`../skills/test-driven-development/SKILL.md`](../skills/test-driven-development/SKILL.md) が正)
4. **認証・テナント境界・LLM 呼び出し経路・DB スキーマ・IaC のいずれにも触れない**

条件 4 に触れる差分は、行数が少なくても降格しない (1 行の設定値変更が公開範囲・所有者スコープ・
コストを変え得る)。**infra リポは §1 の例外により降格対象外** — `terraform` の差分は行数と被害が比例しない。

降格しても `01-construction-loop.md` の S-6 (検証) と S-7 (レビューを別セッションで行うこと) は省略しない。
**「軽微だからレビューを飛ばす」は降格ではない** (自己レビュー禁止の潜脱になる)。

## 5. やってはいけないこと

- SA 定義の frontmatter `model:` を書き換えて昇格 / 降格する (§0)
- 昇格の判定を SA に委ねる / SA の自己申告だけで昇格する (§2)
- 同じ委譲プロンプトのまま tier を上げて投げ直す (§1.2)
- レビュー SA を実装 SA より低い tier で呼ぶ (§1.1)
- T-2 の停止を飛ばして opus で 3 巡目のレビューへ進む (§3.2)
- 判定・昇格を issue に記録しないまま進める (中断・再開時に判定が失われ、再委譲で tier が戻る)
