# Rule 01: 1 issue の作業ループ (app モノレポ / infra リポ 共通)

**GitHub issue 1 本を受け取ってから PR がマージされるまでの手順・担当・停止条件**を定める。
このファイルはオーケストレーター (Claude Code のメインセッション) の行動規範であり、
**2 リポジトリ共通** (app モノレポ / infra リポ。`templates/shared/` から各実装リポの `.claude/rules/` にコピーされる)。
サブツリー / リポ固有の読み替えは §1.3 (検証コマンド) と §2.4 (infra の Red/Green) に限る。

このファイルが定めるのは**順序と担当**のみ。次は他の SSOT が持つ (ここに複製しない):

| 事項 | SSOT |
|---|---|
| Red→Green の書き方・テストの良し悪し | [`.claude/skills/test-driven-development/SKILL.md`](../skills/test-driven-development/SKILL.md) |
| 着手前の影響半径測定・完了前セルフレビュー | [`.claude/skills/implementing-robustly/SKILL.md`](../skills/implementing-robustly/SKILL.md) |
| 実装規約 (層の責務・エラー・テナント境界) | `CLAUDE.md` + `.claude/agents/*.md` |
| 頻出バグパターン | `.claude/rules/feedback_review_patterns.md` |
| issue の粒度・完了条件 (DoD)・リポ跨ぎ / サブツリー跨ぎのマージ順序 | rule `02-issue-granularity.md` |
| 既定モデルと昇格 / 降格の基準 | rule `03-model-escalation.md` |
| 人間承認点の一覧と機構 (environment 承認・deny) | rule `04-human-checkpoints.md` |
| 要件・設計 (何を作るか) | 設計リポ hassan_v3 の `aidlc-docs/inception/<feature>/` と `docs/design/` |

> 本ルールが満たす設計リポ hassan_v3 の受入基準 (feature `construction-workflow`):
> **AC-1.1** §1 / **AC-1.2** §2 / **AC-1.3** §3 / **AC-1.4** §4 / **AC-1.5** §5 / **AC-6.1** §7 / **AC-6.3** §8。
> 本番ゲート `08-production-gates.md` の **D-2** に §7 で回答する。**D-4 / D-6** はループ上の位置のみ §7 で示し、
> 承認機構は rule `04-human-checkpoints.md` が定める。**A / O 領域**の扱いは §8。
> (ここでの AC-ID は設計プロセス側の受入基準であり、実装 issue が扱う AC-ID とは別物)

## 0. 役割と自律範囲

| 記号 | 担当 | 実体 |
|---|---|---|
| **人間** | リポジトリのオーナー | 判断・承認・マージ |
| **OR** | オーケストレーター | Claude Code のメインセッション。委譲・裏取り・issue への記録 |
| **SA** | サブエージェント | 実装 = `go-developer` / `react-developer` / `infra-engineer`、レビュー = `code-reviewer` / `frontend-reviewer` / `infra-reviewer` |
| **CI** | GitHub Actions | `.github/workflows/ci.yml` (と pre-commit hook)。**app モノレポでは path filter でサブツリー別ジョブが出し分けられ、必須チェックは `gate` ジョブ 1 本のみ** (MR-1) |

自律範囲 (実装リポでの確定値。`.claude/settings.json` に落とす):

- **許可**: ブランチ作成 / commit / feature ブランチへの push / PR 作成 / PR の更新
- **人間のみ**: **PR のマージ**、DB マイグレーションの適用、Managed Agent の再発行、本番デプロイ、`terraform apply`
- **deny**: `main` への直接 push (ブランチ保護でも禁止)、force push、ブランチ削除、タグ操作、`--no-verify`

**レビューは実装と別セッションの SA が行う** (自己レビュー禁止)。OR は実装 SA の出力をそのままレビュー SA に
渡すのではなく、`git diff main...HEAD` の範囲を指定して独立に読ませる。

## 1. ステップ表 (AC-1.1)

### 1.1 ループ本体

ステップ ID (S-1〜S-10) は他ルール・issue コメント・PR 本文から参照される**固定の識別子**。

| # | ステップ | 入力 | 出力 | 担当 |
|---|---|---|---|---|
| **S-1** | **issue 受領** | GitHub issue (対象 AC-ID / 影響する層 / 検証コマンド / 人間チェックポイント該当 / 依存 issue の欄) | 着手対象の確定。欄が埋まっていなければ差し戻し (起票者へ) | OR |
| **S-2** | **着手前判定** | issue 本文 + 設計書 (`docs/design/`) の該当節 | ①人間の計画承認が必要かの判定 ②委譲モデルの決定 ③依存 issue のマージ済み確認 ④人間チェックポイント該当の確認 → 結果を issue にコメント | OR (承認が必要なら**人間**) |
| **S-3** | **現状把握と計画** | 設計書・既存コード・issue の AC-ID | 変更計画 (触るファイル・層・テスト一覧)。ブランチ作成 (`<type>/<issue番号>-<slug>`) | OR (調査は SA/Explore に委譲可) |
| **S-4** | **テスト先行 (Red)** | AC-ID ごとの受入基準 | **AC-ID 入りの失敗するテスト** + テスト出力 (FAIL とその理由) | 実装 SA → 裏取りは OR (§2) |
| **S-5** | **実装 (Green)** | Red のテストと計画 | 実装コード + テスト全通過の出力。commit (pre-commit が走る) | 実装 SA → 裏取りは OR (§2) |
| **S-6** | **検証** | 変更全体 | リポの検証ゲート全コマンドの実行結果 (§1.3)。生成物の再生成漏れゼロ | OR (コマンドは自身で実行する) |
| **S-7** | **レビュー (別セッション)** | `git diff main...HEAD` + 対象 issue の AC-ID | レビュー結果 (重大 / 中 / 軽微)。A / O 観点の結果を含む (§8) | レビュー SA (別セッション) |
| **S-8** | **指摘反映** | S-7 の重大・中の指摘 | 修正 commit。重大は全件解消。中・軽微はこの PR で直すか別 issue に切る | 実装 SA → 判定は OR (§3) |
| **S-9** | **PR 作成** | 検証済みブランチ | push + PR (対象 issue の `Closes #N`・DoD チェックリスト・検証出力・レビュー結果の要約)。CI が起動 | OR |
| **S-10** | **マージ** | CI green + レビュー重大ゼロ + DoD 充足 | `main` へのマージ、issue クローズ | **人間** |

補足 (曖昧さを残さないための確定事項):

- **push のタイミング**: 既定は S-9 で 1 回。ただし中断時の退避 push は S-4 以降いつでも可
  (feature ブランチは壊れてよい場所)。
  **退避 push では CI は起動しない** — `ci.yml` の `push` トリガは `main` のみに限定されている
  (2026-08-04 の是正。`push: branches: ["**"]` と `pull_request` を併用すると**同一 SHA に基準の違う
  `gate` チェックランが 2 つ**生まれ、ブランチ保護がどちらを見るか不定になるため)。
  **CI は S-9 で PR を作った時点から `pull_request` で走り、以降の push ごとに再走する**。
  したがって **S-4〜S-8 の間は機械の検証が pre-commit だけになる** — この区間で
  「CI が見てくれる」に期待しない (中断・再開の §6 が想定する期間がここに当たる)。
- **S-7 を PR 作成より前に置く理由**: レビューの差し戻し (§3) が PR のレビューコメント履歴を汚さず、
  人間が PR を開いた時点で「重大ゼロ」であることを保証できる。PR 作成後にレビューする案は、
  人間が「まだレビュー中の PR」を見分けられなくなるため却下。
- **S-8 の後**: 重大が残っていれば S-7 に戻る (最大 2 巡。§3)。解消したら S-6 をやり直してから S-9。
- **1 セッションで S-1〜S-9 を完走することを前提にしない**。中断・再開は §6。

### 1.2 実行中の昇格トリガーが発火する位置

判定基準と昇格先モデルは rule `03-model-escalation.md` が定める。**発火位置**は本ループ上で次の 3 点:

| トリガー | 発火位置 | ループ上の扱い |
|---|---|---|
| ① Red が 2 回連続で意図した失敗にならない | S-4 | 同じ SA に再試行させず、昇格して S-4 をやり直す |
| ② レビューの重大指摘が 2 巡目も残る | S-7 の 2 巡目 | 3 巡目に入らず停止して人間へ (§3) |
| ③ 設計書に無いパターンに到達した | S-3 または S-5 | 昇格ではなく**設計リポへの差し戻し**を先に判定する (§4) |

### 1.3 サブツリー / リポごとの S-6 (検証) の実体

`CLAUDE.md` の「検証ゲート」節が各リポの正。ループ上は**全コマンドが通ることが S-6 の完了条件**:

| サブツリー / リポ | S-6 で OR が実行するコマンド |
|---|---|
| backend (`backend/`) | `go build ./...` / `go vet ./...` / `go test ./...` / `golangci-lint run` / 生成物の再生成 (`make sqlc` `make wire`) と **`scripts/check-regen.sh backend`** |
| frontend (`frontend/`) | `npx tsc --noEmit` / `npm run test` / `npm run build` / `npm run lint` |
| **契約 (`api/`)** | **backend / frontend のどちらを触った場合も実行する**: `make -C backend docs` → **`scripts/check-regen.sh api/openapi.yaml`** → `npm --prefix frontend run generate` → **`scripts/check-regen.sh frontend/src/generated`** (MR-3) |
| infra | `terraform fmt -check -recursive` / `terraform validate` / `tflint --recursive` / `terraform plan` (差分の要約と `destroy`/`replace` の有無) |

**生成物の差分検査は `scripts/check-regen.sh` を通す。裸の `git diff --exit-code` を書かない**:

- `git diff` は**カレントディレクトリに限定されない** — pathspec が無いと他サブツリーの差分を拾う
- `git diff` は**未追跡ファイルを一切見ない** — **新規に生成されたファイル (`api/openapi.yaml` の初回・
  orval / sqlc の新規出力) の追加漏れが素通りする**。これが「エンドポイント追加」という最頻の変更で
  MR-3 を空振りさせていた (2026-08-04 の design-reviewer 指摘 重大 1)
- `check-regen.sh` は **`git status --porcelain --untracked-files=all`** を使うため、
  **追加 (`??`) / 変更 (` M`) / 削除 (` D`) のすべてを検出し、インデックスを触らない**。
  ⚠️ **`git add --intent-to-add` + `git diff` に「簡素化」しないこと** — `git add` が削除を
  ステージするため **削除を見落とし**、かつローカル実行で**意図しない削除が commit に混入する**

**S-6 は OR 自身が実行する**。実装 SA の報告に載っていた出力を S-6 の証拠として流用しない
(SA は変更途中の状態で実行している可能性がある)。

## 2. Red → Green の裏取り (AC-1.2)

**確認責務はオーケストレーター (OR) にある**。実装 SA の「Red を確認しました」という自己申告は
**それだけでは受理しない**。

### 2.1 受理の条件 (3 点すべて)

1. **Red のテスト出力**が報告に貼られている — 失敗したテスト名と失敗理由の行を含む
2. **Green のテスト出力**が報告に貼られている — 対象テストの PASS と、他テストが壊れていないこと
3. **テスト名に AC-ID が埋まっている** — Go は `TestXxx_AC4_2_<Scenario>`、TypeScript は
   テスト名文字列に `AC-4.2` を含める (`AC-4.2` は以下すべて記述例。実際は issue の対象 AC-ID を使う)

### 2.2 「意図した失敗」の定義 (Go でコンパイルエラーになる場合の扱い)

Red が**コンパイルエラー / import エラーだけ**の状態は「意図した失敗」として受理しない
(名前の打ち間違いと区別できない)。手順を次に固定する:

1. 対象の関数・メソッドをシグネチャのみで置く (本体は `constants.NewCodedError` で未実装を返す等)
2. テストを実行し、**assertion の失敗** (期待値と実際値の不一致) を 1 回以上観測する
3. その出力を Red の証拠とする

TypeScript も同様 (型エラーのみの状態を Red としない)。

### 2.3 OR が実行する照合コマンド

SA の報告を受けたら、OR は**自分の手で**次を実行して出力を PR / issue に残す。

```bash
# ① issue の対象 AC-ID がテスト名に存在するか (backend)
for ac in AC-4.2 AC-4.3; do                        # issue 本文の「対象 AC-ID」欄をそのまま並べる
  go_key=$(echo "$ac" | tr -d '-' | tr '.' '_')    # AC-4.2 -> AC4_2 (テスト名規約)
  if grep -rqE "func Test.*${go_key}" --include='*_test.go' .; then
    echo "OK   $ac"
  else
    echo "MISS $ac"                                # 1 件でも MISS があれば S-4 未完了
  fi
done

# ② その AC のテストだけを名指しで実行して赤/緑を自分で見る
go test ./... -run 'AC4_2' -v

# ③ frontend
grep -rn "AC-4.2" --include='*.test.ts' --include='*.test.tsx' src/
npx vitest run -t 'AC-4.2'
```

`MISS` が出た AC がある / 対象テストが 0 件マッチ (`no tests to run`) の場合は **S-4 は未完了**。
「テストは書いたが名前に AC-ID が無い」も未完了として差し戻す (AC ↔ テストの機械照合が壊れるため)。

### 2.4 infra リポでの読み替え

Terraform は失敗するテストを先に書けない範囲があるため、次の 2 段で読み替える:

| 対象 | S-4 (Red) の代替 | S-5 (Green) の代替 |
|---|---|---|
| `modules/` 配下 | `terraform test` で失敗するテストを書き、失敗出力を提示 | テスト通過の出力を提示 |
| `envs/` 配下 (ルートモジュール) | **期待する `plan` 差分を issue に事前宣言** (add / change / destroy のリソース名と件数)。**宣言の無い issue は S-1 で受領しない** (rule `02-issue-granularity.md` §4.1) | `terraform plan` の出力が宣言と一致することを提示。差異があれば理由を説明 |

却下案: 「infra は TDD の対象外とする」— `plan` を読まずに `apply` する経路を作るため却下。
却下案: 「全て `terraform test` に統一する」— 既存リソースの参照や環境固有の値を含む
ルートモジュールでは記述コストが実装コストを超えるため却下 (`modules/` に限定して適用する)。

## 3. レビュー差し戻しと反復上限 (AC-1.3)

| 項目 | 確定値 |
|---|---|
| 差し戻し条件 | レビュー結果に**重大 (Must Fix) が 1 件以上**あること |
| 中・軽微の扱い | この PR で直すか、**別 issue に切って先へ進む** (どちらにしたかを PR に書く)。**重大は別 issue に切らない** |
| レビューの実施回数上限 | **2 回** (= 差し戻し 2 回まで)。**3 巡目のレビューに入らない** |
| 上限到達時 | issue にコメントして**停止**し、**人間へエスカレーション** |
| 2 巡目に重大が残った場合 | **停止が先** (S-8 に進まない)。人間が続行を指示した場合のみ、その指摘反映 (S-8) を実装 SA を昇格させて実施する (rule `03-model-escalation.md` のトリガー ② = T-2 が正) |

巡目の数え方: **レビュー SA を 1 回呼ぶ = 1 巡**。1 巡目で重大あり → S-8 → 2 巡目 → まだ重大あり →
**S-8 も 3 巡目も行わず停止**。

### 3.1 上限到達時に issue へ残すコメント

```markdown
## レビュー差し戻し上限 (2 巡) に到達 — 人間の判断を要求

- ループ位置: S-7 (2 巡目完了) で停止
- ブランチ / 最終 commit: `<branch>` / `<sha>`
- 2 巡目も残った重大指摘:
  1. [file:line] <指摘の要約> — 1 巡目の修正内容と、それでも残った理由
- 収束しない原因の見立て (どちらかを選ぶ):
  - [ ] 設計の曖昧さ → §4 の設計リポ差し戻しに移行すべき
  - [ ] レビュー観点の解釈違い → 人間がどちらの解釈を採るか決める必要がある
- 要求する判断: <人間に決めてほしいことを 1 文で>
```

同時に PR は **draft のまま**にし、issue に `needs-human` ラベルを付ける。
**重大指摘を残したまま PR を ready にしない**。

## 4. 設計リポ (hassan_v3) への差し戻し (AC-1.4)

**実装で辻褄を合わせない**。設計に疑義があれば止めて設計リポへ返す。

### 4.1 判定基準 — 差し戻すもの (1 つでも該当すれば差し戻し)

1. **記述が無い**: 責務の配置先 (どの層か) / テーブル・カラム / エンドポイントとステータス / SSE イベント名 /
   所有者スコープの取り方 のいずれかが設計書に無く、実装で決めるしかない
2. **記述が現実と矛盾**: 設計書の前提 (既存テーブル・既存 API・外部サービスの仕様) が実物と食い違う
3. **解釈が 2 つ以上成り立ち、選択が外部契約に影響**: API の形・DB スキーマ・所有者境界・
   LLM に渡すデータ範囲のいずれかが解釈によって変わる
4. **AC がテストに翻訳できない**: 受入基準の判定条件が観測可能な形で書かれていない

### 4.2 差し戻しに当たらないもの (実装側で決めてよい)

命名・private ヘルパーの分割・テストデータ・ログ文言・エラーメッセージの日本語表現・
既存コードに前例がある書き方の選択。**判断根拠は「既存コードとの平仄」**で足りる。

### 4.3 誰が判定するか

| 判定者 | タイミング | 出力 |
|---|---|---|
| OR | **S-3 (計画時)** — 設計書を読んで計画を立てる過程で §4.1 に該当すると気付く | 実装に着手せず差し戻し。SA を呼ばない |
| 実装 SA | **S-5 (実装中)** — 未完了として差し戻し報告を上げる (エージェント定義の「設計に無い仕様の独断追加」禁止) | OR が §4.1 に照らして**受理判定**する |

OR は SA の差し戻し報告を**自分で判断して埋めない**。§4.2 に該当するだけなら SA に基準を示して再委譲し、
§4.1 に該当するなら §4.4 へ進む。

### 4.4 手順 (issue をどの状態にして止めるか)

1. **実装を止める**。書きかけのコードは**退避 commit + push** する (捨てない)。PR は作らない、
   または draft のまま置く
2. **issue にコメント**する (下記の形式)
3. **issue に `blocked-by-design` ラベル**を付け、担当を人間に移す。issue はクローズしない
4. **設計リポへの受け渡しは人間経由**。実装リポのエージェントは設計リポを編集しない —
   人間が hassan_v3 の `aidlc-docs/inception/<feature>/questions.md` に `[Answer]:` 付きの
   Q として起票し、確定後に `docs/design/` を更新する
5. **再開**: 設計書の更新コミットの参照 (hassan_v3 のパスとコミット) を issue にコメントし、
   **S-3 から**やり直す (計画が変わっている可能性があるため S-5 から再開しない)

```markdown
## 設計リポへの差し戻し (blocked-by-design)

- ループ位置: S-3 / S-5 のどちらで停止したか
- 退避ブランチ / commit: `<branch>` / `<sha>`
- 該当基準: §4.1 の 1 / 2 / 3 / 4 のどれか
- 到達したパターン: <実装しようとして設計に無かったことを 1〜3 行で>
- 設計書の該当箇所: hassan_v3 `docs/design/<file>.md` §<節> (記述が無い場合は「該当節なし」と書く)
- 成り立つ選択肢と影響:
  - 案 A: <内容> — 影響: <API / DB / 所有者境界 / コスト>
  - 案 B: <内容> — 影響: <同上>
- 実装側の仮定 (回答が無い場合に採るつもりの案): <案 X。ただし着手はしない>
```

**禁止**: 仮の実装を入れて「後で直す」/ 設計と違う判断を PR 説明にだけ書いて進める /
設計書に無いテーブル・エンドポイントを実装先行で作る。

## 5. 並列可否 (AC-1.5)

| 単位 | 並列 / 直列 | 条件・理由 |
|---|---|---|
| **異なる issue (同一リポ)** | **並列可** | 触るファイルが重複しないこと。**`git worktree` で隔離**し、1 issue = 1 worktree = 1 ブランチ = 1 セッション |
| **異なる issue (異なるリポ / 異なるサブツリー)** | **並列可** (依存が無い場合のみ) | 依存関係がある場合は直列 (`infra → app`、app 内は `backend → frontend`)。マージ順序は rule `02-issue-granularity.md` |
| **S-3 内の調査** | **並列可** | 独立した読み取り (既存コードの grep・設計書の確認) は同時に委譲してよい |
| **同一 issue の S-4 → S-5 → S-6 → S-7** | **直列必須** | Red を見ずに Green は書けない。検証前のコードをレビューに出すと指摘が検証結果と食い違う |
| **同一 issue の S-7 (レビュー)** | **直列・集約** | 差分全体を 1 セッションで見る。層ごと・ファイルごとに分割して並列レビューしない (層間の不整合が見えない) |
| **同一 issue の S-8 → S-6 → S-9** | **直列必須** | 指摘反映後に検証をやり直してから PR |
| **同一ファイルへの並列編集** | **禁止** | worktree を分けても `main` へのマージで衝突する。issue を切り直す |
| **同一 issue を 2 セッションで進める** | **禁止** | ループ位置 (§6) が二重に進み、二重実装になる |

並列で走らせるときは、各セッションに「**このセッションが触ってよいファイル**」を明示する
(他 issue の対象ファイルを列挙して禁止する)。

## 6. 中断・再開の記録 (AC-1.6)

**1 issue のループが 1 セッションで終わることを前提にしない** (コンテキスト上限・人間承認待ちで中断は必ず起きる)。
再開点が残らないと二重実装・作業漏れになるため、**ループ位置を issue コメントに残す**。

### 6.1 記録する形式

```markdown
## ループ位置 (2026-07-29 14:30 JST)

- 完了: S-1 → S-4 (AC-4.2 / AC-4.3 の Red を確認。出力は上のコメント)
- 現在: S-5 (実装中)
- ブランチ / 最終 commit: `feat/123-theme-list` / `a1b2c3d`
- レビュー巡目: 0 / 2
- 次の 1 手: UseCase 層の所有者スコープ絞り込みを実装し `go test ./usecase/...` を通す
- 停止理由: セッションのコンテキスト上限 / 人間承認待ち / 設計差し戻し のどれか
```

### 6.2 更新するタイミング (この 3 点。毎ステップでは書かない)

1. **セッションを終えるとき** (中断)
2. **人間待ちに入るとき** (S-2 の計画承認・§3 の上限到達・§4 の設計差し戻し・S-10 のマージ待ち)
3. **レビュー巡目が進んだとき** (S-7 完了時)

### 6.3 再開手順

1. issue の**最新のループ位置コメント**を読む
2. 記載のブランチを checkout し、`git log --oneline main..HEAD` と `git diff main...HEAD --stat` で
   実際の到達点を確認する (コメントと実態が食い違う場合は**実態を正**とし、コメントを訂正する)
3. 記載のステップから再開する。**ループ位置コメントが無い場合は S-3 からやり直す**
   (どこまで実装済みかを diff とテストから読み直す)

## 7. pre-commit / CI ゲートとマージ条件 (AC-6.1 / D-2)

**本ルールで CI ゲートを新規に追加しない**。既存の `.github/workflows/ci.yml` と pre-commit hook の
ジョブを、ループ上のどこで効くかとして位置づけるだけである
(ゲートの内容は設計リポ hassan_v3 の設計と `ci.yml` が正。別増分でゲートが追加された場合も同じ枠に載る)。

| 機構 | 走るタイミング | 内容 | ブロックするか |
|---|---|---|---|
| **pre-commit** | S-4 / S-5 / S-8 の各 commit | **staged パスでサブツリーに振り分ける**。backend: `go build` + `go vet` + 変更パッケージの `go test` / frontend: 対応する軽量チェック / infra: `terraform fmt -check` + `validate`。生成物・OpenAPI・Agent 再発行・MR-6 の同梱は**警告**(非ブロック) | する (`--no-verify` 禁止) |
| **CI (pull_request)** | **S-9 の PR 作成後 (以降の push ごとに再走)** | 下表の全ジョブ (path filter で変更サブツリー分のみ実行) | する (必須チェックは `gate` 1 本) |
| **CI (push)** | **`main` へのマージ時のみ** (`ci.yml` の `push` は `main` 限定。**退避 push では起動しない**) | 同上 | — (マージ後の確認) |
| **人間** | S-2 (条件付き) / S-10 | 計画承認 (該当 issue のみ) / PR approve + マージ | する |

### 7.1 既存 CI ジョブのループ上の位置

| サブツリー / リポ | ジョブ / ステップ | S-6 で先に潰せるか |
|---|---|---|
| backend | `go build` / `go vet` / `golangci-lint` / `go test` (UT) | すべて S-6 で同じコマンドを実行して潰す |
| backend | 生成物の差分チェック (sqlc / wire) | S-6 で `make -C backend sqlc wire` + `scripts/check-regen.sh backend` |
| backend | A-1 認証の適用漏れ検査 / A-4 所有者スコープの検査 / D-6 tool schema 3 者一致検査 | S-6 で該当スクリプトを実行。**未実装なら CI が落ちる設計なので、S-3 の計画に実装を含める** |
| frontend | `tsc --noEmit` / `test` / `build` / `lint` | すべて S-6 で実行 |
| **`contract` ジョブ** | `api/openapi.yaml` ↔ `frontend/src/generated` の再生成漏れ (MR-3) | S-6 の「契約」行 (§1.3) で実行。**backend だけ / frontend だけの PR でも走る** |
| **`gate` ジョブ** | 全ジョブの結果集約 (MR-1) | S-6 では再現しない (CI 固有)。**ブランチ保護の必須チェックはこれ 1 本のみ** |
| infra | `fmt -check` / `validate` / `tflint --recursive` / `plan` (dev) + `destroy`/`replace` の検出 | S-6 で実行。`plan` の差分は §2.4 の事前宣言と突き合わせる |

**CI で初めて赤を見るのは S-6 の手抜き**。S-6 は「CI と同じことをローカルで先に通す」ステップである。

### 7.2 マージ条件 (S-10。すべて満たすこと)

1. **CI の全ジョブが green** (必須チェックとして GitHub 側で設定する)
2. **S-7 のレビューで重大ゼロ** (レビュー結果の要約を PR に貼る)。§3 の上限到達で停止した PR はマージしない
3. **PR の DoD チェックリストが充足** (機械検証項目 / 人間判断項目の区別は rule `02-issue-granularity.md`)
4. **依存 issue がマージ済み** — infra への依存は `apply` 済みまで。API 破壊的変更は「backend で新旧併存 → frontend 切替 → 旧削除」の順序で、**3 段を別 PR に分ける** (MR-6)
5. **人間の approve とマージ操作** (エージェントはマージしない)

### 7.3 マージ後 (D-4 / D-6 のループ上の位置)

S-10 の後に走るリリース系は**人間承認点**であり、承認の機構は rule `04-human-checkpoints.md` が定める。
本ルールが定めるのはループとの接続だけ:

- `main` へのマージで **dev への継続デプロイ**が走る (backend は `deploy-backend.yml` / frontend は Vercel の Preview)
- **DB マイグレーションの適用 (D-4)** と **Managed Agent の再発行 (D-6)** を含む issue は、
  S-2 でその該当を宣言し、S-9 の PR 本文に「適用が必要な変更」として明記する。
  適用は人間の承認を経て行われ、**エージェントは実行しない**
- **本番デプロイ**は手動実行のみ (S-10 と別の判断)

## 8. 認証・テナント (A 領域) / 可観測性・LLM コスト (O 領域) の扱い (AC-6.3)

本ルールが担保するのは「**S-7 のレビューが A / O 観点を必ず通ること**」だけである。
**A / O の設計そのものは本ルールの対象外**であり、先送り先は設計リポ hassan_v3 の
親 feature `productionization` — **A は `docs/design/auth.md`、O は `docs/design/observability.md`** が正。

ループ上の担保:

- **S-7 の受理条件**: レビュー報告に次の結果が含まれていること。無ければ **S-7 を未完了として再実行**する
  - **A**: 新規エンドポイントが認証ミドルウェアを通っているか / 取得・一覧・更新・削除に所有者絞り込みがあるか /
    custom tool の引数 ID に所有者チェックがあるか / 401・403・404 の使い分け
  - **O**: 新しい LLM 呼び出し経路にトークン・コスト・`stop_reason` の記録があるか /
    `max_tokens` 切り詰め・JSON パース失敗・タイムアウトが観測可能か
  - 観点の本文はレビュー SA の定義 (`.claude/agents/code-reviewer.md` の観点 2 と 4、
    frontend / infra は各レビュー定義) が正。**本ルールに観点を複製しない**
- **S-3 / S-5 で A / O の設計判断が必要になったら §4 の差し戻し**にする
  (所有者スコープの取り方・コスト上限時の挙動・ログに載せる項目を実装で決めない)
